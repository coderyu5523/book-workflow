# 챕터 4. 인증과 인가

게시판의 기본 기능이 완성되었습니다. 없는 게시글은 예외로 처리했고, 응답에 담을 데이터도 고를 수 있게 되었습니다. 그런데 오픈이는 API를 테스트하다가 새로운 문제를 발견했습니다.

아무런 정보 없이 1번 게시글에 수정 요청을 보냈는데, 응답 창에 200이 돌아오며 제목과 내용이 그대로 변경되었습니다. 삭제 요청도 마찬가지였습니다.

*누구든 글 번호만 알면 내용을 다 바꾸고 지울 수 있네. 요청을 보낸 사람이 누구인지 묻는 절차가 전혀 없구나.*

오픈이는 선배를 찾아가 화면을 보여줬습니다.

**오픈이**: "선배님, 아무런 정보 없이 1번 게시글에 수정과 삭제 요청을 보냈는데 막히는 것 없이 200 성공이 뜹니다."

**선배**: "지금 코드는 들어오는 요청이 누구인지 묻지 않고 모두 컨트롤러로 보내기 때문이에요. 문만 열려 있고 지키는 사람이 없는 것이죠. 요청이 컨트롤러에 닿기 전에 누구인지부터 확인해야 합니다. 확인한 뒤에도 그 작업을 할 권한이 있는지 한 번 더 걸러내는 자리가 필요해요."

이번 챕터에서는 회원 테이블을 추가합니다. 요청이 컨트롤러로 넘어가기 전에 사용자가 누구인지 확인하고(인증), 해당 작업을 수행할 자격이 있는지(인가) 검증하는 과정을 구현해 봅니다.

## 4.1 현재 게시판의 문제

### 4.1.1 인증이 없는 게시판

문제를 눈으로 보고 시작하겠습니다. 인증 절차가 없는 상태에서 1번 게시글에 게시글 수정 API를 호출합니다.

```json [Hoppscotch] 1번 게시글 수정 요청
PUT http://localhost:8080/api/boards/1

{
  "title": "수정한 제목",
  "content": "수정한 내용"
}
```

응답은 200, 성공입니다.

*그림 4-3. 인증 절차가 없어 요청이 컨트롤러까지 그대로 도달합니다*

방금 보낸 수정 요청도 이 흐름을 그대로 지났습니다. 컨트롤러 앞에 요청을 보낸 사람을 확인하는 장치가 하나도 없어, 누가 보냈든 컨트롤러가 곧장 서비스를 호출해 게시글을 고칩니다.

## 4.2 신원을 증명하는 JWT

HTTP는 모든 요청을 독립적으로 처리하는 **무상태(Stateless)** 프로토콜입니다. 서버는 클라이언트의 로그인 상태를 저장하지 않으므로, 사용자는 새로운 요청을 보낼 때마다 자신이 누구인지 다시 증명해야 합니다.

이때 요청에 사용하는 인증 수단이 **JWT(JSON Web Token)** 입니다. JWT는 사용자 식별 정보를 JSON 데이터로 담고 위조 방지를 위한 디지털 서명을 더한 토큰입니다. 서버는 접속 상태를 따로 기록할 필요 없이, 전달받은 토큰의 서명만 검증하여 사용자를 확인합니다.

각 부분이 맡은 역할은 다음과 같습니다.

| 조각 | 담기는 값 |
|------|---------|

페이로드는 Base64로 바꾼 값이라 누구든 되돌려 읽을 수 있습니다. 그래서 비밀번호처럼 감춰야 할 값은 넣지 않습니다. 몰래 고치면 서명 계산 결과가 달라져 토큰에 붙어 있는 서명과 맞지 않게 됩니다.

:::tip
**서버가 기억하는 방식도 있습니다**

반대쪽 선택은 서버가 로그인한 사람을 기억해 두는 것입니다. 서버가 로그인 정보를 보관하고 로그인한 사람에게 식별 번호를 발급하면, 브라우저는 번호를 쿠키(Cookie)에 저장해 두었다가 요청마다 자동으로 함께 보냅니다. 서버는 번호로 보관해 둔 정보를 찾아 누구인지 확인합니다. 이렇게 서버가 상태를 기억하는 방식을 상태 유지(Stateful)라고 하고, 사람마다 보관하는 단위를 세션(Session)이라고 합니다. 접속자가 늘면 서버가 기억할 것도 함께 늘어납니다.
:::


## 4.3 테이블 관계

인증 기능을 구현하려면 먼저 회원 테이블을 추가해야 합니다. 하지만 무작정 테이블을 생성하기 전에, 기존 데이터와 어떤 관계를 맺을지부터 설계하는 것이 좋습니다.

관계형 데이터베이스(RDBMS)는 데이터를 행(Row)과 열(Column)로 구성된 테이블에 저장하며, 이러한 테이블들을 서로 연결하는 '관계'를 통해 전체 데이터를 관리합니다. 테이블이 맺을 수 있는 대표적인 관계로는 1:1, 1:N, N:M(다대다) 세 가지가 있습니다.

### 4.3.1 1:N 관계

## 4.4 회원 엔티티와 연관관계

### 4.4.1 회원 엔티티와 리포지토리

회원 테이블을 만들기 위해 엔티티를 추가합니다. `user/User.java`를 열고 아래 코드를 작성합니다.

```java [실습 1] user/User.java. 회원 엔티티
@NoArgsConstructor
@Data
@Entity
@Table(name = "user_tb")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    @Column(unique = true)
    private String username;
    private String password;
    private String email;

    @CreationTimestamp
    private Timestamp createdAt;

    @Builder
    public User(Integer id, String username, String password,
            String email, Timestamp createdAt) {
        this.id = id;
        this.username = username;
        this.password = password;
        this.email = email;
        this.createdAt = createdAt;
    }
}
```

`username`에 붙은 `@Column(unique = true)`는 같은 유저네임이 두 번 저장되지 못하도록 데이터베이스 차원에서 막습니다.

`user/UserRepository.java`를 열고 아래 코드를 작성합니다.

```java [실습 2] user/UserRepository.java. 유저네임으로 조회
public interface UserRepository extends JpaRepository<User, Integer> {

    Optional<User> findByUsername(String username);
}
```

`findBy` 뒤에 붙인 `Username`이 `User`의 `username` 필드를 가리켜 조회 조건을 정하고, 매개변수로 받은 값이 그 조건에 채워집니다.

### 4.4.2 게시글에 작성자 연결

`board/Board.java`에 작성자 회원 정보를 담을 필드를 추가합니다.

```java [실습 3] board/Board.java. 작성자 연관관계 추가
    @ManyToOne(fetch = FetchType.EAGER)
    @JoinColumn(name = "user_id")
    private User user;

    @Builder
    public Board(Integer id, String title, String content,
            Timestamp createdAt, User user) {
        this.id = id;
        this.title = title;
        this.content = content;
        this.createdAt = createdAt;
```

회원 한 명은 게시글을 여러 개 쓸 수 있습니다. 외래 키는 다수 쪽인 게시글에 속하므로 `Board`에 `@ManyToOne`을 붙입니다. `@JoinColumn(name = "user_id")`은 `board_tb`에 작성자의 기본 키를 담을 `user_id` 컬럼을 만듭니다.

### 4.4.4 JPQL 조인

게시글과 회원 정보를 함께 가져오려면 JOIN이 필요합니다. 조인은 두 테이블의 행을 옆으로 이어 붙여 한 번의 조회로 가져오는 문법이고, 어떤 행끼리 붙일지는 조건으로 정합니다. SQL은 그 조건을 `on` 절에 적지만, JPQL은 연관관계 필드 이름만 적습니다.

```java
select b from Board b join b.user u
```

`Board`에 `@ManyToOne`으로 `user` 필드를 추가해 두었기 때문에, JPQL에서 `b.user`처럼 필드 이름만으로 회원 엔티티를 조인할 수 있습니다.

조인은 조건이 일치하는 데이터만 가져올 것인지, 아니면 한쪽 테이블을 기준으로 조건이 일치하지 않는 데이터까지 포함할 것인지에 따라 종류가 나뉩니다.

| 조인 종류 | 기준 테이블 | 동작 방식 및 조회 결과 |
|----------|-----------|--------------------|
| (INNER) JOIN | 없음 | 양쪽 테이블 모두에 조건이 일치하는 행만 조회합니다. (조건이 일치하지 않으면 조회 대상에서 제외됩니다.) |
| LEFT JOIN | FROM 뒤 테이블 | FROM 쪽 테이블의 모든 행을 조회합니다. 상대 테이블에 조건이 일치하는 데이터가 없으면 해당 컬럼은 null로 채웁니다. |
| RIGHT JOIN | JOIN 뒤 테이블 | JOIN 쪽 테이블의 모든 행을 조회합니다. 상대 테이블에 조건이 일치하는 데이터가 없으면 해당 컬럼은 null로 채웁니다. |
| FULL JOIN | 양쪽 모두 | 두 테이블의 모든 행을 조회합니다. 서로 조건이 일치하지 않는 데이터는 각각 null로 채웁니다. |

작성자 정보가 없는 게시글까지 조회하려면 `left join`을 씁니다.

```java
select b from Board b left join b.user u
```

일반 SQL과 달리 JPQL의 기본 조인은 조인한 회원을 결과로 돌려주지 않고 기준 엔티티인 게시글만 반환합니다. 하지만 FETCH 키워드를 붙이면 연관된 데이터까지 한 번에 조회하여, 기준 엔티티 안의 연관 필드를 실제 데이터로 채워서 돌려줍니다.

```java
select b from Board b join fetch b.user u
```

이제 이 FETCH 조인을 게시글 상세 조회에 적용해 작성자까지 함께 내려 보겠습니다.

## 4.5 회원가입

`user/UserRequest.java`를 열고 회원가입 요청을 받을 DTO를 작성합니다.

```java [실습 9] user/UserRequest.java. 회원가입 요청 DTO
public class UserRequest {

    public record SaveDTO(String username, String password, String email) {

        // 요청 값으로 엔티티를 만든다
        public User toEntity() {
            return User.builder().username(username).password(password)
                    .email(email).build();
        }
    }
}
```

`SaveDTO`는 유저네임과 비밀번호, 이메일을 받습니다. `toEntity`는 리포지토리가 저장할 수 있도록 이 값으로 `User` 엔티티를 만들어 돌려줍니다.

`user/UserResponse.java`를 열고 회원 정보 응답에 사용할 DTO를 작성합니다.

```java [실습 10] user/UserResponse.java. 회원가입 응답 DTO
public class UserResponse {

    public record DTO(Integer userId, String username, String email,
            Timestamp createdAt) {

        public DTO(User user) {
            this(user.getId(), user.getUsername(), user.getEmail(),
                    user.getCreatedAt());
        }
    }
}
```

`DTO`는 반대 방향으로, 저장된 `User`에서 아이디와 유저네임, 이메일, 가입 시각을 꺼내 담습니다. 비밀번호는 응답에 담지 않습니다.

:::tip
**실무에서는 비밀번호를 반드시 암호화합니다**

비밀번호를 입력받은 그대로 저장하면 데이터베이스를 들여다보는 누구든 다른 사람의 비밀번호를 읽을 수 있습니다. 그래서 실무에서는 되돌릴 수 없는 해시로 바꿔 저장합니다. 이 책은 인증 흐름에 집중하려고 비밀번호를 평문으로 다룹니다.
:::

`user/UserService.java`를 열고 아래 코드를 작성합니다.

```java [실습 11] user/UserService.java. 회원가입
@RequiredArgsConstructor
@Service
public class UserService {

    private final UserRepository userRepository;

    // 유저네임 중복을 막고 저장한다
    @Transactional

        if (userRepository.findByUsername(requestDTO.username()).isPresent()) {
            throw new Exception400("이미 존재하는 유저네임입니다");
        }
        User user = userRepository.save(requestDTO.toEntity());

```

`findByUsername`이 회원을 찾아내면 이미 사용 중인 이름이므로 `Exception400`을 발생시켜 가입을 막습니다. 같은 이름을 쓰는 회원이 없으면 `toEntity`로 요청 값을 엔티티에 담아 저장합니다.

## 4.6 JWT 유틸

회원가입까지 마쳤으니 다음은 로그인입니다. 로그인에 성공하면 토큰을 만들어 건네야 하므로, 토큰을 만들고 여는 도구부터 만듭니다.

### 4.6.1 토큰 발급과 검증

토큰을 만들고 확인하는 코드에는 상수가 여럿 등장합니다. 먼저 뜻을 정리합니다.

| 상수 | 값 | 역할 |
|------|-----|------|
| HEADER | `"Authorization"` | 토큰을 담아 보내는 요청 헤더의 이름 |
| TOKEN_PREFIX | `"Bearer "` | 토큰 앞에 붙이는 표식 |
| SECRET | 서버만 아는 비밀 문자열 | 서명하고 검증할 때 사용하는 열쇠 |
| EXPIRATION_TIME | 7일 | 토큰이 유효한 기간 |

`core/util/JwtUtil.java`를 열고 아래 코드를 작성합니다. 위 상수 네 개는 클래스 맨 위에 필드로 선언되어 있고, 아래 두 메서드가 이 상수를 사용합니다.

```java [실습 13] core/util/JwtUtil.java. JWT 발급과 검증
    // 1. 유저 정보를 담아 토큰을 만든다
    public static String create(User user) {
        String jwt = JWT.create()
                .withSubject(user.getUsername())
                .withExpiresAt(new Date(System.currentTimeMillis() + EXPIRATION_TIME))
                .withClaim("id", user.getId())
                .sign(Algorithm.HMAC512(SECRET));
        return TOKEN_PREFIX + jwt;
    }

    // 2. 서명을 확인하고 담긴 정보로 User를 복원한다
    public static User verify(String jwt) {
        DecodedJWT decodedJWT = JWT.require(Algorithm.HMAC512(SECRET))
                .build().verify(jwt);
        Integer userId = decodedJWT.getClaim("id").asInt();
        String username = decodedJWT.getSubject();
        return User.builder().id(userId).username(username).build();
    }
```

`create`는 유저 정보를 페이로드에 담고 `SECRET`으로 서명해 토큰 한 줄을 만듭니다. `verify`는 그 반대로, 서명이 맞는지 확인한 뒤 페이로드의 값으로 `User`를 되살립니다. 서명이 어긋나면 예외가 납니다.

두 메서드는 서버를 띄우지 않고도 확인할 수 있습니다. `test/core/util/JwtUtilTest.java`를 열고 아래 코드를 작성합니다.

```java [실습 14] test/core/util/JwtUtilTest.java. 발급한 토큰을 다시 열어 보기
public class JwtUtilTest {

    @Test
    public void create_and_verify_test() {
        // given
        User user = User.builder().id(1).username("ssar").build();
        // when
        String bearerJwt = JwtUtil.create(user);
        String jwt = bearerJwt.replace(JwtUtil.TOKEN_PREFIX, "");
        User decodedUser = JwtUtil.verify(jwt);
        // eye
        System.out.println("bearerJwt : " + bearerJwt);
        System.out.println("id : " + decodedUser.getId());
        System.out.println("username : " + decodedUser.getUsername());
    }
}
```

`create`가 돌려준 문자열은 `Bearer `로 시작하므로, 그 표식을 떼고 남은 부분만 `verify`에 넘깁니다. 콘솔에 찍힌 아이디와 유저네임이 넣었던 값과 같으면 토큰이 제대로 오갑니다.

### 4.6.2 토큰 꺼내기

`JwtUtil`이 토큰을 만들고 여는 도구라면, 도구를 요청에 연결하는 코드가 하나 더 필요합니다. `core/util/JwtProvider.java`를 열고 아래 코드를 작성합니다.

```java [실습 15] core/util/JwtProvider.java. 토큰 추출과 유저 복원
@Component
public class JwtProvider {

    // 1. 헤더에서 "Bearer " 접두어를 떼고 토큰만 꺼낸다
    public String resolveToken(HttpServletRequest request) {
        String bearerToken = request.getHeader(JwtUtil.HEADER);
        if (bearerToken != null && bearerToken.startsWith(JwtUtil.TOKEN_PREFIX)) {
            return bearerToken.replace(JwtUtil.TOKEN_PREFIX, "");
        }
        return null;
    }

    // 2. 토큰이 유효하면 User, 아니면 null
    public User getUser(String token) {
        try {
            return JwtUtil.verify(token);
        } catch (Exception e) {
            return null;
        }
    }
}
```

요청 헤더에서 토큰을 꺼내 유저로 되살리고, 토큰이 없거나 어긋나면 `null`을 돌려줍니다. 뒤에서 만들 필터는 이 결과만 보고 신원을 판단합니다.

이 도구를 쓰는 곳이 로그인입니다. 로그인 요청을 담을 DTO를 `UserRequest`에 추가합니다.

```java [실습 16] user/UserRequest.java. 로그인 요청 DTO
    public record LoginDTO(String username, String password) {
    }
```

받은 유저네임과 비밀번호로 회원을 확인합니다. `user/UserService.java`에 아래 메서드를 추가합니다.

```java [실습 17] user/UserService.java. 로그인

    public String 로그인(UserRequest.LoginDTO requestDTO) {
        User user = userRepository.findByUsername(requestDTO.username())
                .orElseThrow(() -> new Exception401("유저네임 또는 비밀번호가 일치하지 않습니다"));
        if (!user.getPassword().equals(requestDTO.password())) {
            throw new Exception401("유저네임 또는 비밀번호가 일치하지 않습니다");

    }
```

유저네임이 없든 비밀번호가 틀리든 같은 메시지로 답해, 어떤 유저네임이 있는지 밖으로 알려지지 않게 합니다. 맞으면 앞에서 만든 `JwtUtil.create`로 토큰을 만들어 돌려줍니다.

컨트롤러는 서비스가 돌려준 토큰 문자열을 응답 바디에 담아 내보냅니다.

클라이언트는 이 토큰을 받아 두었다가 이후 요청마다 지니고 옵니다.


## 4.8 인증 필터

이제 요청을 받는 자리에 인증을 둡니다. 인증과 인가로 나눈 둘 중 신원을 밝히는 쪽입니다. 요청마다 헤더의 토큰을 확인해, 유효하면 신원을 요청에 담아 둡니다.

이 일을 맡는 것이 **필터(Filter)** 입니다. 필터는 요청이 컨트롤러에 도달하기 전에 먼저 거쳐 가는 지점입니다. 스프링에서는 `OncePerRequestFilter`를 상속해, 요청 한 건마다 한 번씩 실행되는 필터를 만듭니다.

`core/filter/JwtAuthenticationFilter.java`를 열고 아래 코드를 작성합니다.

```java [실습 19] core/filter/JwtAuthenticationFilter.java. 인증 필터
@RequiredArgsConstructor
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    public static final String SESSION_USER = "sessionUser";
    private final JwtProvider jwtProvider;

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain) throws ServletException, IOException {
        // 1. 헤더에서 토큰을 꺼낸다
        String token = jwtProvider.resolveToken(request);
        // 2. 유효하면 신원을 요청에 담아 둔다 (막지는 않는다)
        if (token != null) {
            User sessionUser = jwtProvider.getUser(token);
            if (sessionUser != null) {
                request.setAttribute(SESSION_USER, sessionUser);
            }
        }
        filterChain.doFilter(request, response);
    }
}
```

필터가 하는 일은 신원을 밝혀 두는 것까지입니다. 토큰을 꺼내 유저로 복원하면, `request.setAttribute`로 복원한 유저를 요청에 `sessionUser`라는 이름으로 담아 둡니다. 뒤에 오는 컨트롤러가 이 이름으로 "이 요청을 보낸 사람"을 알 수 있습니다.

여기서 중요한 것은 마지막 줄입니다. 토큰이 없거나 틀려도 필터는 요청을 막지 않고 `filterChain.doFilter`로 그대로 통과시킵니다. 신원이 확인되면 유저가 요청에 담기고, 확인되지 않으면 담기지 않은 채 지나갑니다. 막는 일은 인증이 아니라 인가가 하므로, 다음 절에서 처리합니다.


## 4.9 쓰기 요청 막기

필터가 담아 둔 유저를 보고 요청을 막을지 말지 정하는 자리가 필요합니다. 그 자리는 요청을 받는 컨트롤러입니다.

게시글 목록과 상세는 로그인하지 않은 사람도 볼 수 있어야 합니다. 반면 게시글을 쓰거나 고치거나 지우는 요청은 로그인한 사람만 보낼 수 있어야 합니다. 같은 게시판 주소라도 요청에 따라 기준이 갈리므로, 판단은 요청을 받는 메서드마다 따로 합니다.

`board/BoardController.java`를 열고 삭제 메서드를 아래처럼 고칩니다.

```java [실습 20] board/BoardController.java. 삭제 요청에서 로그인 확인
    @DeleteMapping("/{boardId}")
    public ResponseEntity<?> deleteById(HttpServletRequest request,
            @PathVariable("boardId") Integer boardId) {
        // 1. 필터가 담아 둔 유저를 꺼낸다
        User sessionUser = (User) request.getAttribute("sessionUser");
        // 2. 없으면 로그인하지 않은 요청이다
        if (sessionUser == null) {
            throw new Exception401("로그인이 필요합니다");
        }
        boardService.게시글삭제(boardId, sessionUser.getId());
        return Resp.ok(null);
    }
```

`request.getAttribute("sessionUser")`는 필터가 담아 둔 유저를 꺼냅니다. 토큰이 없었거나 검증을 통과하지 못했다면 담긴 것이 없어 `null`이 나오므로, `Exception401`을 발생시켜 요청을 여기서 끊습니다. 유저가 들어 있으면 그 아이디를 서비스에 넘깁니다.

게시글을 쓰고 고치는 메서드에도 같은 검사를 넣습니다. 반대로 목록과 상세를 돌려주는 메서드에는 넣지 않아, 로그인하지 않은 사람도 그대로 읽습니다.

## 4.10 소유자 검증과 예외

로그인 확인까지 세웠지만, 문제의 절반은 아직 남아 있습니다. 로그인한 사람이 다른 사람이 쓴 게시글에 게시글 수정 API를 호출해도 응답은 그대로 200입니다. 컨트롤러는 로그인을 했는지만 확인하기 때문에, 다른 사람이 쓴 게시글을 고치려는 요청도 일단 통과시킵니다. 그래서 이 게시글을 쓴 본인이 맞는지를 게시글마다 한 번 더 확인해야 합니다.

이 확인은 컨트롤러가 아니라 서비스에서 합니다. 어느 게시글의 작성자인지는 게시글을 조회해 봐야 알 수 있기 때문입니다. 로그인하지 않은 요청은 컨트롤러에서 `Exception401`로 끊었고, 로그인은 했지만 권한이 없는 요청은 서비스에서 `Exception403`으로 끊습니다. 챕터 3의 전역 예외 처리기가 둘을 받아 401과 403으로 응답합니다.

## 4.11 게시글 삭제 권한 검증

먼저 삭제입니다. `board/BoardService.java`의 삭제 메서드를 아래처럼 고칩니다.

```java [실습 21] board/BoardService.java. 삭제 소유자 검증
    @Transactional
    public void 게시글삭제(Integer boardId, Integer sessionUserId) {
        Board board = boardRepository.findByIdJoinUser(boardId)
                .orElseThrow(() -> new Exception404("게시글을 찾을 수 없습니다"));
        // 작성자 본인이 아니면 막는다
        if (!board.getUser().getId().equals(sessionUserId)) {
            throw new Exception403("게시글을 삭제할 권한이 없습니다");
        }
        boardRepository.delete(board);
    }
```

삭제 메서드가 로그인한 사람의 아이디 `sessionUserId`를 하나 더 받습니다. `findByIdJoinUser`로 게시글을 작성자와 함께 조회해, 게시글의 작성자와 요청자의 아이디가 다르면 작성자가 아니므로 `Exception403`을 발생시킵니다.

## 4.12 게시글 쓰기에 작성자 추가

게시글을 새로 쓰는 `게시글추가`는 주인을 확인할 필요가 없습니다. 아직 주인이 없는 새 게시글입니다. 대신 로그인한 사람을 이 게시글의 작성자로 정해서 저장합니다. 그래서 `BoardRequest`의 `toEntity`가 작성자를 받도록 바뀝니다.

```java [실습 22] board/BoardRequest.java. 작성자를 연결하는 toEntity
    public Board toEntity(User user) {
        return Board.builder().title(title).content(content).user(user).build();
    }
```

챕터 3에서는 `toEntity`가 제목과 내용만 담았습니다. 여기에 작성자가 더해집니다.

그럼 이 로그인한 사람은 어디서 올까요? 앞에서 필터가 토큰을 확인하고, `sessionUser`라는 이름으로 유저를 넣어 뒀습니다. 컨트롤러는 담아 둔 유저를 `request.getAttribute("sessionUser")`로 꺼냅니다. 작성은 유저를 그대로, 수정과 삭제는 유저의 아이디만 서비스에 넘깁니다. 목록과 상세는 로그인이 필요 없으므로 챕터 3 그대로 둡니다. 쓰기 메서드는 아래처럼 바뀝니다.

```java [실습 23] board/BoardController.java. 쓰기 요청에서 로그인 유저 꺼내기
    // 게시글 쓰기 — 로그인 유저를 작성자로 넘긴다
    @PostMapping
    public ResponseEntity<?> save(HttpServletRequest request,
            @RequestBody BoardRequest.SaveDTO requestDTO) {
        User sessionUser = (User) request.getAttribute("sessionUser");
        if (sessionUser == null) {
            throw new Exception401("로그인이 필요합니다");
        }
        BoardResponse.DTO respDTO = boardService.게시글추가(requestDTO, sessionUser);
        return Resp.ok(respDTO);
    }

    // 게시글 수정 — 유저 아이디를 소유자 검증에 넘긴다
    @PutMapping("/{boardId}")
    public ResponseEntity<?> update(HttpServletRequest request,
            @PathVariable("boardId") Integer boardId,
            @RequestBody BoardRequest.UpdateDTO requestDTO) {
        User sessionUser = (User) request.getAttribute("sessionUser");
        if (sessionUser == null) {
            throw new Exception401("로그인이 필요합니다");
        }
        BoardResponse.DTO respDTO =
                boardService.게시글수정(boardId, requestDTO, sessionUser.getId());
        return Resp.ok(respDTO);
    }
```

## 4.13 게시글 수정 권한 검증

수정도 같은 방식입니다. `board/BoardService.java`의 수정 메서드를 아래처럼 고칩니다.

```java [실습 24] board/BoardService.java. 소유자 검증
    @Transactional
    public BoardResponse.DTO 게시글수정(
            Integer boardId, BoardRequest.UpdateDTO requestDTO, Integer sessionUserId) {
        Board board = boardRepository.findByIdJoinUser(boardId)
                .orElseThrow(() -> new Exception404("게시글을 찾을 수 없습니다"));
        // 작성자 본인이 아니면 막는다
        if (!board.getUser().getId().equals(sessionUserId)) {
            throw new Exception403("게시글을 수정할 권한이 없습니다");
        }
        board.setTitle(requestDTO.title());
        board.setContent(requestDTO.content());
        return new BoardResponse.DTO(board);
    }
```

소유자 검증을 통과했을 때만 제목과 내용을 바꿉니다. 저장 코드는 없지만 더티체킹이 변경을 반영합니다.

이제 처음 문제로 돌아가 확인합니다. 로그인하면 `Bearer `로 시작하는 토큰을 받습니다. 이 토큰을 `Authorization` 헤더에 담아서 다른 사람이 쓴 게시글에 게시글 수정 API를 호출하면, 앞서 그냥 통과하던 요청이 이번에는 403으로 막힙니다.

오픈이는 자기 계정으로 로그인한 뒤, 다른 사람이 쓴 게시글에 게시글 수정 API를 다시 호출했습니다.

*이번엔 막히겠지.*

응답 창에 403이 돌아왔습니다. 게시글을 수정할 권한이 없다는 메시지도 함께였습니다. 로그인하지 않은 쓰기는 401에서, 작성자가 아닌 수정은 403에서, 각각 다른 문에 걸려 멈췄습니다. 오픈이는 선배를 찾아가 응답 창을 다시 보여줬습니다.

**오픈이**: "이제 로그인하지 않으면 게시글이 안 써지고, 로그인해도 다른 사람이 쓴 게시글은 못 고칩니다."<br>
**선배**: "아무 정보 없이 통과하던 요청이 이제 401과 403으로 갈려서 막히네요."

확인하는 자리가 비어 있던 컨트롤러 앞에는 이제 신원을 밝히는 필터가 놓였고, 컨트롤러와 서비스는 그 신원으로 자격을 따집니다.

그런데 이 게시판에는 아직 게시글만 있고 댓글이 없습니다. 다음 챕터에서는 게시글에 댓글을 달고, 댓글이 게시글에 딸리는 연관관계를 만들다 조회 성능 문제와 마주칩니다.

:::remember
**이것만은 기억하자**

- **인증은 "너 누구야"를 밝히고, 인가는 "그걸 할 권한이 있어"를 따집니다.** 이번 챕터에서 인증은 토큰을 확인해 신원을 담는 필터가, 인가는 쓰기 요청을 막는 컨트롤러와 작성자를 대조하는 서비스가 맡습니다.
- **로그인에 성공하면 JWT를 발급하고, 클라이언트는 토큰을 요청마다 지니고 옵니다.** 서버는 토큰의 서명만 검증하면 되므로 로그인 상태를 따로 기억하지 않습니다. 다른 사람이 쓴 게시글에 보낸 쓰기 요청은 서비스의 소유자 검증에서 403으로 막힙니다.
:::
