# 챕터 1. 리플렉션 - 스프링은 어떻게 내 코드를 실행하는가

오픈이는 개발을 공부하는 학생입니다. 이번 학기 과제는 웹 서버를 하나 만들어 제출하는 것입니다.

배운 것이 자바뿐이라 자바로 서버를 짜기 시작했지만, 몇 줄 쓰기도 전에 막히고 말았습니다. 브라우저의 요청을 받으려면 통신 연결부터 열어야 했고, 요청에서 주소를 꺼내려면 문자열을 한 글자씩 잘라 읽어야 했습니다.

주소를 겨우 꺼내도 끝이 아니었습니다. 주소마다 어떤 처리를 할지 일일이 연결하고, 응답 규격까지 직접 맞춰야 했습니다.

*과제는 게시판인데, 서버 뼈대만 만들다 학기가 끝나겠네.*

다음 날, 같은 수업을 듣는 선배에게 사정을 털어놓았습니다.

**선배**: "그런 기본 뼈대를 직접 만드는 사람은 없어요. 스프링을 쓰면 다 갖춰져 있거든요."

선배의 말에 스프링을 찾아보니, 소개 첫 줄에 "자바 웹 프레임워크"라고 적혀 있었습니다. 라이브러리는 수업에서 여러 번 써봤지만 프레임워크는 처음입니다. 둘은 무엇이 다를까요?

:::goal

## 1.1 프레임워크

### 1.1.1 라이브러리와 프레임워크는 무엇이 다를까

라이브러리(Library)는 개발자가 필요할 때 꺼내 쓰는 기능입니다. 날짜 계산이 필요하면 날짜 라이브러리를, 파일을 읽어야 하면 파일 라이브러리를 원하는 위치에서 호출합니다. 어떤 기능을 언제 부를지 개발자가 결정하며, 프로그램의 전체 흐름도 직접 제어합니다.

반면, 프레임워크(Framework)는 이 주도권이 뒤집혀 있습니다. 집을 새로 지을 때 기둥과 벽, 배관이 이미 갖춰진 골조를 떠올려 보세요. 개발자는 그 안에서 방만 꾸미면 됩니다. 프레임워크도 이처럼 프로그램에 공통으로 필요한 뼈대를 미리 갖춰 둔 틀입니다. 개발자는 뼈대를 다시 만들지 않고, 정해진 위치에 자신의 코드만 얹으면 됩니다.

### 1.1.2 제어의 역전

뼈대를 프레임워크가 쥐고 있다는 것은, 프로그램의 전체 흐름도 프레임워크가 주도한다는 뜻입니다. 개발자가 작성한 코드가 언제 실행될지 역시 프레임워크가 결정합니다.

라이브러리를 쓸 때는 개발자가 필요한 순간에 직접 기능을 호출했습니다. 프레임워크에서는 이 방향이 반대가 됩니다. 개발자는 코드를 정해진 자리에 올려두기만 하고, 이를 호출해 실행하는 주체는 프레임워크가 됩니다. 이처럼 실행의 주도권이 개발자에서 프레임워크로 넘어가는 현상을 제어의 역전(IoC, Inversion of Control)이라고 합니다.

## 1.2 스프링 프레임워크

### 1.2.1 스프링이 갖춰 둔 웹 서버의 뼈대

앞서 자바만으로 서버를 만들다 막혔던 상황을 떠올려 보겠습니다. 요청을 받고, 주소에 맞는 로직을 연결하고, 응답을 반환하는 뼈대를 모두 직접 짜야 했습니다.

스프링은 자바로 웹 서버를 만들 때 필요한 이 뼈대를 미리 갖춘 프레임워크입니다. 요청을 받아들이고, 주소를 라우팅하며, 결과를 응답으로 내보내는 공통 작업은 스프링이 담당합니다. 개발자는 어떤 주소에 어떤 응답을 반환할지, 핵심 기능만 작성하면 됩니다.

### 1.2.2 스프링은 내 메서드를 어떻게 찾아 실행할까

여기서 의문이 하나 생깁니다. 우리는 직접 만든 메서드를 스프링에 명시적으로 등록한 적이 없습니다. 클래스를 만들고 그 위에 표식 하나를 붙였을 뿐인데, 요청을 보내면 해당 메서드가 실행됩니다.

스프링은 이 메서드가 어디에 있는지 어떻게 알고 호출하는 것일까요? 그 해답은 리플렉션에 있습니다.

## 1.3 리플렉션 - 스프링이 내 코드를 찾아 실행하는 원리

스프링의 동작을 순수 자바로 구현해 보면 크게 세 단계로 나뉩니다.

**조건문 분기.** 가장 단순한 방법입니다. 요청 주소마다 어떤 메서드를 호출할지 if-else문으로 일일이 연결합니다. 하지만 메서드가 추가될 때마다 조건문도 수정해야 하므로 금방 한계에 부딪힙니다.

**리플렉션 도입.** 리플렉션은 프로그램 실행 도중에 클래스의 메서드와 그 위에 붙은 표식을 읽어내는 기술입니다. 이 표식이 바로 어노테이션(Annotation)입니다. 어노테이션은 클래스나 메서드에 붙이는 특별한 표시로, 실행 중에 리플렉션이 그 표시를 읽어 알맞은 동작을 자동으로 수행합니다. 메서드마다 담당할 주소를 어노테이션으로 달아 두면, 조건문 없이 표식만 읽어서 알맞은 메서드를 찾아 실행할 수 있습니다. 새로운 메서드를 추가할 때도 표식만 달면 되므로 호출부 코드를 건드릴 필요가 없습니다.

**컴포넌트 스캔.** 클래스의 위치를 미리 알지 못해도, 지정된 폴더를 탐색해 표식이 붙은 클래스만 찾아 객체로 생성해 둡니다. 개발자가 직접 등록하지 않아도 프로그램이 알아서 필요한 객체를 준비합니다.

이 세 단계가 스프링이 실제로 하는 일입니다. 프로젝트가 시작되면 스프링은 폴더를 뒤져 표식이 붙은 클래스를 객체로 만들어 두고(컴포넌트 스캔), 클라이언트의 요청이 오면 표식을 읽어 알맞은 메서드를 리플렉션으로 실행합니다(디스패처 서블릿). 앞서 직접 호출한 적 없는 메서드가 실행된 이유가 바로 이것입니다.

## 1.4 빈과 의존성 주입

스캔 단계에서 짚고 넘어갈 부분이 하나 더 있습니다. 바로 표식이 붙은 클래스를 찾아 객체로 생성해 두는 과정입니다. 개발자가 직접 만든 것이 아니라, 프로그램이 표식을 확인하고 대신 객체를 생성해 보관합니다.

스프링도 동일하게 동작합니다. 표식이 붙은 클래스를 찾아 객체로 만들고, 자신이 관리하는 공간에 담아 둡니다. 이렇게 스프링이 직접 생성하고 관리하는 객체를 빈(Bean)이라고 부릅니다.

더 나아가 스프링은 생성된 빈들을 서로 필요한 곳에 조립해 줍니다. 게시판 컨트롤러가 게시판 서비스 객체를 필요로 할 때, 개발자가 직접 주입하지 않아도 스프링이 보관소에서 알맞은 빈을 꺼내 넣어줍니다. 이처럼 객체가 필요한 곳에 외부에서 객체를 밀어 넣어주는 방식을 의존성 주입(DI, Dependency Injection)이라고 합니다.

컨트롤러가 서비스를 주입받아 사용하는 구체적인 모습은 다음 챕터에서 게시판을 만들며 직접 확인해 보겠습니다.

이 책은 코드를 많이 쓰기보다 스프링의 개념과 큰 흐름을 이해하고, 단계별로 게시판을 완성하며 익히는 것을 목표로 합니다. 한 챕터씩 스프링의 큰 흐름을 따라가 보겠습니다.
