# 5. 스프링 시큐리티(Spring Security)

# 5.1 스프링 시큐리티

> **스프링 시큐리티는 스프링 기반 애플리케이션의 보안 프레임워크로, 인증(Authentication)과 권한 관리(Authorization)를 합니다. 요청이 컨트롤러에 도달하기 전, SecurityFilterChain을 통해 로그인, 토큰 검증, 세션 관리, CSRF 방어 등 보안 기능을 제공합니다.**
> 

## 5.1.1 스프링 시큐리티란?

스프링 시큐리티를 예를 들어 설명을 하겠습니다.

아래 그림처럼 성이 있습니다. 이 성은 입구만 있으며, 출입자에 대한 신원을 검증하지 않습니다. 

따라서 누구나 성 내부의 자원에 접근할 수 있으며, 이런 구조는 보안에 매우 취약합니다.

![**2.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%201.png)

여기서 성은 우리가 구축한 서버를 의미하고, 성벽과 호수는 스프링 시큐리티에 해당합니다.

외부 사용자가 서버에 요청을 보내면, 스프링 시큐리티는 요청의 **인증(Authentication)** 과 **인가(Authorization)** 를 검증하고, CORS나 XSS와 같은 비정상적인 요청을 차단하는 **보안** 역할을 합니다.

## 5.1.2 시큐리티 필터 체인

> **시큐리티 필터 체인은 사용자의 요청이 서버의 컨트롤러로 전달되기 전 인증, 인가, 예외 처리 등을 순차적으로 검증하는 보안 필터들의 연결 구조입니다.**
> 

로그인에 성공하면 스프링 시큐리티는 인증 결과를 담은 **Authentication** 객체를 생성하고, 이를 **Security Session**에 저장합니다. 

![**4.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%203.png)

**4.png**

<aside>
💡

**시큐리티 세션(Security Session)은 사용자가 로그인했을 때 만들어지는 보안 전용 세션입니다. 로그인 성공 시 생성된 Authentication 객체를 내부에 저장하고, 사용자 정보가 필요할 때 꺼내 쓸 수 있습니다.**

</aside>

스프링의 필터는 스프링 내부에서 가장 앞단에 위치하며, 모든 요청에 대해 전·후 처리를 수행하는 계층입니다. 스프링 필터는 여러 개의 필터가 체인 형태로 구성되어 있습니다. 

스프링 시큐리티는 이 필터 체인에 **FilterChainProxy**를 등록해 스프링 필터 내에서 동작합니다.

**5.png**

그리고 사용자가 HTTP 요청을 보내면 FilterChainProxy가 스프링 컨테이너 내부의 SecurityFilterChain을 호출, 내부의 보안 필터가 인증 및 인가 검증을 수행합니다.

# 5.2 시큐리티 필터 종류

스프링 시큐리티의 대표적인 필터 종류를 알아보겠습니다.

## 5.2.1 UsernamePasswordAuthenticationFilter

UsernamePasswordAuthenticationFilter는  **POST /login** 요청을 가로채 username, password를 검증합니다. 만약 검증에 성공하면 **Authentication** 객체를 반환합니다.

![**7.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%206.png)

**7.png**

UsernamePasswordAuthenticationFilter는 세션 기반으로 JWT를 사용한다면 비활성화 합니다.

## 5.2.2 BasicAuthenticationFilter

BasicAuthenticationFilter는 HTTP 요청 시 Header의 Authentication 값이 base64로 인코딩된 문자열인 경우, username과 password 를 꺼내 검증합니다. 검증 성공 시 Authentication 객체를 반환합니다.

![**8.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%207.png)

**8.png**

BasicAuthenticationFilter 역시 JWT를 사용한다면 비활성화 합니다.

## 5.2.3 ExceptionTranslationFilter

ExceptionTranslationFilter는 인증 또는 권한 검증 과정에서 발생한 예외를 처리하는 필터입니다. 

![**9.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%208.png)

**9.png**

## 5.2.4 AuthorizationFilter

AuthorizationFilter는 이미 인증된 사용자가 요청한 자원에 접근할 권한이 있는지 검사하는 필터입니다. 

예를 들어, 역할이 일반 회원(**USER**)과 관리자(**ADMIN**)로 나뉘어 있을 때, 관리자 전용 자원에 대한 요청이 들어오면 이 필터는 사용자의 권한이 ROLE_ADMIN인지 확인합니다. 권한이 있으면 컨트롤러로 요청을 전달하고, 권한이 없으면 403 Forbidden 응답을 반환합니다.

![**10.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%209.png)

**10.png**

## 5.2.5 OncePerRequestFilter

OncePerRequestFilter는 스프링 시큐리티에서 제공하는 추상 클래스입니다. HTTP 요청마다 한 번만 실행되는 필터를 만들 때 사용합니다.

예를 들어 게시글 작성 후 게시글 목록 페이지로 이동한다고 가정하겠습니다.

사용자가 게시글 작성 요청을 보내면 HTTP 요청이 시작되고, 필터 단계에서 먼저 토큰 검증이 수행됩니다. 토큰이 정상적으로 검증되면 게시글 생성 로직이 실행되고, 이후 서버는 게시글 목록 페이지로 응답을 전달합니다.

![**11.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%2010.png)

**11.png**

이때 사용자는 서버의 지시에 따라 새로운 HTTP 요청을 보내 게시글 목록 페이지를 다시 받아오게 됩니다.

![**12.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%2011.png)

**12.png**

<aside>
💡

**사용자는 단 한 번만 HTTP 요청을 보냈지만, 서버 내부의 처리 과정 때문에 동일한 요청이 필터 체인을 여러 번 통과하면서 중복 실행되는 상황이 발생할 수 있습니다. 
이런 경우 OncePerRequestFilter를 사용해 한 번만 실행되도록 보장할 수 있습니다.**

</aside>

아래 그림처럼 HTTP 요청이 들어올 때 서버 내부 처리 과정으로 인해 동일 요청이 여러 번 필터 체인을 통과하더라도, 토큰 검증 로직은 요청 당 한 번만 실행되도록 보장됩니다.

# 5.3 인가 필터 구현

filter 폴더의 JwtAuthorizationFilter 클래스를 구현해보겠습니다.

JwtAuthorizationFilter 클래스는 OncePerRequestFilter를 구현해 요청이 왔을 때만 실행되며,  JwtProvider 클래스를 활용해 토큰을 검증하는 역할을 합니다.

**core/filter/JwtAuthorizationFilter.java**

```java
package com.metacoding.springv2.core.filter;

import com.metacoding.springv2.core.util.JwtProvider;
import jakarta.servlet.*;
import jakarta.servlet.http.*;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.web.filter.OncePerRequestFilter;
import lombok.RequiredArgsConstructor;
import java.io.IOException;

@RequiredArgsConstructor
public class JwtAuthorizationFilter extends OncePerRequestFilter {
    
    private final JwtProvider jwtProvider;
    
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) throws ServletException, IOException {
        String token = jwtProvider.resolveToken(request);

        if (token != null && jwtProvider.validateToken(token)) {
            Authentication authentication = jwtProvider.getAuthentication(token);
            if (authentication != null) {
		            // 로그인 성공시 인증 객체 저장
                SecurityContextHolder.getContext().setAuthentication(authentication);
            }
        }

        filterChain.doFilter(request, response);
    }
}
```

<aside>
💡

**JWT 기반 서버는 세션 서버와 달리, Securiry Session에 Authentication 객체가 자동으로 저장되지 않습니다. 따라서 로그인 성공 시 시 SecurityContextHolder에 Authentication 객체를 담아 JWT 기반 서버에서도 Authentication 를 꺼내 사용할 수 있도록 처리합니다.**

</aside>

애플리케이션 실행 후 http://localhost:8080에 접속하면 Spring Security가 기본 로그인 페이지를 반환합니다.

 하지만 우리는 Spring Security의 기본 인증 기능을 사용하지 않고, 필요한 보안 기능을 직접 커스터마이징하여 구현할 예정입니다.

2장에서 만든 SecurityConfig 클래스에 필터 체인을 구현합니다.

**springv2 > core > config**

![**15.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%2014.png)

**15.png**

다음과 같이 SecurityConfig에 filterChain 메서드를 작성합니다. 현재는 보안 설정이 되어있지 않아 스프링 시큘티의 기본 보안이 그대로 동작하며, 필요에 따라 필터를 구현해야 합니다.

```java
import java.util.List;

@RequiredArgsConstructor
@Configuration
public class SecurityConfig {

    private final JwtProvider jwtProvider;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
       // ... 생략 
       return http.build();
    }
}
```

이제 시큐리티 **filterChain 메서드**를 커스터마이징하겠습니다. 

## 5.4.1 폼 로그인 비활성

먼저 스프링 시큐리티의 기본 폼 로그인 기능은 사용하지 않으므로 비활성화합니다. 대신 인증은 JWT 방식을 통해 처리합니다.

**core/config/SecurityConfig.java**

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.formLogin(form -> form.disable()); // 폼 로그인 비활성화
    http.httpBasic(basic -> basic.disable()); // HTTP Basic 인증 비활성  
    // ... 생략
    return http.build();
}
```

## 5.4.2 JWT 설정

JWT 인증은 JwtAuthorizationFilter를 활용합니다. 이 필터는 UsernamePasswordAuthenticationFilter보다 앞에 배치되어, 폼 로그인 처리 전에 JWT 인증을 먼저 수행하도록 합니다.

**core/config/SecurityConfig.java**

```java
http.addFilterBefore(new JwtAuthorizationFilter(jwtProvider, UsernamePasswordAuthenticationFilter.class);
```

우리는 JWT 기반 인증을 사용하므로, 서버를 **Stateless** 모드로 적용합니다.

**core/config/SecurityConfig.java**

```java
http.sessionManagement(session 
									-> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
```

## 5.4.3 예외 발생 처리

스프링 시큐리티에서 인증 또는 권한 처리 중 예외가 발생하면, 상태 코드와 에러 메시지를 클라이언트에 반환합니다.

**core/config/SecurityConfig.java**

```java
http.exceptionHandling(ex -> ex
         .authenticationEntryPoint((request, response, authException) 
										         -> RespFilter.fail(response, 401, "로그인 후 이용해주세요"))
         .accessDeniedHandler((request, response, accessDeniedException) 
										         -> RespFilter.fail(response, 403, "권한이 없습니다"))
 );
```

## 5.4.4 권한 설정

사용자의 역할(Role)에 따라 접근 권한을 검증합니다. 

**/api/admin/**** 요청은 ADMIN 권한을 가진 사용자만 접근할 수 있습니다. 

**/api/users/, /api/boards/, /api/replies/**** 요청은 USER 또는 ADMIN 권한을 가진 사용자, 즉 인증된 사용자만 접근할 수 있습니다. 

그 외의 경로는 인증되지 않은 사용자도 자유롭게 이용할 수 있습니다.

**core/config/SecurityConfig.java**

```java
http.authorizeHttpRequests(
      authorize -> authorize
              .requestMatchers("/api/admin/**").hasRole("ADMIN")
              .requestMatchers("/api/users/**", "/api/boards/**", "/api/replies/**").hasAnyRole("USER", "ADMIN")
              .anyRequest().permitAll()
);
```

**core/config/SecurityConfig.java**

```java
http.headers(headers -> headers
      .frameOptions(frameOptions -> frameOptions.sameOrigin()));
```

## 5.5.2 **CSRF 정책 설정**

스프링 시큐리티의 **CSRF 정책**을 비활성화 합니다.

> **CSRF(Cross-Site Request Forgery, 사이트 간 요청 위조)는 브라우저가 세션 쿠키를 자동으로 첨부하는 특성을 악용한 공격입니다. 사용자가 이미 인증된 상태에서 공격자가 만든 악성 페이지에 접근하면, 브라우저는 사용자의 세션 쿠키를 그대로 포함해 서버로 요청을 보내게 되고, 서버는 이를 정상적인 요청으로 착각해 원치 않는 동작을 수행하게 됩니다.**
> 

JWT를 사용하는 경우, 프론트엔드 애플리케이션이 요청 시 직접 JWT를 헤더에 포함해 전송합니다. 브라우저가 자동으로 세션 쿠키를 첨부하는 방식이 아니므로, 공격자는 토큰 값을 알 수 없고 임의로 헤더를 조작할 수도 없습니다. 따라서 CSRF 공격으로부터 상대적으로 안전합니다.

**core/config/SecurityConfig.java**

```java
http.csrf(configure -> configure.disable());
```

## 5.5.3 **CORS 정책 설정**

다음으로 **CORS 정책**을 설정합니다.

> **CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)는 다른 출처(도메인, 프로토콜, 포트 등)에서 서버의 자원에 접근할 수 있도록 허용하는 보안 정책입니다.**
> 

application.properties에 설정한 CORS 환경 변수를 allowedOrigins에 주입하고, corsConfigurationSource 메서드에서 이 값을 활용해 허용할 출처(origin)를 지정합니다. 이후 이 CORS 정책을 필터 체인에 등록해, 서버가 허용된 출처에서 오는 요청만 정상적으로 처리할 수 있도록 합니다.

**core/config/SecurityConfig.java**

```java
package com.metacoding.springv2.core.config;

// 중략
import org.springframework.web.cors.*;

@RequiredArgsConstructor
@Configuration
public class SecurityConfig {

    private final JwtProvider jwtProvider;

		//application.properties의 설정 값 변수로 설정
    @Value("${app.cors.allowed-origins}")
    private String allowedOrigins;

		// 요청 헤더, HTTP 메서드, 요청 출처 허용 설정
    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.addAllowedHeader("*"); // 모든 요청 헤더 허용
        config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS")); // HTTP 메서드 허용
        config.setAllowedOriginPatterns(List.of(allowedOrigins.split(","))); // 허용할 출처 지정
        // 이 설정이 없으면, CORS 요청 시 브라우저는 쿠키, HTTP 인증 헤더(Authorization 등)를 함께 보내지 않음
        config.setAllowCredentials(true);
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/api/**", config); // 모든 /api/** 경로에 CORS 설정 적용
        return source;
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {

				// 중략
				// 필터 체인에 설정 적용	
        http.cors(cors -> cors.configurationSource(corsConfigurationSource()));
        
        return http.build();
    }
}
```

## 5.5.4 비밀번호 암호화

보안을 위해 평문인 비밀번호를 BCrypt 함수를 통해 암호화합니다.

> **BCrypt 해시 알고리즘은 내부적으로  임의의 랜덤 난수를 비밀번호에 포함해 암호화합니다. 
덕분에 같은 비밀번호라도 해시 결과가 매번 달라지므로 비밀번호 추적이 더욱 어려워집니다.
이때 사용되는 랜덤 난수를 Salt라고 부릅니다.**
> 

**core/config/SecurityConfig.java**

```java
package com.metacoding.springv2.core.config;

// 중략

@RequiredArgsConstructor
@Configuration

		// 비밀번호 암호화
    @Bean
    public BCryptPasswordEncoder encodePwd() {
        return new BCryptPasswordEncoder();
    }
    
    // 중략 ...
```

# 5.6 Filter vs AOP 차이점

<aside>
💡

**Filter와 AOP는 비즈니스 핵심 로직과 직접적인 관련이 없는 공통 기능을 분리해 관리하며, 실행 흐름을 가로채 필요한 부가 로직을 적용한다는 공통점을 갖습니다. 다만 두 기술은 동작하는 위치에서 차이가 있습니다.**

</aside>

Filter는 스프링 애플리케이션 앞단, 즉 DispatcherServlet 이전에 위치하여 클라이언트의 요청과 응답을 가로챕니다. 이를 통해 JWT 검증, 로깅, 인코딩, 보안 정책 적용과 같은 공통 처리를 수행할 수 있습니다.

> **DispatcherServlet는 Front Controller 라고도 하며, HTTP 요청을 받아 적합한 컨트롤러로 전달하는 역할을 수행합니다.**
> 

![**16.png**](5%20%EC%8A%A4%ED%94%84%EB%A7%81%20%EC%8B%9C%ED%81%90%EB%A6%AC%ED%8B%B0(Spring%20Security)/image%2015.png)

**16.png**

반면 AOP는 스프링 애플리케이션 내부에서 동작합니다. 클라이언트 요청이 DispatcherServlet을 거쳐 적절한 컨트롤러가 호출되면, AOP는 @Controller, @Service 등 IoC 컨테이너에 등록된 빈의 메서드 실행 전후에 동작합니다.

 이를 통해 각 메서드 실행 시점에서 로깅, 트랜잭션, 유효성 검증과 같은 공통 기능을 세밀하게 적용할 수 있습니다.
