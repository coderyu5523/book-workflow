## 3.1.1 근본적인 불일치: 철학의 차이

소프트웨어를 개발할 때 우리는 서로 다른 철학을 가진 두 개의 세상을 동시에 마주합니다. 바로 데이터의 정합성을 중시하는 관계형 데이터베이스(RDB)와 현실 세계의 복잡성을 표현하는 객체지향 언어(Java)입니다.

### DB 세상 (관계형 모델): "값과 관계 중심"

데이터베이스는 데이터를 안전하게 보관하고 효율적으로 조회하는 것이 목표입니다.

- **구조**: 행(Row)과 열(Column)로 이루어진 평면적인 테이블 구조입니다.
- **연결**: 다른 테이블을 참조하려면 오직 **외래 키(Foreign Key)**라는 '값'을 공유해야 합니다.
- **한계**: 테이블 안에 또 다른 테이블이나 객체 구조를 통째로 담을 수 없습니다.

### 자바 세상 (객체 모델): "상태와 행위 중심"

자바는 현실 세계의 사물을 객체로 추상화하여 관리합니다.

- **구조**: 필드(상태)와 메서드(행위)를 가지며, 객체 간의 관계를 자유롭게 설계합니다.
- **연결**: 객체 안에 다른 객체를 필드로 가지는 **참조(Reference)** 방식을 사용합니다.
- **유연성**: 상속, 다형성, 추상화 등 데이터를 표현하는 방법이 매우 풍부합니다.

---

## 3.1.2 데이터의 평면 세계(DB) vs 입체 세계(Java)

우리가 개발을 할 때 마주하는 두 세계는 데이터를 다루는 방식이 근본적으로 다릅니다. 이 차이를 이해하는 것이 하이버네이트(Hibernate) 기술의 출발점입니다.

### 1. 구조의 차이: 테이블 vs 객체

- **DB(테이블의 세상)**: 데이터가 행과 열로 이루어진 평면적인 표에 저장됩니다. 모든 데이터는 규격화된 칸 안에 '값'으로만 존재합니다.
- **Java(객체의 세상)**: 데이터뿐만 아니라 그 데이터가 어떻게 행동하는지(상속, 메서드)를 포함하는 입체적인 객체 구조를 가집니다.

### 2. 상속과 타입의 불일치

- **상속(Inheritance)**: 자바에는 부모 객체의 특징을 물려받는 '상속' 개념이 명확하지만, DB 테이블에는 상속이라는 개념이 존재하지 않습니다.
- **자료형(Data Type)**: 숫자나 문자 같은 기본 자료형은 서로 비슷하지만, DB는 자바의 '객체 자체'나 '컬렉션(List, Map 등)'을 한 칸에 담을 수 있는 능력이 없습니다.

### 3. 햄버거 세트로 보는 '불일치'의 핵심

이 차이를 가장 잘 보여주는 것이 바로 **'햄버거 세트'** 예시입니다.

- **자바의 방식 (Composition)**: `햄버거 세트`라는 객체 하나가 `햄버거`, `콜라`, `감자튀김` 객체를 품고(has-a) 있습니다. 우리는 그저 세트 하나만 들고 다니면 그 안의 내용물에 바로 접근할 수 있습니다.
- **DB의 방식 (FK 참조)**: DB는 '세트'라는 큰 상자 안에 다른 음식을 집어넣는 것이 불가능합니다. 대신 햄버거, 콜라, 감자 테이블을 각각 따로 만들고, 서로 **외래 키(FK)**를 통해 "우리는 같은 세트예요"라고 연결만 해둘 뿐입니다.

![Screenshot_2.png](3%20%ED%95%98%EC%9D%B4%EB%B2%84%EB%84%A4%EC%9D%B4%ED%8A%B8%20%ED%85%8C%EC%8A%A4%ED%8A%B8/Screenshot_2.png)

### 4. 하이버네이트: 두 세계를 잇는 통역사

결국 **DB는 무결성(데이터의 정확성)**을 지키는 데 완벽한 세상을 꿈꾸고, **자바는 표현 방법(현실 세계의 복잡성)**이 풍부한 세상을 지향합니다.

하이버네이트는 이처럼 **서로 불일치한 세상의 데이터를 마치 같은 세상인 것처럼 일치시켜주는 역할**을 합니다. 개발자가 복잡한 DB의 연결 방식(FK, JOIN 등)을 일일이 신경 쓰지 않아도, 자바에서 객체를 다루듯 편하게 코딩할 수 있게 돕는 '마법의 도구'인 셈입니다.

---

## 3.1.3 지옥의 번역가 시대: SQL 중심 개발의 한계

ORM이 없던 시절, 개발자는 자바 개발자인 동시에 **'수동 번역가'**였습니다.

1. **반복되는 CRUD**: 테이블이 하나 늘어날 때마다 수십 줄의 유사한 SQL과 매핑 코드를 작성해야 했습니다.
2. **객체 지향 상실**: 비즈니스 로직을 짜는 시간보다 SQL 결과를 객체에 일일이 채워넣는(`rs.get...`) 시간이 더 길었습니다.
3. **강한 결합**: 테이블 컬럼 하나만 바뀌어도 관련된 모든 SQL 코드를 찾아 수정해야 하는 유지보수의 재앙이 뒤따랐습니다.

## 3.1.4 해결사 하이버네이트(Hibernate)의 등장

하이버네이트는 개발자는 객체에만 집중하고, DB 번역은 나에게 맡겨라"라고 말하며 등장했습니다.

![3.png](3%20%ED%95%98%EC%9D%B4%EB%B2%84%EB%84%A4%EC%9D%B4%ED%8A%B8%20%ED%85%8C%EC%8A%A4%ED%8A%B8/3.png)

하이버네이트를 통해 우리는 드디어 각자의 세상을 존중하며 개발할 수 있게 되었습니다.

- **객체는 객체답게**: 상속과 참조를 마음껏 활용하며 풍부한 도메인 모델을 설계합니다.
- **DB는 DB답게**: 정규화된 테이블 구조와 데이터 무결성을 유지합니다.
- **번역은 ORM이**: 하이버네이트가 중간에서 객체 그래프를 탐색하고, 필요할 때마다 SQL을 생성하여 두 세계를 연결합니다.

## 3.1.5 결론: 본질로의 회귀

> 관계형 데이터베이스와 객체지향 언어는 해결하려는 문제의 도구가 다를 뿐, 둘 다 소프트웨어의 핵심입니다. 하이버네이트의 진정한 가치는 단순히 SQL 작성을 대신해 주는 데 있지 않습니다. **개발자가 데이터 중심의 사고에서 벗어나, 객체지향의 풍부한 표현력을 회복하게 해준다는 점**에 있습니다. 이제 우리는 테이블의 구조에 얽매이지 않고, 비즈니스 로직의 본질에 더 집중할 수 있게 되었습니다.

> **`EntityManager`는 JPA에서 데이터베이스 작업을 총괄하는 핵심 객체로, 엔티티의 저장·조회·수정·삭제를 담당하며 영속성 컨텍스트(1차 캐시)를 관리합니다.**

# 3.3 **JPQL 문법 정리**

> **JPQL은 테이블이 아닌 엔티티와 필드명을 기준으로 작성하는 JPA의 SQL입니다. 실행 시 JPA가 SQL로 변환하여 DB에 전달되며, SELECT, UPDATE, DELETE 지원합니다. 
(INSERT는 지원하지 않고 em.persist() 를 사용합니다.)**
> 

JPQL의 기본 문법은 다음과 같습니다. 테이블대신 엔티티를 사용하며, 별칭을 사용해 조회합니다.

```java
SELECT b FROM Board b // 전체 조회
```

특정 컬럼만 조회가 필요하다면 다음과 같이  <별칭.컬럼명>으로 작성하면 됩니다.

```java
SELECT b.title, b.content FROM Board b
```

특정 조건으로 조회하려면 where 절에 <:컬럼명> 을 사용해 조회합니다.

```java
SELECT b FROM Board b WHERE b.id = :id
```

삭제와 수정도 다음과 같이 사용할 수 있습니다.

```java
UPDATE Board b SET b.title = '제목 수정' WHERE b.id = :id // 수정

DELETE FROM Board b WHERE b.id = :id // 삭제
```

작성한 JPQL은 em.createQuery() 사용해 실행할 수 있습니다.

```java
em.createQuery(
    "SELECT b FROM Board b WHERE b.title b.id = :id", Board.class
).getResultList();
```

# 3.4 **영속성 컨텍스트 개념잡기**

> **영속성 컨텍스트(Persistence Context)는 EntityManager가 관리하는 엔티티 객체들의 저장소로 em.persist() 나 em.find() 등을 통해 엔티티가 등록·조회되는 순간 영속 상태가 됩니다.**
> 

영속성 컨텍스트의 특징에 대해 알아보겠습니다.

## 3.4.1 캐싱(Caching)

**예시 1)**

```java
Board board1 = em.find(Board.class, 1); 
Board board2 = em.find(Board.class, 1); 
```

만약  예시 1) 와 같이 em.find() 를 실행한다면 어떻게 될까요?

영속성 컨텍스는 DB를 조회하는 것이 아니라 먼저 캐시에서 조회를 합니다. 만약 캐시에 결과가 없다면 DB에서 조회 후 영속화된 객체를 캐시에 저장합니다.

## 3.4.2 쓰기 지연(**write**-behind)

**예시 2)**


## 3.4.3 더티 체킹**(Dirty Checking)**

> **더티 체킹(Dirty Checking)은 영속성 컨텍스트가 엔티티의 변경 사항을 감지해 자동으로 UPDATE 쿼리를 생성하는 과정입니다.**
> 
> 1. **영속 상태 진입: em.find() 로 엔티티를 조회하면 최초 상태를 스냅샷에 저장합니다.**
> 2. **엔티티 수정: 필드 변경 시, 변경을 감지해 UPDATE 쿼리를 만들고 버퍼에 저장합니다.**
> 3. **flush 시점:  em.flush() 호출 시 버퍼에 저장된 UPDATE 쿼리를 DB에 반영합니다.** 
> 
> ```java
> Board board = em.find(Board.class, 1);
> board.setTitle("제목 수정 1");
> 
> em.flush(); // DB에 SQL 전송
> ```
> 

**예시 3)**

# 3.5 **단위 테스트와 통합 테스트 개념**

## 3.5.1 **단위 테스트와 통합 테스트**

> **단위 테스트(Unit Test)는 가장 작은 모듈(메서드 혹은 클래스)을 외부 의존성 없이 검증하는 테스트입니다. DB나 네트워크 같은 환경을 배제하고, 필요한 경우 가짜(Mock) 객체를 사용해 순수한 비즈니스 로직만 빠르게 정확하게 테스트할 수 있습니다. 이를 통해 실패 원인이 코드 내부에 한정되므로, 문제 파악과 수정이 용이합니다.**
> 
> 
> 
> **단위 테스트가 개별 모듈의 동작을 검증하는 데 초점을 둔다면, 통합 테스트는 단위 테스트가 끝난 모듈들을 결합해 시스템 전체의 흐름과 상호 작용을 검증하는 테스트입니다.**
>

## 3.5.2 given-when-then 패턴

> **Given–When–Then은 테스트를 사전 조건(Given) → 동작(When) → 결과 검증(Then)의 구조로 서술하는 행위 주도 개발(BDD) 기법입니다. 스토리처럼 사람이 쉽게 이해할 수 있는 테스트를 구현해 협업자 모두가 요구사항과 테스트 의도를 쉽게 파악할 수 있게 합니다.**
> 

각 항목은 다음의 역할을 합니다.

- **given: 테스트를 위해 필요한 환경과 데이터를 준비합니다.**
- **when: 검증 대상 기능을 실제로 호출해 실행합니다.**
- **then: 실행 결과가 기대와 일치하는지 검증합니다.**

<aside>
💡

**Then 단계는 실행 결과가 기대값과 일치하는지를 assert 메서드로 검증하는 단계입니다. 
다만 학습 초기 단계에서는  print 메서드를 사용해 결과를 직접 확인하는 Eye(시각적 검증) 단계로 대체할 수 있습니다. 우리는 Eye 단계를 사용해서 테스트를 하겠습니다.**

</aside>

## 3.6.4 게시글 수정하기

> **게시글 수정하기는 UPDATE 메서드를 만들지 않고 영속 상태 엔티티의 변경 감지(더티 체킹)을 사용합니다.**
> 

테스트에서는 변경 내용이 실제 DB에 반영되었는지 확인하기 위해 `EntityManager.flush()`를 호출합니다.`flush()`는 영속성 컨텍스트에 누적된 변경 사항을 기반으로 UPDATE 쿼리를 생성하여 DB에 반영합니다.

다만, 수정 후 같은 트랜잭션 안에서 다시 조회하면 1차 캐시(영속성 컨텍스트)에 남아있는 엔티티가 반환될 수 있습니다. 따라서 `EntityManager.clear()`를 호출해 영속성 컨텍스트를 비운 뒤 다시 조회하면, 캐시가 아닌 DB에서 값을 다시 읽어오므로 실제 반영 여부를 정확히 검증할 수 있습니다.

**BoardRepositoryTest.java**

```jsx
@Test
public void update_test(){
        //given
        int id = 2;        
        //when
        Board board = boardRepository.findById(id);
        board.setTitle("title-update");
        board.setContent("Update-test");
        em.flush(); // update 쿼리 전송  
        em.clear(); // 영속성 컨텍스트 초기화
        //eye
        Board result = boardRepository.findById(id);
        System.out.println("=======================");
        System.out.println("Board title : " + result.getTitle());
        System.out.println("Board content : " + result.getContent());
}   // 전체 게시글 조회, 게시글 조회, 게시글 저장하기 메서드 생략    
```
