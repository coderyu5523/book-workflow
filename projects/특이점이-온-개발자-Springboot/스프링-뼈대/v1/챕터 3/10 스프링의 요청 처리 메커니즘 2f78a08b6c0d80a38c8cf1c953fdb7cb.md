# 10. 스프링의 요청 처리 메커니즘

### **사용자의 요청이 DB까지 닿는 머나먼 여정**

웹 애플리케이션에 접속하는 순간부터 데이터가 저장되기까지, 우리의 코드는 보이지 않는 곳에서 거대한 체계를 통과합니다.

**① 톰캣(Tomcat)과 버퍼**
브라우저가 8080 포트로 요청을 보내면, 톰캣은 `Header`와 `Body` 정보를 담은 `req(Request)` 객체를 생성합니다. 이때 효율적인 처리를 위해 미리 만들어진 **Request Pooling(Thread Pool)**에서 일꾼을 꺼내 작업을 할당합니다.

**② 스프링 컨테이너의 핵심 계층**

- **DS(DispatcherServlet)**: 모든 요청의 진입점입니다. URL과 HTTP 메서드를 분석해 어떤 컨트롤러가 일을 처리할지 찾아줍니다.
- **C(Controller)**: 사용자의 요청을 직접 응답 처리하는 곳입니다.
- **S(Service)**: 비즈니스 로직이 수행되며, 가장 중요한 **트랜잭션 관리**가 일어납니다. `@Transactional` 어노테이션이 붙은 메서드가 종료되는 시점이 바로 트랜잭션의 끝입니다.
- **R(Repository)**: 실제 DB에 질의를 던지는 DML 수행 계층입니다.
- **PC(Persistence Context)**: 영속성 컨텍스트, 즉 '물감통'입니다. 객체와 DB 사이의 완충 지대 역할을 하며 데이터를 관리합니다.

**③ 자원 효율화: 풀링(Pooling)**
서버는 무한한 자원을 가지고 있지 않습니다. 그래서 **Request Pooling(예: 50개)**과 **DBCP(Database Connection Pool, 예: 20개)**를 미리 준비해둡니다. 요청이 올 때마다 새로 만드는 것이 아니라, 미리 만들어진 연결 통로를 '빌려 쓰고 반납하는' 방식을 통해 서버의 부하를 획기적으로 줄입니다.
