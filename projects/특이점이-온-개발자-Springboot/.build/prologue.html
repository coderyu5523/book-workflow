프롤로그

서버 뼈대에 막히다

오픈이는 이제 막 자바(Java)를 배우기 시작한 학생입니다. 이번 학기 과제인 게시판 웹 서버를 만들기 위해 호기롭게 키보드에 손을 올렸지만, 몇 줄 쓰지도 못하고 벽에 부딪혔습니다.

문제는 게시판 기능 그 이전 단계에 있었습니다. 웹 서버를 처음부터 직접 만들려다 보니 외부와 통신하는 작업부터, 들어온 요청의 주소를 해석해 알맞은 코드로 연결하는 과정까지 전부 스스로 구현해야 했습니다. 중요한 게시글 화면은 시작도 못했는데, 서버 뼈대를 만들기 위한 작업만 산더미같이 쌓여 있었습니다.

이거 뼈대만 만들다가 과제는 손도 못 대겠는데...

다음 날, 오픈이는 같은 수업을 듣는 선배에게 고민을 털어놓았습니다. 선배는 오픈이가 지금까지 쓴 코드를 훑어보더니 말했습니다.

선배: "이런 걸 처음부터 직접 다 만드는 사람은 없어요. 웹 서버에 공통으로 필요한 뼈대는 프레임워크에 이미 다 갖춰져 있거든요. 자바로 웹 서버를 만들면 보통 스프링(Spring) 을 써요. 스프링으로 시작해서 게시판 기능만 구현해 봐요."

선배의 말을 들은 오픈이는 스프링에 대해 알아보기로 했습니다. 스프링은 자바를 기반으로 복잡한 애플리케이션을 쉽게 만들 수 있도록 돕는 프레임워크로, 외부 요청을 처리하는 서버의 기본 뼈대를 이미 갖추고 있습니다. 따라서 개발자가 모든 흐름을 직접 통제할 필요가 없습니다. 클래스와 메서드에 약속된 표식만 붙여 두면, 요청이 들어왔을 때 스프링이 표식을 읽어 알맞은 코드를 찾아 실행합니다.

개발자가 메서드를 직접 호출하던 방식과 달리, 프레임워크가 개발자의 코드를 호출하도록 흐름이 뒤집힌 이 원리를 제어의 역전(IoC) 이라고 합니다. 서버 뼈대를 만드는 일을 스프링에 위임하고 나니, 오픈이는 핵심인 게시판 기능에만 온전히 집중할 수 있게 되었습니다.

게시판을 완성하다

다음 날 저녁, 오픈이는 노트북을 열고 스프링으로 새 프로젝트를 만들어 보기로 했습니다. 스프링이 표식을 읽어 알맞은 코드를 찾아 실행한다는 원리까지는 이해했습니다.

이제 남은 건 그 원리 위에서 직접 기능을 만드는 일이었습니다. 첫 번째 목표는 게시판이었습니다.

스프링으로 게시판의 기본 기능을 만들어 보자.

오픈이는 먼저 게시글을 데이터베이스에 저장하기 위해 테이블을 설계했습니다. 그런데 스프링은 데이터를 자바 객체로 다루고, 객체와 테이블은 구조가 다릅니다. 그래서 객체의 값을 테이블에 옮겨 담으려면 매핑 작업이 필요합니다. 이 과정을 쉽게 처리하기 위해 스프링에서는 JPA라는 기술을 사용합니다. JPA는 이 매핑 정보를 바탕으로 저장과 조회에 필요한 SQL을 생성합니다.

JPA는 영속성 컨텍스트라는 공간을 통해 객체를 관리합니다. 영속성 컨텍스트는 애플리케이션과 데이터베이스 사이에서 객체를 보관하고, 객체에 생긴 변경을 모아 데이터베이스에 반영합니다.

오픈이는 스프링과 JPA를 활용해 게시판의 기본 기능을 구현해 냈습니다. 학기 과제로 기획했던 게시판이 첫 동작을 시작한 순간이었습니다.

실패한 이유를 응답에 담다

뿌듯한 마음으로 선배에게 결과물을 보여주던 날이었습니다. 선배는 마우스를 몇 번 딸깍거리더니, 주소창의 게시글 번호를 '999'로 바꾼 뒤 엔터를 쳤습니다. 화면에는 여전히 '200 성공'이라는 코드가 떴지만, 정작 내용은 텅 비어 있었습니다.

어라? 게시글이 없는 번호인데 왜 성공했다고 나오지?

선배: "데이터를 못 찾았으면 빈 값을 던질 게 아니라 처리를 중단해야죠. 안 그러면 나중에 없는 글을 수정하거나 삭제하려다 서버에 큰 오류가 날 거예요. 문제가 생겼을 땐 어떤 사유로 실패했는지 클라이언트에게 명확히 알려주는 예외 처리가 필수예요."

조언을 들은 오픈이는 조회 결과가 없으면 즉시 처리를 멈추고 예외를 발생시키도록 코드를 고쳤습니다. 여기저기서 터지는 예외들을 한곳에 모아 명확한 사유와 상태 코드로 반환하게 만들자, 999번을 조회했을 때 '게시글을 찾을 수 없다'는 깔끔한 응답이 돌아왔습니다.

응답을 다시 보니 다른 문제도 있었습니다. 테이블 구조와 같은 객체를 그대로 응답하다 보니 화면에서 쓰지 않는 값까지 담겨 나갔고, 테이블 구조가 바뀌면 클라이언트가 받는 형식까지 함께 흔들렸습니다. 오픈이는 요청과 응답에 필요한 값만 담는 DTO를 따로 두었습니다.

요청한 사람을 식별하다

다음 순서는 회원을 추가해 '인증 게시판'을 만드는 것이었습니다. 회원가입과 로그인은 무사히 구현했지만, 진짜 문제는 로그인이 끝난 직후부터 시작되었습니다.

로그인까지는 좋은데, 방금 글을 쓴 이 사람이 아까 로그인한 그 사람인지 서버가 어떻게 알지?

선배: "서버는 기본적으로 기억력이 없어요. 그러니까 로그인에 성공한 순간, 사용자에게 위조할 수 없는 사원증을 쥐여줘야 해요. 사용자가 다음 요청 때마다 사원증을 보여주면, 서버는 그걸 보고 누군지 식별하는 거죠."

사원증의 정체는 바로 JWT 토큰이었습니다. 오픈이는 로그인 성공 시 토큰을 발급하고, 이후 요청이 들어올 때마다 서버가 토큰의 서명을 가장 먼저 검사하도록 만들었습니다. 이제 서버가 일일이 로그인 상태를 외우고 있지 않아도, 토큰만 확인하면 누구의 요청인지 단번에 알아차릴 수 있었습니다. 여기에 '작성자 본인만 글을 지울 수 있는' 인가 기능까지 덧붙이자 제법 그럴싸한 서비스의 형태를 갖추게 되었습니다.

게시글과 댓글을 연결하다

마지막 관문은 댓글 기능이었습니다. 게시글 상세 화면을 띄울 때 여러 개의 댓글과 각각의 작성자 정보까지 한 번에 엮어서 보여줘야 했습니다.

데이터들이 너무 얽혀있는데… 이걸 화면 하나에 띄우려면 쿼리를 대체 몇 번이나 날려야 하는 거야?

머리를 쥐어뜯는 오픈이에게 선배가 마지막 힌트를 던졌습니다.

선배: "자바 객체는 기본적으로 일방통행이지만, 양방향 매핑을 쓰면 반대쪽에서도 참조할 수 있게 길을 뚫을 수 있어요. 그러면 조인을 통해서 한 번에 필요한 데이터를 싹 쓸어올 수 있죠."

선배의 말대로 굳게 닫혀있던 참조의 길을 양쪽으로 열어주자, 복잡하게 얽혀 있던 데이터가 한 번의 요청으로 깔끔하게 묶여 나왔습니다.

학기 초, 주소를 어떻게 나눠야 할지 몰라 깜빡이는 커서만 보며 한숨짓던 과제가 어느새 인증과 댓글까지 오가는 번듯한 게시판으로 거듭나 있었습니다. 백엔드 세계에 첫발을 내디딘 오픈이의 서버 개발은 이제부터가 시작입니다.
