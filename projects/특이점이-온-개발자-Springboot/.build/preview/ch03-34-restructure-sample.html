3.4 재구성 시안

도입부 그림 셋은 역할 이름만 씁니다. 코드 이름이 든 흐름은 실습 6 뒤에 한 장으로 모읍니다. 회색 배경 안내문은 시안 설명이고 본문에 들어가지 않습니다.

3.4 예외 처리 추가

스프링에서 예외가 어떻게 처리되는지 흐름부터 알아보겠습니다.

없는 게시글을 조회하면 서비스의 조회 결과가 비어 있습니다. 내보낼 값이 없으므로 서비스는 값을 반환하는 대신 예외를 던지고, 그 아래 코드는 실행되지 않습니다.

그림 3-4. 예외 발생 지점

던져진 예외를 잡는 코드가 없으면 서비스는 그 자리에서 중단되고, 예외는 자신을 호출한 곳을 거쳐 디스패처 서블릿까지 전달됩니다.

그림 3-5. 예외 전파 경로

디스패처 서블릿은 예외를 직접 처리하지 않고, 그 예외를 맡은 메서드를 실행합니다. 특정 컨트롤러에 속하지 않고 모든 컨트롤러에서 발생한 예외를 받기 때문에 전역 예외 처리기라고 부릅니다. 그 메서드가 반환한 값이 응답이 되어 클라이언트에게 전달됩니다.

그림 3-6. 전역 예외 처리기의 응답

3.4.1 커스텀 예외 만들기

앞에서 본 흐름에서 서비스가 던지는 예외를 먼저 만듭니다. 게시글을 찾지 못한 상황을 나타내는 예외이고, 이름은 응답할 상태 코드를 따라 Exception404로 정합니다.

core/handler/ex/Exception404.java를 열어 아래와 같이 작성합니다.

public class Exception404 extends RuntimeException {
    public Exception404(String message) {
        super(message);
    }
}

상황에 맞게 직접 정의한 예외를 커스텀 예외라고 합니다. RuntimeException을 상속하면 이 예외를 사용하는 곳마다 try-catch를 적지 않아도 됩니다.

이어지는 나머지 예외 클래스 안내와 상태 코드 표는 지금 원고 그대로입니다.

3.4.2 전역 예외 처리

다음으로 예외가 발생했을 때 처리할 핸들러를 구현해 보겠습니다. @RestControllerAdvice 어노테이션이 지정된 클래스는 각 컨트롤러에서 요청을 처리하는 도중 발생하는 예외를 전역적(Global)으로 가로채어 한 곳에서 일괄 처리하는 역할을 합니다. 앞에서 흐름으로 본 전역 예외 처리기가 이 클래스입니다.

core/handler/GlobalExceptionHandler.java를 열어 아래와 같이 작성합니다.

@RestControllerAdvice
public class GlobalExceptionHandler {

    // 1. 커스텀 예외는 저마다의 상태 코드로 바꾼다
    @ExceptionHandler(Exception404.class)
    public ResponseEntity<?> exApi404(Exception404 e) {
        return Resp.fail(HttpStatus.NOT_FOUND, e.getMessage());
    }

    // ... 400, 401, 403, 500 생략

    // 2. 나머지 모든 예외는 500으로 처리한다
    @ExceptionHandler(Exception.class)
    public ResponseEntity<?> exUnKnown(Exception e) {
        return Resp.fail(HttpStatus.INTERNAL_SERVER_ERROR, "서버 오류가 발생했습니다");
    }
}

@ExceptionHandler는 메서드마다 어떤 예외를 맡을지 지정합니다. 커스텀 예외 넷은 저마다 400·401·403·404 응답이 되고, 그 밖의 예외는 모두 500 응답이 됩니다.
