제안 (4단계 흐름)

제안 2 (전역 · 일괄이 보이는 그림)

여러 곳에서 나온 서로 다른 예외가 한 곳으로 모이고, 거기서 상태 코드별로 갈라져 나갑니다. "전역적으로 가로채어 한 곳에서 일괄 처리한다"는 문장이 그림으로 보입니다.

제안 3 (스프링이 예외를 처리하는 흐름)

커스텀 예외 이름과 JSON 응답 형태를 뺐습니다. 남긴 것은 예외가 발생한 뒤 스프링 안에서 무슨 일이 일어나는가입니다. 화살표 옆 문구가 각 단계의 동작입니다.

제안 4 (블로그식 전체 흐름)

요청 경로와 예외 경로를 한 장에 놓고, 디스패처 서블릿이 예외를 처리할 곳을 순서대로 찾아 내려가는 과정을 그렸습니다. 이번 챕터에서 만드는 부분만 색을 넣고 나머지는 흐리게 두었습니다.

그림 3-4. 스프링의 예외 처리 흐름

제안 5 (단계별로 쪼갠 흐름)

한 장에 몰아넣지 않고 세 단계로 나눴습니다. 각 그림은 한 가지 사실만 말하고, 그림 아래 문장이 그 단계를 설명합니다. 리졸버 클래스 이름은 넣지 않았습니다.

1단계. 예외가 발생하지만 아무도 잡지 않습니다

그림 3-4. 예외가 발생한 지점

서비스가 게시글을 찾지 못하면 예외를 발생시킵니다. 컨트롤러는 이 예외를 잡는 코드를 갖고 있지 않으므로, 예외는 컨트롤러를 그대로 지나갑니다.

2단계. 스프링이 예외를 넘겨받습니다

그림 3-5. 예외를 넘겨받는 지점

요청을 가장 먼저 받은 디스패처 서블릿까지 예외가 올라옵니다. 디스패처 서블릿은 이 예외를 맡은 곳이 있는지 찾습니다.

3단계. 전역 예외 처리기가 응답으로 바꿉니다

그림 3-6. 예외가 응답이 되는 지점

디스패처 서블릿이 찾은 곳이 전역 예외 처리기입니다. 여기서 이 예외를 맡은 메서드가 실행되고, 그 메서드가 반환한 값이 응답이 되어 클라이언트에게 전달됩니다.

제안 6 (조사한 내용을 세 단계로)

3-1에 없는 두 가지, 트랜잭션 되돌림과 반환값이 응답으로 바뀌는 과정을 넣었습니다.

1단계. 예외가 서비스를 벗어나면 트랜잭션이 되돌아갑니다

그림 3-4. 예외가 트랜잭션을 벗어나는 지점

커스텀 예외는 RuntimeException을 상속합니다. 이런 예외가 @Transactional 메서드 밖으로 나가면 스프링이 트랜잭션을 되돌립니다. 게시글 수정이나 삭제 도중에 예외가 나도 그때까지의 변경이 데이터베이스에 반영되지 않습니다.

2단계. 디스패처 서블릿이 맡은 메서드를 찾아 실행합니다

그림 3-5. 예외를 맡는 지점

디스패처 서블릿은 이 예외를 맡은 메서드가 있는지 찾습니다. @RestControllerAdvice가 붙은 클래스에서 해당 예외를 맡은 메서드를 찾아 실행하고, 그 메서드는 ResponseEntity를 반환합니다.

3단계. 반환값이 상태 코드와 응답 바디로 나뉩니다

그림 3-6. 응답이 만들어지는 지점

스프링은 반환된 ResponseEntity를 둘로 나눠 씁니다. status에 담긴 값은 HTTP 응답의 상태 코드가 되고, 바디에 든 Resp 객체는 메시지 컨버터가 JSON 문자열로 바꿔 응답 바디에 담습니다. 컨트롤러가 정상 응답을 만들 때 거치는 경로와 같습니다.

제안 7 (경로가 아니라 데이터가 바뀌는 모습)

박스와 화살표로 지나가는 길을 그리는 대신, 각 지점에서 실제 값이 어떻게 되는지를 보여 줍니다.

예외가 나면 쌓아 둔 SQL이 버려집니다

그림 3-4. 예외가 났을 때의 데이터베이스

커스텀 예외는 RuntimeException을 상속합니다. 이런 예외가 @Transactional 메서드 밖으로 나가면 스프링이 트랜잭션을 되돌립니다. 챕터 2에서 버퍼에 쌓였다가 트랜잭션이 성공할 때 나간다고 한 SQL이, 여기서는 나가지 않고 버려집니다.

반환한 값이 HTTP 응답으로 바뀝니다

그림 3-5. 반환값과 실제 응답

status에 담긴 404는 응답의 상태 코드가 되고, 바디에 든 Resp 객체는 메시지 컨버터가 JSON 문자열로 바꿉니다. 컨트롤러가 정상 응답을 만들 때 거치는 경로와 같습니다.
