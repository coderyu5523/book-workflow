1.4 Spring MVC

객체를 만드는 일을 스프링 컨테이너가 맡는다면, 요청 주소에 맞는 메서드를 찾아 호출하는 일은 스프링의 웹 모듈인 Spring MVC가 맡습니다.

1.4.1 MVC 패턴

Spring MVC라는 이름은 MVC 패턴에서 왔습니다. MVC 패턴은 웹 애플리케이션의 코드를 데이터를 담는 모델(Model), 화면을 만드는 뷰(View), 요청을 받아 처리하는 컨트롤러(Controller) 로 나누는 설계 방식입니다.

요청 처리, 데이터, 화면 코드가 한곳에 섞여 있으면 화면 하나를 바꿀 때도 요청을 처리하는 코드까지 함께 고쳐야 합니다. 역할을 나누면 화면은 뷰에서, 요청 처리는 컨트롤러에서 따로 고칠 수 있고, 같은 모델의 데이터를 여러 화면에서 함께 쓸 수도 있습니다.

Spring MVC는 이 패턴에 따라 역할별로 나뉜 코드를 연결해 요청을 처리합니다. 앞에서 만든 BoardController는 이 중 컨트롤러에 해당합니다.

1.4.2 디스패처 서블릿

Spring MVC에서는 디스패처 서블릿(DispatcherServlet) 이 이 연결을 맡습니다. 모든 요청은 디스패처 서블릿에 먼저 도착하고, 디스패처 서블릿이 요청 주소에 맞는 컨트롤러의 메서드를 찾아 호출합니다. 컨트롤러가 모델을 반환하면 디스패처 서블릿은 이를 뷰에 전달해 응답을 만듭니다. 이처럼 모든 요청이 한곳을 거치므로, 처리 중 발생한 예외를 오류 응답으로 바꾸는 일처럼 요청마다 공통으로 필요한 처리도 디스패처 서블릿이 맡습니다.

1.4.3 톰캣과 필터

디스패처 서블릿은 이름처럼 서블릿(Servlet) 입니다. 서블릿은 톰캣(Tomcat) 같은 웹 애플리케이션 서버(WAS) 가 받은 요청을 넘겨받아 처리하는 자바 클래스입니다.

톰캣은 자바 코드를 실행해 동적인 결과를 만들어 내는 서버로, 클라이언트가 보낸 요청을 스프링이 이해할 수 있는 객체로 변환해 디스패처 서블릿에 전달하고 스프링이 만든 결과를 다시 클라이언트에 응답합니다. 요청은 디스패처 서블릿에 도착하기 전에 먼저 필터(Filter) 를 거치는데, 필터에서는 인증이나 인코딩처럼 애플리케이션 전반에 공통으로 필요한 작업을 처리합니다.
