1.4 스프링의 요청 흐름과 Spring MVC

앞에서 만든 프로그램은 객체를 만드는 일과 주소에 맞는 메서드를 찾아 호출하는 일을 대신 처리했습니다. 스프링에서는 객체를 만드는 일을 스프링 컨테이너가, 메서드를 찾아 호출하는 일을 Spring MVC가 맡습니다. 스프링은 이처럼 하는 일에 따라 여러 모듈로 나뉘어 있고, Spring MVC는 그중 웹 요청을 처리하는 모듈입니다.

다만 직접 만든 main 메서드에는 요청 주소를 문자열로 적어 넣었습니다. 실제 웹 애플리케이션에서는 이 주소가 클라이언트가 네트워크로 보낸 요청 안에 들어 있습니다.

1.4.1 톰캣과 필터

클라이언트가 보낸 요청을 가장 먼저 받는 것은 스프링이 아니라 톰캣(Tomcat) 입니다. 톰캣은 자바 코드를 실행해 동적인 결과를 만들어 내는 웹 애플리케이션 서버(WAS) 로, 네트워크로 들어온 요청을 먼저 자바 객체로 바꿉니다.

그다음 톰캣은 요청 주소를 보고, 그 주소를 담당하는 자바 클래스에 요청 객체를 넘겨 실행합니다. 이 클래스는 톰캣이 호출할 수 있도록 정해진 규격에 맞춰 작성하며, 이렇게 작성한 클래스를 서블릿(Servlet) 이라고 합니다.

톰캣은 요청을 서블릿에 넘기기 전에 필터(Filter) 를 먼저 실행합니다. 필터는 인증이나 인코딩처럼 모든 요청에 공통으로 필요한 작업을 한곳에서 처리하고, 조건에 맞지 않는 요청은 서블릿에 넘기지 않고 걸러 낼 수도 있습니다.

그림 1-17. 톰캣과 필터

1.4.2 디스패처 서블릿

Spring MVC는 디스패처 서블릿(DispatcherServlet) 이라는 서블릿 하나를 톰캣에 등록해, 필터를 통과한 요청을 모두 이 서블릿으로 받습니다. 주소마다 서블릿을 따로 두지 않는 대신, 디스패처 서블릿이 앞에서 만든 findUri()처럼 어노테이션을 읽어 요청 주소를 담당하는 컨트롤러 메서드를 찾고, 그 메서드를 리플렉션으로 호출합니다.

1.4.3 MVC 패턴

디스패처 서블릿이 호출하는 컨트롤러는 MVC 패턴의 한 역할입니다. MVC 패턴은 요청을 받아 응답하기까지의 코드를 다음 세 역할로 나누는 설계 방식이며, Spring MVC라는 이름도 이 패턴에서 왔습니다.

  • 컨트롤러(Controller): 요청을 받아 처리합니다.
  • 모델(Model): 컨트롤러가 처리한 결과 데이터입니다.
  • 뷰(View): 모델의 데이터로 응답 화면(HTML)을 만듭니다.

역할을 이렇게 나누면 컨트롤러에는 화면을 만드는 코드가, 뷰에는 데이터를 처리하는 코드가 들어가지 않습니다. 그래서 화면을 바꿀 때는 뷰만, 요청 처리 방식을 바꿀 때는 컨트롤러만 고치면 됩니다.

이렇게 나뉜 컨트롤러와 뷰는 디스패처 서블릿이 연결합니다. 디스패처 서블릿이 컨트롤러를 호출하면 컨트롤러는 처리 결과를 모델로 반환하고, 디스패처 서블릿은 이 모델을 뷰에 전달한 뒤 뷰가 만든 화면을 클라이언트에 응답으로 전달합니다.

그림 1-19. 디스패처 서블릿과 MVC 패턴

외부와 통신하며 요청을 자바 객체로 바꾸는 일은 톰캣이, 모든 요청에 공통인 작업은 필터가, 주소에 맞는 메서드를 찾아 호출하고 응답을 만드는 일은 Spring MVC가 맡습니다. 그래서 개발자는 통신이나 라우팅을 직접 구현하지 않고, 어떤 주소에 어떤 코드를 실행할지만 컨트롤러에 작성하면 됩니다.
