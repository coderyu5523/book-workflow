1.4 Spring MVC

Spring MVC는 스프링에서 웹 요청을 처리하는 모듈입니다. 앞에서 main 메서드가 직접 하던 일, 즉 요청 주소에 맞는 메서드를 찾아 호출하는 일을 Spring MVC가 대신하고, 메서드가 반환한 결과로 응답까지 만듭니다. 그래서 개발자는 요청을 받아 메서드를 찾는 코드를 직접 만들지 않고, 요청마다 실행할 코드를 컨트롤러에 작성하면 됩니다.

그림 1-17. Spring MVC가 맡는 일

1.4.1 톰캣과 디스패처 서블릿

Spring MVC에 요청이 도착하기 전에, 네트워크를 통해 들어온 요청을 먼저 받는 것은 톰캣(Tomcat) 입니다. 톰캣은 자바 코드를 실행해 동적인 결과를 만들어 내는 웹 애플리케이션 서버(WAS) 로, 받은 요청을 자바 객체로 바꿔 전달합니다.

그림 1-18. 요청을 받는 톰캣

요청 객체는 스프링에 전달되기 전에 필터(Filter) 를 거칩니다. 필터는 인증이나 인코딩처럼 모든 요청에 공통으로 필요한 작업을 먼저 처리합니다.

그림 1-19. 필터를 거치는 요청

필터를 통과한 요청은 서블릿(Servlet) 이 처리합니다. 서블릿은 톰캣이 요청 처리를 맡기는 자바 객체이고, Spring MVC는 디스패처 서블릿(DispatcherServlet) 이라는 서블릿 하나를 톰캣에 등록해 모든 요청을 이곳에서 받습니다.

그림 1-20. 모든 요청을 받는 디스패처 서블릿

1.4.2 MVC 패턴

디스패처 서블릿이 받은 요청은 MVC 패턴에 따라 처리됩니다. MVC 패턴은 요청을 처리하는 컨트롤러(Controller), 데이터를 담는 모델(Model), 화면을 만드는 뷰(View) 로 역할을 나누는 방식이며, Spring MVC라는 이름도 여기서 왔습니다.

디스패처 서블릿은 먼저 요청 주소와 일치하는 @RequestMapping이 붙은 컨트롤러 메서드를 찾아 리플렉션으로 호출합니다.

그림 1-21. 요청 주소에 맞는 메서드 호출

컨트롤러는 처리 결과를 모델에 담아 반환하고, 디스패처 서블릿은 이 모델을 뷰에 넘깁니다. 뷰는 모델의 데이터로 화면(HTML)을 만들어 응답합니다.

그림 1-22. 모델과 뷰를 거친 응답

역할을 나눠 두었기 때문에 화면을 바꿀 때는 뷰만 고치면 되고, 컨트롤러 코드는 그대로 둘 수 있습니다.
