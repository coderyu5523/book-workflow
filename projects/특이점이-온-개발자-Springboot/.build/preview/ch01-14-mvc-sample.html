1.4 스프링의 요청 흐름

요청이 서버에 도착해 컨트롤러에서 처리되고 응답으로 돌아가기까지 어떤 단계를 거치는지 따라가 보겠습니다.

원본: 요청이 서버에 도착해서 컨트롤러에 전달되기까지 어떤 단계를 거치는지 따라가 보겠습니다.

그림 1-17. 요청 처리 흐름

외부 요청이 컨트롤러로 전달되는 흐름에서 각 단계가 맡는 역할은 다음과 같습니다.

  1. 톰캣과 필터. 톰캣(Tomcat)은 자바 코드를 실행해 동적인 결과를 만들어 내는 웹 애플리케이션 서버(WAS) 입니다. 클라이언트가 보낸 통신 요청을 스프링이 이해할 수 있는 객체로 변환해 전달하고, 스프링이 만든 최종 결과를 다시 응답하는 출입문 역할을 합니다. 요청은 스프링으로 넘어가기 전에 먼저 필터(Filter)를 거치는데, 필터에서는 인증이나 인코딩처럼 애플리케이션 전반에 공통으로 필요한 작업을 미리 걸러내어 처리합니다.
  2. 디스패처 서블릿. 필터를 무사히 통과한 요청은 디스패처 서블릿(DispatcherServlet) 으로 들어옵니다. 디스패처 서블릿은 스프링으로 들어오는 모든 요청을 맨 앞에서 가로챈 뒤, 요청 주소(URL)를 분석하여 이를 담당할 가장 적절한 컨트롤러를 찾아 길을 안내해 줍니다.
  3. 컨트롤러 호출. 디스패처 서블릿은 찾아낸 컨트롤러의 메서드를 리플렉션으로 호출합니다. 컨트롤러가 반환한 결과는 요청이 지나온 경로를 거꾸로 거쳐 클라이언트에 전달됩니다.
새로 추가

디스패처 서블릿이 요청을 받아 컨트롤러를 호출하고 그 결과를 응답하는 이 구조는 스프링에 포함된 웹 프레임워크인 Spring MVC가 제공합니다. Spring MVC에서는 앞에서 직접 만든 어노테이션과 이름이 같은 @Controller와 @RequestMapping으로 개발자가 컨트롤러와 담당 주소를 지정합니다.

Spring MVC라는 이름은 MVC 패턴에서 왔습니다. MVC 패턴은 데이터를 담는 모델(Model), 화면을 만드는 뷰(View), 요청을 받는 컨트롤러(Controller)로 역할을 나누는 설계 방식입니다. 화면을 만들어 응답하는 서버에서는 컨트롤러가 처리 결과를 모델에 담아 반환합니다. 그러면 디스패처 서블릿이 모델을 뷰에 전달하고, 뷰는 모델의 데이터를 채워 HTML을 생성합니다.

반면 다음 챕터부터 만들 게시판 서버는 화면 없이 데이터만 응답합니다. 그래서 디스패처 서블릿은 컨트롤러가 반환한 데이터를 뷰에 전달하지 않고 응답에 담습니다. 이렇게 데이터를 응답하는 컨트롤러에는 @Controller 대신 @RestController를 붙입니다.
