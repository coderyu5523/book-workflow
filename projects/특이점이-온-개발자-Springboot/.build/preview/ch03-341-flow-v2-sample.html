3.4.1 예외 처리 흐름 — 시안 v2

외부 자료는 이렇게 그립니다

스프링 예외 처리를 다루는 글들(김영한 스프링 MVC 2편 정리 글 다수, 전역 예외 처리기 동작 원리 글)은 공통으로 요청이 지나간 계층을 한 줄로 세우고, 예외가 그 줄을 거꾸로 되돌아가는 모습으로 그립니다. 전역 예외 처리기가 없을 때는 예외가 WAS(톰캣)까지 간 뒤 WAS가 /error로 요청을 다시 보내는 두 번째 흐름을 따로 그리고, 있을 때는 디스패처 서블릿에서 예외가 멈추고 정상 응답으로 바뀌는 흐름으로 그립니다.

처리기 없음
  요청:   WAS → 필터 → 서블릿 → 인터셉터 → 컨트롤러(예외 발생)
  전달:   WAS ← 필터 ← 서블릿 ← 인터셉터 ← 컨트롤러
  재요청: WAS /error 다시 요청 → 필터 → 서블릿 → BasicErrorController → 응답

처리기 있음
  예외 발생 → 디스패처 서블릿 → ExceptionResolver → @ExceptionHandler 실행
  → 정상 응답으로 반환 (예외는 WAS까지 가지 않음)

이 책은 인터셉터를 다루지 않으므로 뺐고, 예외는 서비스에서 발생하므로 서비스까지 그렸습니다. 앞 시안에서 "톰캣 → 기본 오류 응답"을 상자 하나로 줄였던 부분을, 외부 자료처럼 /error 재요청으로 바로잡았습니다.

두 그림의 차이

- 그림 A: 예외가 디스패처 서블릿을 지나 톰캣까지 갑니다. 톰캣이 /error로 요청을 다시 보내고, 스프링 부트의 기본 오류 컨트롤러가 500 응답을 만듭니다. 실패 사유는 담기지 않습니다.
- 그림 B: 예외가 디스패처 서블릿에서 멈춥니다. 전역 예외 처리기가 만든 응답이 일반 응답처럼 필터와 톰캣을 거쳐 클라이언트에게 갑니다.
- 필터에서 난 예외는 디스패처 서블릿을 거치지 않으므로, 전역 예외 처리기가 있어도 그림 A처럼 톰캣 → /error 흐름으로 처리됩니다.
- 그림 A의 500 응답 JSON은 스프링 부트 기본 동작 기준입니다. 반영 전에 처리기를 뺀 상태에서 999번 조회로 실제 응답을 확인해야 합니다.
