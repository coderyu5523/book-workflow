3.4.1 예외 처리 흐름 — 구조 시안

지금 3.4.1은 전역 예외 처리기가 있는 흐름만 보여 줍니다. 처리기가 없으면 예외가 어디까지 가서 어떤 응답이 되는지를 먼저 보여 주고, 처리기가 그 흐름의 어디서 예외를 받는지를 이어서 보여 주는 구조입니다. 두 그림은 같은 틀(클라이언트 → 톰캣 → 필터 → 디스패처 서블릿 → 컨트롤러 → 서비스)을 씁니다.

그림 A — 전역 예외 처리기가 없을 때

그림 A. 전역 예외 처리기가 없을 때의 예외 흐름

서비스에서 던진 예외는 호출된 순서를 거꾸로 거쳐 디스패처 서블릿까지 옵니다. 디스패처 서블릿에는 이 예외를 처리할 곳이 없어 그대로 필터와 톰캣까지 넘어가고, 톰캣은 처리되지 않은 예외를 스프링 부트의 기본 오류 응답으로 넘깁니다. 클라이언트는 실패 사유 없이 500만 받습니다. 필터에서 예외가 나도 마지막은 똑같이 톰캣 → 기본 오류 응답입니다.

그림 B — 전역 예외 처리기가 있을 때

그림 B. 전역 예외 처리기가 있을 때의 예외 흐름

디스패처 서블릿까지 온 예외를 전역 예외 처리기가 받아 상태 코드와 실패 사유를 담은 응답으로 바꿉니다. 예외가 필터와 톰캣까지 넘어가지 않으므로 기본 오류 응답(500)이 나가지 않습니다. 반대로 필터에서 난 예외는 디스패처 서블릿을 거치지 않아 여전히 그림 A처럼 처리됩니다.

근거와 확인 필요한 점

단계근거
2~3. 서비스 → 컨트롤러 → 디스패처BoardService의 orElseThrow(() -> new Exception404(...)), BoardController에 try-catch 없음
A-3. 디스패처가 그대로 넘김@ExceptionHandler가 없으면 디스패처 서블릿의 예외 처리기 목록 중 Exception404를 처리하는 곳이 없어 예외를 다시 던짐 (스프링 MVC 기본 동작)
A-4·5. 톰캣 → 기본 오류 응답 500스프링 부트가 등록한 오류 경로(/error)가 timestamp·status·error·path를 담은 JSON을 만듦. server.error.include-message 설정이 없어 메시지는 빠짐 (application.properties 확인)
B-4·5. 전역 예외 처리기GlobalExceptionHandler.exApi404 → Resp.fail(NOT_FOUND, e.getMessage()), 그림 3-7 실제 응답과 같은 JSON

그림 A의 500 응답 JSON은 스프링 부트 기본 동작 기준입니다. 처리기를 뺀 코드를 실제로 실행해 확인하려던 명령은 이번 세션에서 권한이 거절돼 실행하지 못했습니다. 반영 전에 999번 조회로 실제 응답을 캡처해 두는 것을 권합니다.
