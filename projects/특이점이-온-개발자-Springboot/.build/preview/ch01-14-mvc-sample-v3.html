1.4 스프링의 요청 흐름

스프링 컨테이너에 등록된 컨트롤러 빈을 웹 요청에 맞춰 호출하고 그 결과로 응답을 만드는 일은 Spring MVC라는 웹 모듈이 담당합니다. 이 모듈은 스프링 프로젝트에 라이브러리로 추가해야 사용할 수 있으며, 다음 챕터에서 프로젝트를 만들 때 추가하는 Spring Web에 들어 있습니다. 요청이 서버에 도착해 응답으로 돌아가기까지의 흐름을 따라가며 Spring MVC가 맡는 부분을 살펴보겠습니다.

1.4.1 요청 전달

요청은 클라이언트에서 출발해 톰캣과 필터, 디스패처 서블릿을 차례로 거쳐 컨트롤러에 도착합니다.

원본: 요청이 서버에 도착해서 컨트롤러에 전달되기까지 어떤 단계를 거치는지 따라가 보겠습니다. (같은 말을 1.4 도입에서 하므로 바꿈)

그림 1-17. 요청 처리 흐름

외부 요청이 컨트롤러로 전달되는 흐름에서 각 단계가 맡는 역할은 다음과 같습니다.

  1. 톰캣과 필터. 톰캣(Tomcat)은 자바 코드를 실행해 동적인 결과를 만들어 내는 웹 애플리케이션 서버(WAS) 입니다. 클라이언트가 보낸 통신 요청을 스프링이 이해할 수 있는 객체로 변환해 전달하고, 스프링이 만든 최종 결과를 다시 응답하는 출입문 역할을 합니다. 요청은 스프링으로 넘어가기 전에 먼저 필터(Filter)를 거치는데, 필터에서는 인증이나 인코딩처럼 애플리케이션 전반에 공통으로 필요한 작업을 미리 걸러내어 처리합니다.
  2. 디스패처 서블릿. 필터를 무사히 통과한 요청은 디스패처 서블릿(DispatcherServlet) 으로 들어옵니다. 디스패처 서블릿은 스프링으로 들어오는 모든 요청을 맨 앞에서 가로챈 뒤, 요청 주소(URL)를 분석하여 이를 담당할 가장 적절한 컨트롤러를 찾아 길을 안내해 줍니다.
  3. 컨트롤러 호출. 디스패처 서블릿은 찾아낸 컨트롤러의 메서드를 리플렉션으로 호출합니다. 컨트롤러가 반환한 결과는 요청이 지나온 경로를 거꾸로 거쳐 클라이언트에 전달됩니다.

이 흐름에서 톰캣과 필터를 지나 디스패처 서블릿에 들어온 뒤부터가 Spring MVC가 맡는 부분입니다. 디스패처 서블릿은 앞에서 직접 만든 것과 이름이 같은 @Controller와 @RequestMapping 어노테이션을 기준으로, 요청 주소에 맞는 컨트롤러의 메서드를 찾아 호출합니다.

1.4.2 화면 응답

이렇게 호출된 컨트롤러가 결과를 반환하면, Spring MVC는 이 결과로 응답을 만듭니다. 그 방식은 서버가 화면을 응답하는지, 데이터만 응답하는지에 따라 나뉩니다. 먼저 화면을 응답하는 서버는 MVC 패턴을 사용합니다.

MVC 패턴은 웹 요청을 처리하는 코드를 모델(Model), 뷰(View), 컨트롤러(Controller) 세 가지 역할로 나눕니다. Spring MVC라는 이름도 이 패턴에서 왔습니다.

역할하는 일
모델화면에 보여 줄 데이터를 담습니다
뷰모델의 데이터로 화면(HTML)을 생성합니다
컨트롤러요청을 받아 처리하고, 결과를 모델에 담아 반환합니다

화면을 응답할 때는 세 역할이 차례로 동작합니다. 디스패처 서블릿이 @Controller가 붙은 컨트롤러를 호출하면, 컨트롤러는 처리 결과를 모델에 담아 반환합니다. 디스패처 서블릿은 이 모델을 뷰에 전달하고, 뷰는 모델의 데이터를 채워 HTML을 생성합니다. 이렇게 생성된 HTML이 클라이언트에 응답으로 전달됩니다.

그림 1-18. 뷰를 거치는 화면 응답

1.4.3 데이터 응답

반면 다음 챕터부터 만들 게시판 서버는 화면 없이 데이터만 응답합니다. 화면을 만들지 않으므로 뷰도 필요 없습니다. 그래서 디스패처 서블릿은 컨트롤러가 반환한 데이터를 뷰에 전달하지 않고 응답에 담습니다. 이렇게 데이터를 응답하는 컨트롤러에는 @Controller 대신 @RestController를 붙입니다.
