1.4 Spring MVC

객체를 만드는 일을 스프링 컨테이너가 맡는다면, 요청 주소에 맞는 메서드를 찾아 호출하는 일은 스프링의 웹 모듈인 Spring MVC가 맡습니다.

1.4.1 MVC 패턴

Spring MVC라는 이름은 MVC 패턴에서 왔습니다. MVC 패턴은 웹 애플리케이션의 코드를 데이터를 담는 모델(Model), 화면을 만드는 뷰(View), 요청을 받아 처리하는 컨트롤러(Controller) 로 나누는 설계 방식입니다. 요청 주소마다 처리할 메서드를 모아 둔 BoardController가 이 중 컨트롤러에 해당합니다.

1.4.2 디스패처 서블릿

직접 만든 프로그램에서는 findUri()가 @RequestMapping에 적힌 주소를 요청 주소와 비교해 BoardController의 메서드를 찾고, 리플렉션으로 호출했습니다. Spring MVC에서는 모든 요청이 디스패처 서블릿(DispatcherServlet) 을 거치고, 디스패처 서블릿이 이 일을 맡습니다.

1.4.3 요청 처리 흐름

직접 만든 프로그램은 요청 주소를 문자열로 넣었지만, 실제 요청은 네트워크를 통해 들어와 디스패처 서블릿에 도착하기 전에 몇 단계를 더 거칩니다.

그림 1-19. 요청 처리 흐름

외부 요청이 컨트롤러로 전달되는 흐름에서 각 단계가 맡는 역할은 다음과 같습니다.

  1. 톰캣과 필터. 톰캣(Tomcat)은 자바 코드를 실행해 동적인 결과를 만들어 내는 웹 애플리케이션 서버(WAS) 입니다. 클라이언트가 보낸 통신 요청을 스프링이 이해할 수 있는 객체로 변환해 전달하고, 스프링이 만든 최종 결과를 다시 응답하는 출입문 역할을 합니다. 요청은 스프링으로 넘어가기 전에 먼저 필터(Filter)를 거치는데, 필터에서는 인증이나 인코딩처럼 애플리케이션 전반에 공통으로 필요한 작업을 미리 걸러내어 처리합니다.
  2. 디스패처 서블릿과 컨트롤러. 필터를 통과한 요청은 디스패처 서블릿을 거쳐 컨트롤러의 메서드에 도착합니다. 컨트롤러가 반환한 결과는 요청이 지나온 경로를 거꾸로 거쳐 클라이언트에 전달됩니다.
