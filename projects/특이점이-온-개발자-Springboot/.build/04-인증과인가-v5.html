챕터 4. 인증과 인가

게시판의 기본 기능이 완성되었습니다. 없는 게시글은 예외로 처리했고, 응답에 담을 데이터도 고를 수 있게 되었습니다. 그런데 오픈이는 API를 테스트하다가 새로운 문제를 발견했습니다.

아무런 정보 없이 1번 게시글에 수정 요청을 보냈는데, 응답 창에 200이 돌아오며 제목과 내용이 그대로 변경되었습니다. 삭제 요청도 마찬가지였습니다.

누구든 글 번호만 알면 내용을 다 바꾸고 지울 수 있네. 요청을 보낸 사람이 누구인지 묻는 절차가 전혀 없구나.

오픈이는 선배를 찾아가 화면을 보여줬습니다.

오픈이: "선배님, 아무런 정보 없이 1번 게시글에 수정과 삭제 요청을 보냈는데 막히는 것 없이 200 성공이 뜹니다."
선배: "서버에 요청자를 알아볼 근거가 하나도 없어요. 아무 표식 없이 온 요청도 그대로 통과합니다. 요청에 신원을 실어 보내게 하고, 서버는 그 신원으로 두 번 걸러야 해요. 본인이 맞는지, 그리고 이 글의 주인이 맞는지."

이번 챕터에서는 회원 테이블을 추가합니다. 요청이 컨트롤러로 넘어가기 전에 사용자가 누구인지 확인하고(인증), 해당 작업을 수행할 자격이 있는지(인가) 검증하는 과정을 구현해 보겠습니다.

그림 4-1. 로그인하면 JWT가 발급되고, 이후 요청은 필터에서 신원이 담긴 뒤 서비스에서 자격이 가려집니다

이번 챕터가 끝나면

  • 인증과 인가가 어떻게 다른지 설명할 수 있습니다
  • 로그인하면 JWT를 발급하고, 필터로 토큰을 확인해 신원을 담고, 서비스에서 쓰기 요청을 막습니다
  • 게시글 상세 응답에 작성자와 본인 여부를 함께 담습니다
  • 로그인한 본인만 자기 게시글을 수정하고 삭제하게 만듭니다

4.1 게시판의 문제

4.1.1 인증이 없는 게시판

인증 절차가 없는 상태에서 1번 게시글에 게시글 수정 API를 호출합니다.

Hoppscotch 1번 게시글 수정 요청
PUT http://localhost:8080/api/boards/1 { "title": "수정한 제목", "content": "수정한 내용" }

응답은 200, 성공입니다.

그림 4-2. 수정 요청이 아무 확인 없이 처리되어 게시글이 그대로 바뀝니다

이 요청이 그대로 처리된 이유는 서버에 인증 절차가 없기 때문입니다. 지금 서버는 요청을 이렇게 처리합니다.

그림 4-3. 인증 절차가 없어 요청이 컨트롤러까지 그대로 도달합니다

방금 보낸 수정 요청도 이 흐름을 그대로 지났습니다.

4.1.2 인증과 인가

막는 자리를 넣기 전에 무엇을 확인할지부터 갈라야 합니다. 회사 건물에는 확인하는 자리가 두 군데 있습니다.

로비의 경비는 사원증을 보고 누구인지 확인합니다. 사원증이 없으면 여기서 돌아가야 합니다. 사원증을 보이고 들어갔다고 모든 문이 열리지도 않습니다. 각 부서 문은 사원증에 적힌 부서와 맞을 때만 열립니다.

서버도 이렇게 나눕니다. 요청을 보낸 사람이 누구인지 밝히는 일을 인증(Authentication) 이라고 합니다. 밝혀진 사람이 그 동작을 할 자격이 있는지 따지는 일을 인가(Authorization) 라고 합니다. 인증은 "누구인가"에 답하고, 인가는 "그 일을 할 권한이 있는가"에 답합니다.

그림 4-4. 인증은 사원증으로 누구인지를 확인하고, 인가는 사원증에 적힌 부서의 문만 열립니다

이번 챕터에서 두 확인은 서로 다른 자리가 맡습니다. 신원을 밝히는 인증은 요청을 받는 자리에서 토큰을 확인하는 필터가 담당하고, 자격을 따지는 인가는 요청을 처리하는 서비스가 담당합니다. 컨트롤러는 담긴 신원을 꺼내 서비스로 넘길 뿐입니다. 먼저 신원을 무엇으로 밝힐지부터 정해야 합니다.

4.2 JWT

4.2.1 무상태와 JWT

HTTP는 모든 요청을 독립적으로 처리하는 무상태(Stateless) 프로토콜입니다. 서버는 클라이언트의 로그인 상태를 저장하지 않으므로, 사용자는 새로운 요청을 보낼 때마다 자신이 누구인지 다시 증명해야 합니다.

이때 요청에 사용하는 인증 수단이 JWT(JSON Web Token) 입니다. JWT는 사용자 식별 정보를 JSON 데이터로 담고 위조 방지를 위한 디지털 서명을 더한 토큰입니다. 서버는 접속 상태를 따로 기록할 필요 없이, 전달받은 토큰의 서명만 검증하여 사용자를 확인합니다.

4.2.2 토큰의 세 조각

JWT는 점(.)으로 구분된 헤더, 페이로드, 서명 세 부분으로 이루어집니다.

그림 4-5. JWT는 헤더, 페이로드, 서명 세 부분으로 이루어지며 점으로 이어져 한 줄이 됩니다
조각 담기는 값
헤더 typ은 이 문자열이 JWT라는 표시, alg는 서명에 쓴 알고리즘(HS512)
페이로드 sub은 토큰의 주인인 유저네임, id는 회원의 기본 키, exp는 만료 시각
서명 헤더와 페이로드를 SECRET과 함께 계산한 값

페이로드는 Base64로 바꾼 값이라 누구든 되돌려 읽을 수 있습니다. 그래서 비밀번호처럼 감춰야 할 값은 넣지 않습니다. 몰래 고치면 서명 계산 결과가 달라져 토큰에 붙어 있는 서명과 맞지 않게 됩니다.

서버가 기억하는 방식도 있습니다

반대쪽 선택은 서버가 로그인한 사람을 기억해 두는 것입니다. 서버가 로그인 정보를 보관하고 로그인한 사람에게 식별 번호를 발급하면, 브라우저는 번호를 쿠키(Cookie)에 저장해 두었다가 요청마다 자동으로 함께 보냅니다. 서버는 번호로 보관해 둔 정보를 찾아 누구인지 확인합니다. 이렇게 서버가 상태를 기억하는 방식을 상태 유지(Stateful)라고 하고, 사람마다 보관하는 단위를 세션(Session)이라고 합니다. 접속자가 늘면 서버가 기억할 것도 함께 늘어납니다.

4.3 테이블 관계

인증 기능을 구현하려면 회원 테이블이 필요합니다. 테이블을 만들기 전에 기존 데이터와 어떤 관계를 맺을지부터 정합니다.

관계형 데이터베이스(RDBMS)는 데이터를 행(Row)과 열(Column)로 구성된 테이블에 저장하며, 이러한 테이블들을 서로 연결하는 '관계'를 통해 전체 데이터를 관리합니다. 테이블이 맺을 수 있는 대표적인 관계로는 1:1, 1:N, N:M(다대다) 세 가지가 있습니다.

4.3.1 1:N 관계

먼저 1:N은 한쪽의 데이터 하나가 다른 쪽의 데이터 여러 개와 연결되는 구조입니다. 재고가 단 하나뿐인 제품을 판매한다고 가정해 보겠습니다. 고객 한 명은 여러 제품을 살 수 있지만, 특정 제품은 오직 한 명의 고객에게만 판매됩니다.

그림 4-6. 고객 한 명이 제품 여러 개를 사므로 고객이 1, 제품이 N입니다

전체 구조로 보면 고객이 1, 제품이 N인 1:N 관계가 성립합니다. 두 테이블을 연결하려면 한쪽에 상대를 가리키는 값을 넣어 두어야 합니다. 이렇게 다른 테이블의 기본 키를 담는 컬럼을 외래 키(Foreign Key) 라고 하며, 'N(다수)' 쪽인 제품 테이블에 둡니다.

한 칸에는 값 하나만 들어가야 합니다

만약 테이블을 나누지 않고 고객 테이블 하나에 모든 정보를 담는다면 어떻게 될까요? 아래 그림처럼 고객 한 명의 제품 칸에 여러 개의 데이터가 들어가게 됩니다. 이는 '하나의 칸에는 하나의 값만 있어야 한다'는 데이터베이스의 원자성(Atomicity) 원칙을 어기는 잘못된 설계입니다.

그림 4-7. 테이블을 나누지 않으면 한 칸에 값 세 개가 함께 들어갑니다

4.3.2 N:M 관계

이번에는 일반적인 상황처럼 제품 테이블에 넉넉한 재고 수량이 있는 경우입니다. 고객 한 명이 여러 제품을 사는 것은 이전과 같습니다.

그림 4-8. 제품에 수량이 있어도 고객 한 명은 제품 여러 개를 삽니다

하지만 이제는 특정 제품 역시 재고가 있는 만큼 여러 고객에게 팔릴 수 있습니다.

그림 4-9. 반대로 제품 하나도 여러 고객에게 팔립니다

이처럼 양쪽 모두가 여럿과 연결되는 구조를 N:M 관계라고 합니다. 관계형 데이터베이스에서는 N:M 관계를 직접 연결할 수 없으므로, 사이에 '중간 테이블'을 만들어 두 개의 1:N 관계로 쪼개야 합니다. '구매'라는 중간 테이블을 두면, '고객 한 명이 여러 번 구매하는 구조(1:N)'와 '제품 하나가 여러 고객에게 구매되는 구조(1:N)'로 나누어 데이터를 올바르게 담을 수 있습니다.

그림 4-10. 구매 테이블을 사이에 두면 N:M 관계가 1:N 관계 둘로 나뉩니다

우리가 추가하려는 게시판의 회원과 게시글 역시 대표적인 1:N 관계입니다. 회원 한 명이 게시글을 여러 개 작성할 수 있고, 하나의 게시글은 한 명의 회원에게만 속하기 때문입니다. 따라서 외래 키는 'N'에 해당하는 게시글 테이블에 둡니다.

4.4 테이블 만들기

4.4.1 회원 엔티티

회원 테이블을 만들기 위해 엔티티를 추가합니다. user/User.java를 열고 아래 코드를 작성합니다.

실습 1 user/User.java. 회원 엔티티
@NoArgsConstructor @Data @Entity @Table(name = "user_tb") public class User { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Integer id; @Column(unique = true) private String username; private String password; private String email; @CreationTimestamp private Timestamp createdAt; @Builder public User(Integer id, String username, String password, String email, Timestamp createdAt) { this.id = id; this.username = username; this.password = password; this.email = email; this.createdAt = createdAt; } }

username에 붙은 @Column(unique = true)는 같은 유저네임이 두 번 저장되지 못하도록 데이터베이스 차원에서 막습니다.

4.4.2 게시글에 작성자 연결

board/Board.java에 작성자 회원 정보를 담을 필드를 추가합니다.

실습 2 board/Board.java. 작성자 연관관계 추가
@ManyToOne(fetch = FetchType.EAGER) @JoinColumn(name = "user_id") private User user; @Builder public Board(Integer id, String title, String content, Timestamp createdAt, User user) { this.id = id; this.title = title; this.content = content; this.createdAt = createdAt; this.user = user; }

외래 키는 다수 쪽인 게시글에 속하므로 Board에 @ManyToOne을 붙입니다. @JoinColumn(name = "user_id")은 board_tb에 작성자의 기본 키를 담을 user_id 컬럼을 만듭니다.

4.4.3 더미 데이터

회원 테이블이 새로 생겼으니 시작할 때 넣어 둘 데이터도 바뀝니다. resources/db/data.sql을 열고 아래 코드를 작성합니다.

실습 3 resources/db/data.sql. 회원과 게시글 더미 데이터
insert into user_tb (username, password, email, created_at) values ('ssar', '1234', 'ssar@metacoding.com', now()); insert into user_tb (username, password, email, created_at) values ('cos', '1234', 'cos@metacoding.com', now()); insert into board_tb (title, content, created_at, user_id) values ('title1', 'content1', now(), 1); insert into board_tb (title, content, created_at, user_id) values ('title2', 'content2', now(), 1);

회원 두 명을 먼저 넣고, 게시글 두 건을 넣습니다. 게시글의 user_id는 @JoinColumn으로 만든 외래 키 컬럼이고, 값이 둘 다 1이므로 1번 회원 ssar이 게시글 두 개를 쓴 상태가 됩니다.

로그인한 사람을 알아보려면 토큰을 만들고, 요청에 실려 온 토큰을 확인하는 코드가 필요합니다. core 폴더에 인증과 관련된 클래스는 다음과 같습니다.

파일 역할

4.5.1 JwtUtil

core/util/JwtUtil.java를 열고 아래 코드를 작성합니다.

실습 4 core/util/JwtUtil.java. JWT 발급과 검증
public class JwtUtil { public static final String HEADER = "Authorization"; public static final String TOKEN_PREFIX = "Bearer "; // 실제 서비스에서는 외부 설정으로 분리한다 public static final String SECRET = "메타코딩시크릿키"; public static final Long EXPIRATION_TIME = 1000L * 60 * 60 * 24 * 7; // 7일 // 1. 유저 정보를 담아 토큰을 만든다 public static String create(User user) { String jwt = JWT.create() .withSubject(user.getUsername()) .withExpiresAt(new Date(System.currentTimeMillis() + EXPIRATION_TIME)) .withClaim("id", user.getId()) .sign(Algorithm.HMAC512(SECRET)); return TOKEN_PREFIX + jwt; } // 2. 서명을 확인하고 담긴 정보로 User를 복원한다 public static User verify(String jwt) { DecodedJWT decodedJWT = JWT.require(Algorithm.HMAC512(SECRET)) .build().verify(jwt); Integer userId = decodedJWT.getClaim("id").asInt(); String username = decodedJWT.getSubject(); return User.builder().id(userId).username(username).build(); } }

create()는 유저 정보를 페이로드에 담고 SECRET으로 서명해 토큰 한 줄을 만듭니다. verify()는 그 반대로, 서명이 맞는지 확인한 뒤 페이로드에서 회원 정보를 꺼냅니다. 서명이 어긋나면 예외가 납니다.

4.5.2 JwtProvider

JwtProvider는 요청 헤더에서 토큰을 꺼낸 뒤, JwtUtil을 사용해 회원 정보를 얻습니다. core/util/JwtProvider.java를 열고 아래 코드를 작성합니다.

실습 5 core/util/JwtProvider.java. 토큰 추출과 유저 복원
@Component public class JwtProvider { // 1. 헤더에서 "Bearer " 접두어를 떼고 토큰만 꺼낸다 public String resolveToken(HttpServletRequest request) { String bearerToken = request.getHeader(JwtUtil.HEADER); if (bearerToken != null && bearerToken.startsWith(JwtUtil.TOKEN_PREFIX)) { return bearerToken.replace(JwtUtil.TOKEN_PREFIX, ""); } return null; } // 2. 토큰이 유효하면 User, 아니면 null public User getUser(String token) { try { return JwtUtil.verify(token); } catch (Exception e) { return null; } } }

토큰이 없거나 서명이 어긋나면 null을 돌려줍니다. 다음에 만들 필터는 이 결과만 보고 신원을 판단합니다.

4.5.3 인증 필터

필터(Filter) 는 요청이 컨트롤러에 도달하기 전에 먼저 거쳐 가는 지점입니다. 스프링에서는 OncePerRequestFilter를 상속해, 요청 한 건마다 한 번씩 실행되는 필터를 만듭니다.

JwtAuthenticationFilter는 이 자리에서 요청을 가로채, JwtProvider로 토큰에서 회원 정보를 얻어 요청에 담아 둡니다. core/filter/JwtAuthenticationFilter.java를 열고 아래 코드를 작성합니다.

실습 6 core/filter/JwtAuthenticationFilter.java. 인증 필터
@RequiredArgsConstructor @Component public class JwtAuthenticationFilter extends OncePerRequestFilter { private final JwtProvider jwtProvider; @Override protected void doFilterInternal( HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) throws ServletException, IOException { // 1. 헤더에서 토큰을 꺼낸다 String token = jwtProvider.resolveToken(request); // 2. 유효하면 신원을 요청에 담아 둔다 (막지는 않는다) if (token != null) { User loginUser = jwtProvider.getUser(token); if (loginUser != null) { request.setAttribute("loginUser", loginUser); } } filterChain.doFilter(request, response); } }

회원 정보는 loginUser라는 이름으로 요청에 담깁니다. 컨트롤러는 이 이름으로 꺼냅니다. 토큰이 없거나 서명이 어긋나면 담지 않고 통과시킵니다.

4.8 게시글 상세

게시글 상세에서는 게시글 정보와 작성자가 함께 응답되어야 합니다. 그러려면 데이터베이스에서 게시글 엔티티와 회원 엔티티를 한 번에 가져와야 합니다.

4.8.1 JPQL 조인문

이때 쓰는 문법이 JOIN입니다. 조인은 두 테이블의 행을 옆으로 이어 붙여 한 번의 조회로 가져오고, 어떤 행끼리 붙일지는 조건으로 정합니다. SQL은 그 조건을 on 절에 적지만, JPQL은 연관관계 필드 이름만 적습니다.

select b from Board b join b.user u

Board에 @ManyToOne으로 user 필드를 추가해 두었기 때문에, JPQL에서 b.user처럼 필드 이름만으로 회원 엔티티를 조인할 수 있습니다.

조인은 조건이 일치하는 데이터만 가져올 것인지, 아니면 한쪽 테이블을 기준으로 조건이 일치하지 않는 데이터까지 포함할 것인지에 따라 종류가 나뉩니다.

조인 종류 기준 테이블 동작 방식 및 조회 결과
(INNER) JOIN 없음 양쪽 테이블 모두에 조건이 일치하는 행만 조회합니다. (조건이 일치하지 않으면 조회 대상에서 제외됩니다.)
LEFT JOIN FROM 뒤 테이블 FROM 쪽 테이블의 모든 행을 조회합니다. 상대 테이블에 조건이 일치하는 데이터가 없으면 해당 컬럼은 null로 채웁니다.
RIGHT JOIN JOIN 뒤 테이블 JOIN 쪽 테이블의 모든 행을 조회합니다. 상대 테이블에 조건이 일치하는 데이터가 없으면 해당 컬럼은 null로 채웁니다.
FULL JOIN 양쪽 모두 두 테이블의 모든 행을 조회합니다. 서로 조건이 일치하지 않는 데이터는 각각 null로 채웁니다.

작성자 정보가 없는 게시글까지 조회하려면 left join을 씁니다.

select b from Board b left join b.user u

일반 SQL과 달리 JPQL의 기본 조인은 조인한 회원을 결과로 돌려주지 않고 기준 엔티티인 게시글만 반환합니다. 하지만 FETCH 키워드를 붙이면 연관된 데이터까지 한 번에 조회하여, 기준 엔티티 안의 연관 필드를 실제 데이터로 채워서 돌려줍니다.

select b from Board b join fetch b.user u

꺼낸 유저가 null이어도 그대로 넘깁니다. 막을지 말지는 서비스가 정합니다.

4.10 게시글 수정

수정은 로그인 확인과 소유자 검증을 모두 거칩니다.

4.10.1 서비스

쓰기와 마찬가지로 로그인부터 확인합니다. 이어서 작성자를 대조하는데, 어느 게시글의 작성자인지는 게시글을 조회해 봐야 알 수 있으므로 이 대조도 서비스에서 합니다. 작성자가 아니면 Exception403을 발생시킵니다. board/BoardService.java의 수정 메서드를 아래처럼 고칩니다.

실습 22 board/BoardService.java. 로그인 확인과 소유자 검증
@Transactional public BoardResponse.DTO 게시글수정( Integer boardId, BoardRequest.UpdateDTO requestDTO, User loginUser) { // 1. 넘어온 유저가 없으면 로그인하지 않은 요청이다 if (loginUser == null) { throw new Exception401("로그인이 필요합니다"); } Board board = boardRepository.findByIdJoinUser(boardId) .orElseThrow(() -> new Exception404("게시글을 찾을 수 없습니다")); // 2. 작성자 본인이 아니면 막는다 if (!board.getUser().getId().equals(loginUser.getId())) { throw new Exception403("게시글을 수정할 권한이 없습니다"); } board.setTitle(requestDTO.title()); board.setContent(requestDTO.content()); return new BoardResponse.DTO(board); }

두 검사를 모두 통과했을 때만 제목과 내용을 바꿉니다. 저장 코드는 없지만 더티체킹이 변경을 반영합니다.

4.10.2 컨트롤러

컨트롤러는 쓰기와 같은 모양으로, 꺼낸 유저를 그대로 서비스에 넘깁니다.

실습 23 board/BoardController.java. 수정 요청에서 로그인 유저 꺼내기
@PutMapping("/{boardId}") public ResponseEntity<?> update(HttpServletRequest request, @PathVariable("boardId") Integer boardId, @RequestBody BoardRequest.UpdateDTO requestDTO) { User loginUser = (User) request.getAttribute("loginUser"); BoardResponse.DTO respDTO = boardService.게시글수정(boardId, requestDTO, loginUser); return Resp.ok(respDTO); }

4.11 게시글 삭제

삭제도 같은 순서입니다.

4.11.1 서비스

board/BoardService.java의 삭제 메서드를 아래처럼 고칩니다.

실습 24 board/BoardService.java. 삭제의 로그인 확인과 소유자 검증
@Transactional public void 게시글삭제(Integer boardId, User loginUser) { // 1. 넘어온 유저가 없으면 로그인하지 않은 요청이다 if (loginUser == null) { throw new Exception401("로그인이 필요합니다"); } Board board = boardRepository.findByIdJoinUser(boardId) .orElseThrow(() -> new Exception404("게시글을 찾을 수 없습니다")); // 2. 작성자 본인이 아니면 막는다 if (!board.getUser().getId().equals(loginUser.getId())) { throw new Exception403("게시글을 삭제할 권한이 없습니다"); } boardRepository.delete(board); }

삭제 메서드가 로그인한 사람 loginUser를 하나 더 받습니다. 로그인을 확인한 뒤 findByIdJoinUser()로 게시글을 작성자와 함께 조회해, 게시글의 작성자와 요청자의 아이디가 다르면 작성자가 아니므로 Exception403을 발생시킵니다.

4.11.2 컨트롤러

컨트롤러도 꺼낸 유저를 그대로 넘깁니다.

실습 25 board/BoardController.java. 삭제 요청에서 로그인 유저 꺼내기
@DeleteMapping("/{boardId}") public ResponseEntity<?> deleteById(HttpServletRequest request, @PathVariable("boardId") Integer boardId) { User loginUser = (User) request.getAttribute("loginUser"); boardService.게시글삭제(boardId, loginUser); return Resp.ok(null); }

세 메서드가 모두 필터가 담아 둔 유저를 꺼내 서비스로 넘기는 같은 모양이 되었습니다. 컨트롤러는 요청에서 값을 꺼내 넘기고 응답을 돌려줄 뿐, 막는 일은 서비스가 맡습니다.

이제 처음 문제로 돌아가 확인합니다. 로그인하면 Bearer로 시작하는 토큰을 받습니다. 이 토큰을 Authorization 헤더에 담아서 다른 사람이 쓴 게시글에 게시글 수정 API를 호출하면, 앞서 그냥 통과하던 요청이 이번에는 403으로 막힙니다.

그림 4-12. 로그인하면 토큰이 발급되고, 다른 사람이 쓴 게시글을 수정하려 하면 403으로 막힙니다

오픈이는 자기 계정으로 로그인한 뒤, 다른 사람이 쓴 게시글에 게시글 수정 API를 다시 호출했습니다.

이번엔 막히겠지.

응답 창에 403이 돌아왔습니다. 게시글을 수정할 권한이 없다는 메시지도 함께였습니다. 로그인하지 않은 쓰기는 401로, 작성자가 아닌 수정은 403으로 갈려 멈췄습니다. 오픈이는 선배를 찾아가 응답 창을 다시 보여줬습니다.

오픈이: "이제 로그인하지 않으면 게시글이 안 써지고, 로그인해도 다른 사람이 쓴 게시글은 못 고칩니다."
선배: "아무 정보 없이 통과하던 요청이 이제 401과 403으로 갈려서 막히네요."

확인하는 자리가 비어 있던 컨트롤러 앞에는 이제 신원을 밝히는 필터가 놓였고, 서비스는 담긴 신원으로 자격을 따집니다.

그런데 이 게시판에는 아직 게시글만 있고 댓글이 없습니다. 다음 챕터에서는 게시글에 댓글을 달고, 댓글이 게시글에 딸리는 연관관계를 만들다 조회 성능 문제와 마주칩니다.

이것만은 기억하자

  • 인증은 "너 누구야"를 밝히고, 인가는 "그걸 할 권한이 있어"를 따집니다. 이번 챕터에서 인증은 토큰을 확인해 신원을 담는 필터가, 인가는 로그인 여부와 작성자를 확인하는 서비스가 맡습니다. 컨트롤러는 담긴 신원을 꺼내 서비스로 넘깁니다.
  • 로그인에 성공하면 JWT를 발급하고, 클라이언트는 토큰을 요청마다 지니고 옵니다. 서버는 토큰의 서명만 검증하면 되므로 로그인 상태를 따로 기억하지 않습니다. 다른 사람이 쓴 게시글에 보낸 수정·삭제 요청은 서비스의 소유자 검증에서 403으로 막힙니다.
  • 상세 응답의 isOwner는 화면이 수정·삭제 버튼을 감추는 데 씁니다. 버튼을 감춰도 요청은 보낼 수 있으므로, 실제로 막는 일은 서비스의 401과 403이 맡습니다.
