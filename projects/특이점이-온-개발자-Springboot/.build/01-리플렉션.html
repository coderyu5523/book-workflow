챕터 1. 리플렉션 - 스프링은 어떻게 내 코드를 실행하는가

오픈이는 개발을 공부하는 학생입니다. 이번 학기 과제는 웹 서버를 하나 만들어 제출하는 것입니다.

배운 것이 자바뿐이라 자바로 서버를 짜기 시작했지만, 몇 줄 쓰기도 전에 막히고 말았습니다. 브라우저의 요청을 받으려면 통신 연결부터 열어야 했고, 요청에서 주소를 꺼내려면 문자열을 한 글자씩 잘라 읽어야 했습니다.

주소를 겨우 꺼내도 끝이 아니었습니다. 주소마다 어떤 처리를 할지 일일이 연결하고, 응답 규격까지 직접 맞춰야 했습니다.

과제는 게시판인데, 서버 뼈대만 만들다 학기가 끝나겠네.

다음 날, 같은 수업을 듣는 선배에게 사정을 털어놓았습니다.

선배: "그런 기본 뼈대를 직접 만드는 사람은 없어요. 스프링을 쓰면 다 갖춰져 있거든요."

선배의 말에 스프링을 찾아보니, 소개 첫 줄에 "자바 웹 프레임워크"라고 적혀 있었습니다. 라이브러리는 수업에서 여러 번 써봤지만 프레임워크는 처음입니다. 둘은 무엇이 다를까요?

오픈이가 이번 챕터에서 파헤칠 스프링의 정체를 먼저 큰 그림으로 펼쳐 보겠습니다. 스프링이 내 코드를 대신 실행하는 원리를 순수 자바로 세 단계에 걸쳐 직접 만들어 볼 예정입니다. 지금은 세 단계가 있다는 것만 눈에 담아 두면 됩니다.

그림 1-1. 스프링이 내 코드를 실행하는 원리를 if-else, 리플렉션, 컴포넌트 스캔 세 단계로 직접 구현합니다

이번 챕터가 끝나면

  • 라이브러리와 프레임워크가 무엇이 다른지, 제어의 역전이 무엇인지 설명할 수 있습니다
  • 스프링이 리플렉션으로 내가 만든 메서드를 찾아 실행하는 원리를 이해합니다
  • 커스텀 어노테이션과 컴포넌트 스캔이 어떻게 동작하는지 순수 자바로 직접 구현합니다

1.1 프레임워크

1.1.1 라이브러리와 프레임워크는 무엇이 다를까

라이브러리(Library)는 개발자가 필요할 때 꺼내 쓰는 기능입니다. 날짜 계산이 필요하면 날짜 라이브러리를, 파일을 읽어야 하면 파일 라이브러리를 원하는 위치에서 호출합니다. 어떤 기능을 언제 부를지 개발자가 결정하며, 프로그램의 전체 흐름도 직접 제어합니다.

반면, 프레임워크(Framework)는 이 주도권이 뒤집혀 있습니다. 집을 새로 지을 때 기둥과 벽, 배관이 이미 갖춰진 골조를 떠올려 보세요. 개발자는 그 안에서 방만 꾸미면 됩니다. 프레임워크도 이처럼 프로그램에 공통으로 필요한 뼈대를 미리 갖춰 둔 틀입니다. 개발자는 뼈대를 다시 만들지 않고, 정해진 위치에 자신의 코드만 얹으면 됩니다.

그림 1-2. 라이브러리는 필요한 기능을 내가 골라 부르고, 프레임워크는 갖춰진 틀에 내 코드만 채웁니다

1.1.2 제어의 역전

뼈대를 프레임워크가 쥐고 있다는 것은, 프로그램의 전체 흐름도 프레임워크가 주도한다는 뜻입니다. 개발자가 작성한 코드가 언제 실행될지 역시 프레임워크가 결정합니다.

라이브러리를 쓸 때는 개발자가 필요한 순간에 직접 기능을 호출했습니다. 프레임워크에서는 이 방향이 반대가 됩니다. 개발자는 코드를 정해진 위치에 올려두기만 하고, 이를 호출해 실행하는 주체는 프레임워크가 됩니다. 이처럼 실행의 주도권이 개발자에서 프레임워크로 넘어가는 현상을 제어의 역전(IoC, Inversion of Control)이라고 합니다.

스프링은 자바로 웹 서버를 만들 때 필요한 뼈대를 미리 갖춘 프레임워크입니다. 오픈이가 막혔던 그 뼈대, 요청을 받아들이고 주소를 라우팅하며 결과를 응답으로 내보내는 공통 작업을 스프링이 대신 담당합니다. 개발자는 어떤 주소에 어떤 응답을 반환할지, 핵심 기능만 작성하면 됩니다.

1.2 스프링은 어떻게 내 메서드를 찾아 실행하나

여기서 오픈이의 머릿속에 의문이 하나 생깁니다. 스프링을 쓰면 클래스를 하나 만들고 그 위에 표식을 붙이는 게 전부입니다. 그런데 브라우저에서 특정 주소로 요청을 보내면, 등록한 적도 없는 그 클래스의 메서드가 실행됩니다.

나는 이 메서드를 어디에도 등록한 적이 없는데. 스프링은 이게 여기 있는 걸 어떻게 알고 부르지?

프로그램은 보통 개발자가 new로 객체를 만들고, 이름을 정확히 적어 메서드를 호출해야 실행됩니다. 그런데 스프링은 개발자가 무슨 클래스를 만들지, 그 안에 어떤 메서드를 둘지 미리 알 수 없습니다. 개발자가 방금 작성한 코드를, 이름도 모르는 채로 찾아내 실행해야 합니다.

이 일을 가능하게 하는 기술이 리플렉션(Reflection)입니다. 리플렉션은 프로그램 실행 도중(런타임)에 클래스와 메서드, 필드 정보를 읽고 호출까지 할 수 있는 기능입니다. 코드를 미리 알지 못해도, 실행 중에 들여다보며 동적으로 객체를 만들고 메서드를 실행할 수 있습니다.

말로만 들으면 아직 손에 잡히지 않습니다. 그래서 스프링이 하는 일을 순수 자바로 직접 만들어 보겠습니다. 가장 원시적인 방법에서 출발해, 리플렉션을 도입하고, 폴더를 자동으로 뒤지는 단계까지 세 번에 걸쳐 발전시킵니다.

1.3 if-else 라우팅과 그 한계

가장 단순한 방법부터 시작합니다. 요청 주소를 하나 정해 두고, 그 주소가 무엇인지 if 문으로 따져 알맞은 메서드를 직접 부르는 방식입니다.

먼저 요청을 처리할 컨트롤러를 만듭니다. 게시글을 다루는 BoardController에 등록(insert), 삭제(delete), 수정(update) 세 메서드를 둡니다. 각 메서드는 자신이 호출되었다는 것을 콘솔에 찍기만 합니다.

ex01/BoardController.java를 열고 아래 코드를 작성합니다.

실습 1 ex01/BoardController.java. 요청을 처리할 컨트롤러
public class BoardController { public void insert() { System.out.println("insert 호출됨"); } public void delete() { System.out.println("delete 호출됨"); } public void update() { System.out.println("update 호출됨"); } }

이제 이 컨트롤러를 부르는 main을 작성합니다. uri라는 변수에 요청 주소가 담겨 있다고 가정하고, 그 값을 if 문으로 하나씩 비교해 알맞은 메서드로 연결합니다. 요청 주소를 받아 담당 메서드로 넘겨주는 이 연결 작업을 라우팅(Routing)이라고 합니다.

ex01/App.java를 열고 TODO 자리에 아래 코드를 작성합니다.

실습 2 ex01/App.java. 주소에 따라 메서드 호출
public class App { public static void main(String[] args) { String uri = "/insert"; BoardController boardController = new BoardController(); // TODO: uri에 맞는 메서드를 직접 호출한다 // 1. 주소가 /insert면 insert() 호출 if (uri.equals("/insert")) { boardController.insert(); // 2. /update면 update() 호출 } else if (uri.equals("/update")) { boardController.update(); // 3. /delete면 delete() 호출 } else if (uri.equals("/delete")) { boardController.delete(); } } }

uri 값이 /insert이므로, main을 실행하면 첫 번째 조건이 맞아 insert()가 불립니다. 콘솔에 insert 호출됨이 출력됩니다.

여기까지는 잘 동작합니다. 그런데 게시글을 조회하는 기능이 필요해져, 컨트롤러에 select 메서드를 하나 더 추가한다고 해 보겠습니다.

설명 ex01/BoardController.java. 메서드 추가
public void select() { System.out.println("select 호출됨"); }

메서드를 추가하는 것만으로는 끝나지 않습니다. /select 요청이 들어와도 main의 if 문에는 그 주소를 처리할 분기가 없습니다. 결국 App.java로 돌아가 else if (uri.equals("/select")) 한 줄을 또 붙여야 합니다.

메서드 하나 늘 때마다 호출부를 또 고치라고?

메서드를 추가할 때마다 그것을 부르는 쪽 코드까지 손대야 한다는 것이 이 방식의 한계입니다. 개발자 한 명이 자기 코드를 고치는 것이라면 그나마 참을 만합니다. 하지만 스프링 같은 프레임워크 입장에서는 사정이 다릅니다. 프레임워크는 개발자가 앞으로 어떤 컨트롤러에 어떤 메서드를 만들지 전혀 알 수 없습니다. 그런데도 개발자가 메서드를 추가할 때마다 프레임워크의 호출부를 고쳐야 한다면, 그런 프레임워크는 쓸 수가 없습니다.

그래서 필요한 것이 리플렉션입니다. 호출부를 건드리지 않고, 실행 중에 컨트롤러를 들여다보며 알맞은 메서드를 찾아 부르는 방식으로 바꿔 보겠습니다.

1.4 리플렉션과 표식으로 찾아 호출

방향을 바꿉니다. 주소를 if 문 안에 박아 두는 대신, 각 메서드 위에 자신이 담당할 주소를 표식으로 달아 둡니다. 그리고 실행 중에 컨트롤러의 메서드를 모두 훑으며 표식을 읽어, 요청 주소와 일치하는 메서드를 찾아 호출합니다.

메서드 위에 붙이는 이 표식을 어노테이션(Annotation)이라고 합니다. 어노테이션은 클래스나 메서드에 붙이는 특별한 표시로, 실행 중에 리플렉션이 그 표시를 읽어 알맞은 동작을 자동으로 수행합니다.

그림 1-3. if-else는 메서드를 추가할 때 호출부까지 고쳐야 하지만, 리플렉션은 컨트롤러에 표식만 달면 호출부는 건드리지 않습니다

스프링에는 @RequestMapping 같은 어노테이션이 이미 준비되어 있습니다. 그 정체를 이해하기 위해, 같은 이름의 어노테이션을 직접 만들어 보겠습니다.

ex02/RequestMapping.java를 열고 아래 코드를 작성합니다. 어노테이션은 클래스나 인터페이스처럼 @interface 키워드로 정의합니다.

실습 3 ex02/RequestMapping.java. 주소를 담는 커스텀 어노테이션
// 1. 실행 중(런타임)에도 이 표식을 읽을 수 있게 유지한다 @Retention(RetentionPolicy.RUNTIME) // 2. 메서드 위에만 붙일 수 있는 표식으로 지정한다 @Target(ElementType.METHOD) public @interface RequestMapping { // 3. 이 표식이 담을 속성 - 담당할 주소 String uri(); }

두 개의 표식이 이 어노테이션의 성격을 결정합니다. @Retention(RetentionPolicy.RUNTIME) 은 이 어노테이션을 실행 중에도 읽을 수 있게 유지하라는 지시입니다. 리플렉션은 실행 중에 표식을 읽으므로, 이 설정이 없으면 표식이 컴파일 이후 사라져 리플렉션이 보지 못합니다. @Target(ElementType.METHOD) 은 이 어노테이션을 메서드 위에만 붙일 수 있게 제한합니다. String uri() 는 이 표식이 담을 값으로, 각 메서드가 담당할 주소를 여기에 적어 둡니다.

이제 앞서 if 문으로 비교하던 주소를, 각 메서드의 표식으로 옮깁니다. ex02/BoardController.java를 열고 아래처럼 메서드마다 @RequestMapping을 답니다.

실습 4 ex02/BoardController.java. 메서드마다 담당 주소를 표식으로
public class BoardController { @RequestMapping(uri = "/insert") public void insert() { System.out.println("insert 호출됨"); } @RequestMapping(uri = "/delete") public void delete() { System.out.println("delete 호출됨"); } @RequestMapping(uri = "/update") public void update() { System.out.println("update 호출됨"); } @RequestMapping(uri = "/select") public void select() { System.out.println("select 호출됨"); } }

각 메서드가 자신이 담당할 주소를 명찰처럼 달고 있습니다. 이제 main에서 if 문 없이, 이 명찰을 읽어 요청 주소와 맞는 메서드를 찾아 부르면 됩니다.

ex02/App.java를 열고 TODO 자리에 아래 코드를 작성합니다.

실습 5 ex02/App.java. 표식을 읽어 맞는 메서드를 호출
public class App { public static void main(String[] args) { String uri = "/update"; BoardController boardController = new BoardController(); // TODO: 표식을 읽어 uri가 일치하는 메서드를 실행한다 // 1. 컨트롤러가 가진 모든 메서드를 꺼낸다 Method[] methods = boardController.getClass().getDeclaredMethods(); for (Method method : methods) { // 2. 그 메서드에 붙은 @RequestMapping 표식을 읽는다 RequestMapping rm = method.getDeclaredAnnotation(RequestMapping.class); // 3. 표식의 uri가 요청 주소와 같으면 그 메서드를 실행한다 if (rm.uri().equals(uri)) { method.invoke(boardController); break; } } } }

여기서 리플렉션의 세 동작이 등장합니다. getClass().getDeclaredMethods() 는 컨트롤러가 가진 모든 메서드를 꺼내 옵니다. 개발자가 메서드 이름을 하나하나 적지 않아도, 실행 중에 클래스가 가진 메서드 목록을 통째로 얻어냅니다. getDeclaredAnnotation(RequestMapping.class) 는 각 메서드에 붙은 @RequestMapping 표식을 읽어 옵니다. method.invoke(boardController) 는 찾아낸 메서드를 실제로 호출합니다. 이름을 직접 적어 부르는 대신, 리플렉션이 쥐고 있는 메서드를 실행하라고 시키는 것입니다.

uri 값이 /update이므로, 반복문이 표식을 훑다가 /update 명찰을 단 update()를 만나 호출합니다. 실행하면 콘솔에 update 호출됨이 출력됩니다.

이제 앞서 골칫거리였던 상황을 다시 떠올려 보겠습니다. 컨트롤러에 새 메서드를 추가하려면 어떻게 해야 할까요?

설명 ex02/BoardController.java. 표식을 단 메서드만 추가
@RequestMapping(uri = "/create") public void create() { System.out.println("create 호출됨"); }

컨트롤러에 표식을 단 메서드를 추가하는 것으로 끝입니다. main은 어떤 메서드가 새로 생겼는지 알 필요가 없습니다. 실행 중에 메서드 목록을 다시 훑어 표식을 읽을 뿐이므로, 호출부 코드는 한 글자도 건드리지 않습니다.

표식만 달면 끝이네.

1.5 폴더를 뒤져 자동 등록·실행

한 가지가 아직 남았습니다. main은 여전히 new BoardController()로 컨트롤러를 직접 만들고 있습니다. 컨트롤러가 하나면 상관없지만, 게시판 컨트롤러, 회원 컨트롤러, 댓글 컨트롤러처럼 늘어나면 그때마다 new를 손으로 적어야 합니다. 프레임워크는 개발자가 어떤 컨트롤러를 만들지 미리 알 수 없으므로, 이 방식도 결국 앞의 if 문과 같은 한계에 부딪힙니다.

그래서 이번에는 클래스를 직접 new 하지 않습니다. 지정한 폴더를 통째로 뒤져, 표식이 붙은 클래스만 골라 객체로 만들어 둡니다. 특정 어노테이션이 붙은 클래스를 자동으로 찾아 객체를 생성하고 관리하는 이 기능을 컴포넌트 스캔(Component Scan)이라고 합니다.

그림 1-4. 폴더 안의 클래스를 하나씩 살펴 표식이 붙은 것만 객체로 만들어 보관하고, 요청이 오면 그 객체에서 메서드를 찾아 실행합니다

이번에는 메서드가 아니라 클래스에 붙일 표식이 필요합니다. 컨트롤러 역할을 하는 클래스라는 것을 나타내는 @Controller 어노테이션을 만듭니다.

ex03/Controller.java를 열고 아래 코드를 작성합니다. 메서드가 아닌 클래스에 붙이므로 @Target을 ElementType.TYPE으로 지정합니다.

실습 6 ex03/Controller.java. 컨트롤러임을 나타내는 표식
@Retention(RetentionPolicy.RUNTIME) // 1. 클래스나 인터페이스 위에 붙일 수 있는 표식으로 지정한다 @Target(ElementType.TYPE) public @interface Controller { }

앞서 만든 RequestMapping.java는 그대로 재사용합니다. ex03 폴더에도 같은 어노테이션이 필요하므로, ex02의 것을 복사해 둡니다. 이제 BoardController 클래스 위에 @Controller를 답니다. 이 표식이 붙은 클래스를 스캔으로 찾아내는 것이 목적입니다.

ex03/BoardController.java를 열고 클래스 선언 위에 @Controller를 추가합니다.

실습 7 ex03/BoardController.java. 클래스 위에 @Controller 표식
@Controller public class BoardController { @RequestMapping(uri = "/insert") public void insert() { System.out.println("insert 호출됨"); } @RequestMapping(uri = "/delete") public void delete() { System.out.println("delete 호출됨"); } @RequestMapping(uri = "/update") public void update() { System.out.println("update 호출됨"); } @RequestMapping(uri = "/select") public void select() { System.out.println("select 호출됨"); } @RequestMapping(uri = "/create") public void create() { System.out.println("create 호출됨"); } }

이제 핵심인 main입니다. new BoardController()는 어디에도 없습니다. 대신 ex03 폴더의 실제 경로를 찾아, 그 안의 클래스 파일을 하나씩 살피며 @Controller가 붙은 것만 객체로 만듭니다.

ex03/App.java를 열고 TODO 자리에 아래 코드를 작성합니다.

실습 8 ex03/App.java. 폴더를 뒤져 @Controller 클래스를 자동 등록
public class App { public static void main(String[] args) { // TODO: ex03 폴더를 뒤져 @Controller 클래스만 객체로 만든다 // 1. ex03 폴더의 실제 경로를 찾는다 ClassLoader classLoader = Thread.currentThread().getContextClassLoader(); URL packageUrl = classLoader.getResource("com/reflection/ex03"); File ex03 = new File(packageUrl.toURI()); List<Object> instances = new ArrayList<>(); // 2. 폴더 안의 .class 파일을 하나씩 살핀다 for (File file : ex03.listFiles()) { System.out.println("파일명: " + file.getName()); if (file.getName().endsWith(".class")) { String className = "com.reflection.ex03." + file.getName().replace(".class", ""); Class cls = Class.forName(className); // 3. @Controller 표식이 붙은 클래스만 객체로 만들어 보관한다 if (cls.isAnnotationPresent(Controller.class)) { Object instance = cls.newInstance(); instances.add(instance); } } } // 4. 보관한 객체에서 주소에 맞는 메서드를 찾아 실행한다 findUri(instances, "/delete"); } }

새로 등장한 도구들이 폴더 스캔을 이룹니다. ClassLoader는 자바가 클래스 파일을 읽어 들이는 장치로, getResource("com/reflection/ex03")로 그 폴더의 실제 위치를 알아냅니다. 그 폴더를 File로 열어 listFiles()로 파일 목록을 얻고, 이름이 .class로 끝나는 것만 골라 Class.forName으로 클래스 정보를 읽어 옵니다. isAnnotationPresent(Controller.class)는 그 클래스에 @Controller가 붙어 있는지 확인하고, 붙어 있으면 newInstance()로 객체를 만들어 instances 목록에 담습니다.

찾아서 호출하는 뒷부분은 실습 5에서 만든 리플렉션 로직 그대로입니다. 이번에는 객체가 여러 개일 수 있으므로, 보관한 객체를 하나씩 훑도록 findUri 메서드로 감쌌습니다.

설명 ex03/App.java. 보관한 객체에서 주소로 메서드 찾기
public static void findUri(List<Object> instances, String uri) { for (Object instance : instances) { Method[] methods = instance.getClass().getDeclaredMethods(); for (Method method : methods) { RequestMapping rm = method.getDeclaredAnnotation(RequestMapping.class); if (rm.uri().equals(uri)) { method.invoke(instance); break; } } } }

main을 실행하면 콘솔에 폴더 안 파일들의 이름이 하나씩 찍히고, @Controller가 붙은 BoardController만 객체로 등록됩니다. 마지막으로 findUri에 넘긴 /delete 주소에 맞는 메서드가 호출되어 delete 호출됨이 출력됩니다.

그림 1-5. 폴더를 스캔해 파일 이름을 훑고, @Controller가 붙은 클래스에서 delete 메서드를 찾아 실행한 결과입니다

이제 개발자가 할 일은 클래스에 @Controller를 붙이고 메서드에 주소 표식을 다는 것뿐입니다. 객체를 만드는 일도, 메서드를 찾아 부르는 일도 프로그램이 알아서 합니다. 앞서 오픈이가 품었던 의문, 등록한 적 없는 메서드가 어떻게 실행되느냐는 물음의 답이 바로 이것입니다.

1.6 스프링이 객체를 만들어 넣어준다

방금 만든 스캔에서 한 가지를 더 짚고 넘어가겠습니다. BoardController 객체를 개발자가 만든 것이 아니라, 프로그램이 표식을 확인하고 대신 만들어 instances에 보관했다는 점입니다.

스프링도 동일하게 동작합니다. 표식이 붙은 클래스를 찾아 객체로 만들고, 자신이 관리하는 공간에 담아 둡니다. 이렇게 스프링이 직접 생성하고 관리하는 객체를 빈(Bean)이라고 부릅니다. 방금 instances 목록에 담은 객체가, 스프링에서는 빈에 해당합니다.

스프링은 여기서 한 걸음 더 나아갑니다. 만들어 둔 빈들을 서로 필요한 곳에 조립해 줍니다. 다음 챕터에서 만들 게시판 컨트롤러는 게시판 서비스 객체를 필요로 하는데, 개발자가 직접 new로 넣어 주지 않아도 스프링이 보관소에서 알맞은 빈을 꺼내 넣어 줍니다. 이처럼 객체가 필요한 곳에 외부에서 객체를 넣어 주는 방식을 의존성 주입(DI, Dependency Injection)이라고 합니다.

컨트롤러가 서비스를 주입받아 쓰는 구체적인 모습은 다음 챕터에서 게시판을 만들며 직접 확인해 보겠습니다. 지금은 스프링이 객체를 대신 만들어 필요한 곳에 넣어 준다는 큰 그림만 담아 두면 충분합니다.

1.7 요청 하나가 실행되기까지

리플렉션과 스캔이 스프링 안에서 실제로 어디에 놓여 있는지, 요청 하나의 여정을 따라가며 확인해 보겠습니다. 브라우저가 주소를 요청한 순간부터 데이터베이스까지 이어지는 전체 흐름입니다. 지금은 각 단계의 이름과 역할만 가볍게 파악하고, 세부 동작은 이어지는 챕터에서 다룹니다.

그림 1-6. 요청이 톰캣과 디스패처 서블릿을 거쳐 컨트롤러 메서드로 전달되고, 서비스와 리포지토리를 지나 데이터베이스까지 이어지는 흐름입니다

브라우저가 8080 포트로 요청을 보내면 톰캣(Tomcat)이 받습니다. 톰캣은 요청의 헤더와 본문을 담은 req 객체와, 응답을 담을 resp 객체를 만듭니다. 이때 요청마다 새 일꾼을 만드는 대신, 미리 준비해 둔 일꾼 묶음에서 하나를 꺼내 작업을 맡깁니다. 이렇게 미리 만들어 두고 빌려 쓰는 방식을 풀링(Pooling)이라고 하며, 요청 처리에 쓰는 것이 요청 풀링(예: 50개), 데이터베이스 연결에 쓰는 것이 DBCP(Database Connection Pool, 예: 20개)입니다. 요청이 몰려도 서버가 무너지지 않는 이유가 여기에 있습니다.

톰캣이 받은 요청은 스프링 컨테이너의 진입점인 디스패처 서블릿(DispatcherServlet, 그림에서 DS)으로 넘어갑니다. 디스패처 서블릿은 모든 요청이 가장 먼저 도착하는 안내데스크입니다. 그리고 이 안내데스크가 하는 일이 바로 이번 챕터에서 만든 원리입니다. 요청의 주소를 분석해, 어떤 컨트롤러의 어떤 메서드가 그 주소를 담당하는지 리플렉션으로 찾아 호출합니다. 앞서 findUri가 표식을 읽어 맞는 메서드를 부른 것과 같은 일을, 스프링에서는 디스패처 서블릿이 합니다.

호출된 컨트롤러(C)는 요청을 받아 응답을 처리하고, 실제 작업은 서비스(S)로 넘깁니다. 서비스는 트랜잭션을 관리하며 리포지토리(R)를 통해 데이터베이스에 질의를 던집니다. 그 사이에서 객체와 데이터베이스를 이어 주는 영속성 컨텍스트(PC)가 데이터를 관리합니다. 컨트롤러부터 서비스, 리포지토리로 이어지는 이 계층 구조와 영속성 컨텍스트는 다음 챕터의 게시판 실습에서 직접 만들며 확인합니다.

이 책의 학습 여정은 다섯 챕터로 이어집니다.

그림 1-7. 게시판을 만들고 예외 처리와 로그인, 댓글까지 더하는 앞으로의 학습 여정입니다

  • 챕터 3에서는 없는 글을 조회해도 터지지 않게 예외를 처리하고, 응답을 DTO로 정리합니다.
  • 챕터 4에서는 로그인(JWT)을 붙여 로그인한 본인만 자기 글을 수정하고 삭제하게 합니다.
  • 챕터 5에서는 게시글에 댓글을 달고 삭제합니다.

이 책은 코드를 많이 쓰기보다 스프링의 개념과 큰 흐름을 이해하고, 단계별로 게시판을 완성하며 익히는 것을 목표로 합니다. 한 챕터씩 스프링의 큰 흐름을 따라가 보겠습니다.

이번 챕터에서 다룬 용어를 한자리에 모으면 다음과 같습니다.

비유 용어 정의
골조가 갖춰진 집 프레임워크(Framework) 공통으로 필요한 뼈대를 미리 갖춘 틀. 개발자는 정해진 위치에 자기 코드만 얹습니다
주도권이 뒤집힘 제어의 역전(IoC) 코드를 언제 실행할지 결정하는 주체가 개발자에서 프레임워크로 넘어가는 것입니다
실행 중에 코드를 들여다보는 눈 리플렉션(Reflection) 런타임에 클래스·메서드·필드 정보를 읽고 호출할 수 있는 기능입니다
메서드나 클래스에 붙이는 명찰 어노테이션(Annotation) 코드에 붙이는 특별한 표시. 실행 중 리플렉션이 읽어 동작을 수행합니다
폴더를 뒤져 명찰을 찾음 컴포넌트 스캔(Component Scan) 특정 어노테이션이 붙은 클래스를 자동으로 찾아 객체로 생성·관리하는 기능입니다
스프링이 보관하는 객체 빈(Bean) 스프링이 직접 생성하고 관리하는 객체입니다
필요한 곳에 넣어 줌 의존성 주입(DI) 객체가 필요한 곳에 외부에서 객체를 넣어 주는 방식입니다
요청의 안내데스크 디스패처 서블릿(DispatcherServlet) 모든 요청의 진입점. 주소를 분석해 담당 메서드를 리플렉션으로 찾아 호출합니다

이것만은 기억하자

  • 프레임워크는 공통으로 필요한 뼈대를 미리 갖춘 틀입니다. 개발자는 뼈대를 다시 만들지 않고, 그 위에 자기 기능만 얹습니다.
  • 스프링이 등록한 적 없는 내 메서드를 찾아 실행하는 정체는 리플렉션입니다. 표식(어노테이션)을 읽어 맞는 메서드를 찾고(method.invoke), 폴더를 뒤져 표식 붙은 클래스를 자동으로 객체로 등록합니다(컴포넌트 스캔).
  • 다음 챕터에서는 이 뼈대 위에 게시판을 만듭니다. 컨트롤러와 서비스, 리포지토리를 직접 짜서 글을 저장하고 불러오는 REST API를 완성합니다.
