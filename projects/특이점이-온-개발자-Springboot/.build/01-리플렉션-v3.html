챕터 1. 리플렉션

오픈이는 이제 막 개발을 배우기 시작한 학생입니다. 이번 학기 과제는 게시판 웹 서버를 만들어 제출하는 것입니다. 써 본 언어가 자바(Java)뿐이라 자바로 코드를 쓰기 시작했지만, 몇 줄 쓰기도 전에 벽에 부딪혔습니다.

문제는 게시판 기능이 아니라 그 이전 단계에 있었습니다. 브라우저와 연결을 맺으려면 소켓부터 직접 열어야만 했습니다. 연결이 된 후에는 요청 문자열을 잘라내어 어떤 주소를 요청했는지 파악해야 했고, 그 주소마다 실행할 코드를 일일이 연결해 주어야 했습니다.

게시글 하나 띄우지 못했는데 통신과 문자열 처리에만 수십 줄이 쌓였습니다. 오픈이는 모니터를 보며 한숨을 쉬었습니다.

과제는 게시판인데, 서버 뼈대만 만들다 학기가 끝나겠네.

다음 날, 같은 수업을 듣는 선배에게 사정을 털어놓았습니다. 화면을 훑어보던 선배가 말했습니다.

선배: "이런 기본 뼈대를 밑바닥부터 직접 짜는 사람은 없어요. 프레임워크를 쓰면 통신 연결이나 주소 분배 같은 공통 기능은 이미 갖춰져 있거든요. 자바 웹이면 보통 스프링을 쓰니까, 그 위에 만들고 싶은 게시판 기능만 구현해 봐요."
그림 1-1. 이번 챕터에서는 스프링이 내 코드를 실행하는 원리를 if-else, 리플렉션, 컴포넌트 스캔 세 단계로 나눠 직접 구현합니다

이번 챕터가 끝나면

  • 라이브러리와 프레임워크가 무엇이 다른지, 제어의 역전이 무엇인지 설명할 수 있습니다
  • 스프링이 리플렉션으로 내가 만든 메서드를 찾아 실행하는 원리를 이해합니다
  • 커스텀 어노테이션과 컴포넌트 스캔이 어떻게 동작하는지 순수 자바로 직접 구현합니다

1.1 스프링의 실행 원리

1.1.1 라이브러리와 프레임워크

날짜를 계산하거나 파일을 읽을 때처럼, 개발자가 필요할 때마다 직접 꺼내 쓰는 도구를 라이브러리(Library) 라고 합니다. 언제 어떤 기능을 쓸지, 프로그램의 전체 흐름은 개발자가 정합니다.

반면, 스프링과 같은 프레임워크(Framework) 는 다릅니다. 통신 연결이나 주소 분배처럼 웹 서버가 갖춰야 할 기본 뼈대가 이미 완성되어 있습니다. 건축으로 치면 튼튼한 기둥과 벽, 배관 공사까지 모두 끝난 상태와 같습니다. 개발자는 바닥부터 새로 집을 짓는 대신, 미리 세워진 뼈대 안에서 자신이 원하는 기능만 알맞게 채워 넣으면 됩니다.

그림 1-2. 라이브러리는 필요한 도구를 골라 꺼내 쓰고, 프레임워크는 이미 세워진 뼈대 안에 내 코드만 채웁니다

1.1.2 제어의 역전

프레임워크의 가장 큰 특징은 호출의 방향에서 드러납니다. 라이브러리를 쓸 때는 개발자의 코드가 라이브러리를 호출합니다. 필요한 기능이 있을 때마다 개발자가 원하는 것을 골라 호출합니다. 프레임워크는 반대입니다. 개발자가 정해진 규칙에 맞춰 코드를 준비해 두면, 실행 중에 프레임워크가 필요한 시점에 준비된 코드를 호출합니다.

그림 1-3. 라이브러리는 개발자가 기능을 호출하지만, 프레임워크는 프레임워크가 개발자의 코드를 호출합니다

이처럼 프로그램의 실행 주도권이 개발자에서 프레임워크로 뒤바뀌는 현상을 제어의 역전(IoC, Inversion of Control) 이라고 부릅니다.

스프링도 이 원칙을 따릅니다. 통신 연결이나 주소 분배 같은 공통 작업은 스프링이 처리합니다. 덕분에 개발자는 어떤 요청이 들어왔을 때 무엇을 응답할지에만 집중할 수 있습니다.

1.1.3 리플렉션

주도권이 프레임워크로 넘어갔다는 것은, 개발자가 작성한 코드를 스프링이 대신 실행해 준다는 뜻입니다. 그런데 남이 만든 코드를 대신 실행하는 일은 간단하지 않습니다. 보통의 자바 프로그램에서는 코드를 호출하는 것도 코드를 작성한 개발자입니다. 개발자는 자기가 만든 클래스라 이름을 알고 있으니, new로 객체를 만들어 메서드 이름을 정확히 적어 호출합니다.

그림 1-4. 보통의 자바에서는 개발자가 메서드 이름을 적어 직접 호출합니다

반면 스프링에서는 코드를 호출하는 것은 스프링이고, 코드를 작성하는 것은 개발자입니다. 스프링은 개발자가 앞으로 어떤 클래스에 어떤 메서드를 만들지 미리 알 수 없습니다. 이름도 모르는 코드를 실행 중에 찾아내 호출해야 합니다.

그림 1-5. 스프링은 이름을 모르므로 실행 중에 클래스 안을 읽어 메서드 목록을 확인합니다

이 일을 가능하게 하는 기술이 리플렉션(Reflection) 입니다. 리플렉션은 프로그램이 실행되는 도중(런타임)에 클래스와 메서드, 필드 정보를 읽고 호출까지 할 수 있는 자바의 기능입니다.

1.2 리플렉션 구현

리플렉션이 실제로 어떻게 동작하는지 자바 코드로 직접 구현해 보겠습니다. 가장 단순한 형태의 코드부터 시작해 한 단계씩 기능을 확장해 나갑니다.

1.2.1 if-else 라우팅

가장 원시적인 요청 처리 방식은 요청 주소를 if 문으로 비교해 알맞은 메서드를 직접 호출하는 것입니다. 먼저 게시글을 다루는 BoardController에 등록(insert), 삭제(delete), 수정(update) 세 메서드를 작성합니다. 각 메서드는 호출되면 콘솔에 이름을 찍습니다.

ex01/BoardController.java를 열고 아래 코드를 작성합니다.

실습 1 ex01/BoardController.java. 요청을 처리할 컨트롤러
public class BoardController { public void insert() { System.out.println("insert 호출됨"); } public void delete() { System.out.println("delete 호출됨"); } public void update() { System.out.println("update 호출됨"); } }

이제 이 컨트롤러를 호출하는 main 메서드를 작성합니다. uri에 담긴 요청 주소를 담당 메서드로 넘기는 연결 작업을 라우팅(Routing)이라고 합니다.

ex01/App.java를 열고 아래 코드를 작성합니다.

실습 2 ex01/App.java. 주소에 따라 메서드 호출
public class App { public static void main(String[] args) { String uri = "/insert"; BoardController boardController = new BoardController(); // TODO: uri에 맞는 메서드를 직접 호출한다 // 1. 주소가 /insert면 insert() 호출 if (uri.equals("/insert")) { boardController.insert(); // 2. /update면 update() 호출 } else if (uri.equals("/update")) { boardController.update(); // 3. /delete면 delete() 호출 } else if (uri.equals("/delete")) { boardController.delete(); } } }

uri가 /insert이므로, 실행하면 콘솔에 insert 호출됨이 출력됩니다.

실행결과
insert 호출됨
그림 1-6. if 문이 /insert 주소에 맞는 insert 메서드를 호출한 결과입니다

여기서 만약 게시글을 조회하는 select 메서드를 하나 더 추가한다면 어떨까요?

설명 ex01/BoardController.java. 메서드 추가
public void select() { System.out.println("select 호출됨"); }

이제 /select 요청이 들어와도 main 메서드의 if 문에는 이를 받을 분기가 없습니다. 메서드를 추가할 때마다 App.java로 돌아가 else if 한 줄을 더 추가해야 합니다. 호출부까지 매번 고쳐야 하는 것이 이 방식의 한계입니다.

그래서 필요한 것이 리플렉션입니다. 호출부를 건드리지 않고, 실행 중에 컨트롤러의 메서드를 살펴 알맞은 메서드를 찾아 호출하는 방식으로 바꿔 보겠습니다.

1.2.2 어노테이션과 리플렉션

주소를 if 문 안에 나열하는 대신, 각 메서드 위에 담당할 주소를 표식으로 붙여 둡니다. 그러면 프로그램이 실행 중에 컨트롤러의 메서드를 모두 확인해 붙어 있는 표식을 읽고, 요청 주소와 일치하는 메서드를 찾아 호출할 수 있습니다.

메서드 위에 붙이는 이 표식을 어노테이션(Annotation) 이라고 합니다. 어노테이션은 클래스나 메서드에 붙이는 특별한 표시로, 실행 중에 리플렉션이 표시를 읽어 알맞은 동작을 자동으로 수행합니다.

그림 1-7. if문은 등록된 주소만 실행하지만, 리플렉션은 어노테이션을 읽어 처음 보는 주소도 실행합니다

스프링에는 @RequestMapping 같은 어노테이션이 이미 준비되어 있습니다. 어떻게 동작하는지 이해하기 위해, 같은 이름의 어노테이션을 직접 만들어 보겠습니다.

ex02/RequestMapping.java를 열고 아래 코드를 작성합니다. RequestMapping은 메서드마다 담당할 요청 주소를 적어 두는 어노테이션입니다.

실습 3 ex02/RequestMapping.java. 주소를 담는 커스텀 어노테이션
// 1. 실행 중(런타임)에도 이 어노테이션을 읽을 수 있게 유지한다 @Retention(RetentionPolicy.RUNTIME) // 2. 메서드 위에만 붙일 수 있는 어노테이션으로 지정한다 @Target(ElementType.METHOD) public @interface RequestMapping { // 3. 이 어노테이션이 담을 속성 - 담당할 주소 String uri(); }

어노테이션은 클래스나 인터페이스처럼 @interface 키워드로 정의합니다. RequestMapping은 메서드에만 붙일 수 있고, 컴파일한 뒤에도 사라지지 않아 실행 중에 리플렉션이 읽을 수 있습니다.

이제 앞서 if 문으로 비교하던 주소를, 각 메서드의 어노테이션으로 옮깁니다. ex02/BoardController.java를 열고 아래처럼 메서드마다 @RequestMapping을 추가합니다.

실습 4 ex02/BoardController.java. 메서드마다 담당 주소를 어노테이션으로
public class BoardController { @RequestMapping(uri = "/insert") public void insert() { System.out.println("insert 호출됨"); } @RequestMapping(uri = "/delete") public void delete() { System.out.println("delete 호출됨"); } @RequestMapping(uri = "/update") public void update() { System.out.println("update 호출됨"); } @RequestMapping(uri = "/select") public void select() { System.out.println("select 호출됨"); } }

이제 main 메서드가 if 문 없이 이 어노테이션을 읽어 요청 주소와 맞는 메서드를 호출하면 됩니다.

ex02/App.java를 열고 아래 코드를 작성합니다.

실습 5 ex02/App.java. 어노테이션을 읽어 맞는 메서드를 호출
public class App { public static void main(String[] args) { String uri = "/update"; BoardController boardController = new BoardController(); // TODO: 어노테이션을 읽어 uri가 일치하는 메서드를 실행한다 // 1. 컨트롤러가 가진 모든 메서드를 꺼낸다 Method[] methods = boardController.getClass().getDeclaredMethods(); for (Method method : methods) { // 2. 그 메서드에 붙은 @RequestMapping 어노테이션을 읽는다 RequestMapping rm = method.getDeclaredAnnotation(RequestMapping.class); // 3. 어노테이션의 uri가 요청 주소와 같으면 그 메서드를 실행한다 if (rm.uri().equals(uri)) { try { method.invoke(boardController); break; } catch (Exception e) { e.printStackTrace(); } } } } }

main 메서드는 어떤 메서드가 있는지 미리 알지 못해도, 리플렉션이 실행 중에 어노테이션을 읽어 요청 주소와 맞는 메서드를 호출합니다.

실행결과
update 호출됨
그림 1-8. 리플렉션이 /update 어노테이션을 읽어 update 메서드를 호출한 결과입니다

컨트롤러에 새 메서드를 추가할 때는 어떻게 될까요?

설명 ex02/BoardController.java. 어노테이션을 추가한 메서드
@RequestMapping(uri = "/create") public void create() { System.out.println("create 호출됨"); }

새 메서드에 어노테이션을 추가하면 됩니다. main 메서드는 실행 중에 목록을 다시 읽어 어노테이션을 확인하므로, 호출부는 수정하지 않아도 됩니다.

1.2.3 컴포넌트 스캔

지금은 main 메서드에서 객체를 직접 만들고 있습니다. 컨트롤러가 하나뿐이면 문제가 없지만, 게시판·회원·댓글로 늘어나면 개발자가 그때마다 객체를 만들어야 합니다. 객체 생성을 개발자가 맡는 한, 프레임워크는 어떤 컨트롤러가 있는지 미리 알 수 없어 이 방식도 앞의 if 문과 같은 한계를 가집니다.

그래서 이번에는 개발자가 객체를 직접 만들지 않습니다. 클래스에 어노테이션을 추가해 두면, 프로그램이 실행 중에 클래스를 확인해 어노테이션이 붙은 것만 객체로 만듭니다. 이 기능을 컴포넌트 스캔(Component Scan) 이라고 합니다.

그림 1-9. 개발자는 클래스에 어노테이션만 추가하고, 객체를 만드는 일은 프로그램이 맡습니다

이번에는 메서드가 아니라 클래스에 붙일 어노테이션이 필요합니다. 컨트롤러 역할을 하는 클래스라는 것을 나타내는 @Controller를 만듭니다.

ex03/Controller.java를 열고 아래 코드를 작성합니다.

실습 6 ex03/Controller.java. 컨트롤러임을 나타내는 어노테이션
@Retention(RetentionPolicy.RUNTIME) // 1. 클래스나 인터페이스 위에 붙일 수 있는 어노테이션으로 지정한다 @Target(ElementType.TYPE) public @interface Controller { }

이제 BoardController 클래스 위에 @Controller를 추가합니다. 이 어노테이션이 붙은 클래스를 스캔이 찾아냅니다.

ex03/BoardController.java를 열고 클래스 선언 위에 @Controller를 추가합니다.

실습 7 ex03/BoardController.java. 클래스 위에 @Controller 어노테이션
@Controller public class BoardController { @RequestMapping(uri = "/insert") public void insert() { System.out.println("insert 호출됨"); } @RequestMapping(uri = "/delete") public void delete() { System.out.println("delete 호출됨"); } @RequestMapping(uri = "/update") public void update() { System.out.println("update 호출됨"); } @RequestMapping(uri = "/select") public void select() { System.out.println("select 호출됨"); } @RequestMapping(uri = "/create") public void create() { System.out.println("create 호출됨"); } }

이제 핵심인 main 메서드입니다. new BoardController()는 어디에도 없습니다. 대신 main 메서드가 ex03 폴더의 실제 경로를 찾아, 폴더 안의 클래스 파일을 하나씩 확인해 @Controller가 붙은 것만 객체로 만듭니다.

ex03/App.java를 열고 아래 코드를 작성합니다.

실습 8 ex03/App.java. 폴더를 뒤져 @Controller 클래스를 자동 등록
public class App { public static void main(String[] args) throws URISyntaxException, ClassNotFoundException, InstantiationException, IllegalAccessException { // TODO: ex03 폴더를 뒤져 @Controller 클래스만 객체로 만든다 // 1. ex03 폴더의 실제 경로를 찾는다 ClassLoader classLoader = Thread.currentThread().getContextClassLoader(); URL packageUrl = classLoader.getResource("com/reflection/ex03"); File ex03 = new File(packageUrl.toURI()); List<Object> instances = new ArrayList<>(); // 2. 폴더 안의 .class 파일을 하나씩 살핀다 for (File file : ex03.listFiles()) { System.out.println("파일명: " + file.getName()); if (file.getName().endsWith(".class")) { String className = "com.reflection.ex03." + file.getName().replace(".class", ""); Class cls = Class.forName(className); // 3. @Controller 어노테이션이 붙은 클래스만 객체로 만들어 보관한다 if (cls.isAnnotationPresent(Controller.class)) { System.out.println("어노테이션이 있는 클래스 : " + file.getName()); Object instance = cls.newInstance(); instances.add(instance); } } } System.out.println("--------------------------------"); // 4. 보관한 객체에서 주소에 맞는 메서드를 찾아 실행한다 findUri(instances, "/delete"); } }

이번에는 객체가 여러 개일 수 있으므로, 보관한 객체를 하나씩 확인하는 코드를 findUri 메서드로 분리합니다.

설명 ex03/App.java. 보관한 객체에서 주소로 메서드 찾기
public static void findUri(List<Object> instances, String uri) { for (Object instance : instances) { Method[] methods = instance.getClass().getDeclaredMethods(); for (Method method : methods) { RequestMapping rm = method.getDeclaredAnnotation(RequestMapping.class); if (rm.uri().equals(uri)) { try { method.invoke(instance); break; } catch (Exception e) { e.printStackTrace(); } } } } }

실행하면 콘솔에 폴더 안 파일 이름이 하나씩 찍히고, @Controller가 붙은 BoardController만 객체로 등록됩니다. findUri에 넘긴 /delete에 맞는 delete()가 호출되어 delete 호출됨이 출력됩니다.

실행결과
파일명: App.class
파일명: BoardController.class
어노테이션이 있는 클래스 : BoardController.class
파일명: Controller.class
파일명: RequestMapping.class
--------------------------------
delete 호출됨
그림 1-10. 폴더를 스캔해 파일 이름을 읽고, @Controller가 붙은 클래스에서 delete 메서드를 찾아 실행한 결과입니다

이제 개발자는 클래스에는 @Controller를, 메서드에는 @RequestMapping을 추가하면 됩니다. 객체를 만드는 일도, 메서드를 찾아 호출하는 일도 프로그램이 대신 처리합니다. 이것이 컴포넌트 스캔의 원리입니다.

1.3 객체 생성과 연결

1.3.1 빈과 컨테이너

방금 앞서 살펴본 예제에서 BoardController 객체는 개발자가 직접 new 키워드로 생성하지 않았습니다. 프로그램이 클래스에 붙은 어노테이션을 확인하고, 객체를 대신 생성해 내부 저장소(instances)에 보관했습니다.

스프링의 핵심 원리도 이와 똑같이 동작합니다. 스프링은 애플리케이션이 실행될 때 특정 어노테이션이 붙은 클래스들을 찾아 객체로 생성하고, 이를 자신이 관리하는 전용 공간에 담아 둡니다. 이때 객체들을 보관하고 관리하는 특별한 공간을 스프링 컨테이너(Spring Container), 컨테이너가 담고 있는 이 객체들을 빈(Bean) 이라고 부릅니다.

그림 1-11. 스프링은 어노테이션이 붙은 클래스를 객체로 만들어 컨테이너에 보관합니다. 이 객체들을 빈이라고 부릅니다

1.3.2 의존성 주입

그렇다면 이렇게 만들어진 빈들은 어떻게 서로 기능들을 주고받을까요? 한 객체가 다른 객체를 필요로 하는 상태를 '의존성을 가진다'고 표현합니다. 그런데 코드 내부에서 의존 객체를 직접 생성하면 객체 간의 결합도가 높아져 향후 코드를 수정하거나 테스트하기가 까다로워집니다.

스프링은 이 문제를 의존성 주입(Dependency Injection) 이라는 방식으로 해결합니다. 빈이 다른 빈의 기능을 써야 할 때, 개발자는 필요한 빈을 직접 만들지 않고 무엇이 필요한지만 코드에 적어 둡니다. 그러면 컨테이너가 실행될 때 만들어 둔 빈 중에서 찾아 넣어 주고, 빈은 받은 기능을 그대로 불러 쓸 수 있습니다.

그림 1-12. 빈 A가 선언해 둔 클래스를 보고, 스프링 컨테이너가 클래스가 같은 빈 B를 찾아 주입합니다

이처럼 의존성 주입을 활용하면 개발자는 객체의 생성과 연결 같은 관리를 스프링 컨테이너에 맡길 수 있습니다. 결과적으로 개발자는 핵심 비즈니스 로직 구현에만 집중할 수 있고, 객체 간의 결합도가 낮아져 유연하고 유지보수하기 좋은 코드가 만들어집니다.

1.4 스프링의 요청 흐름

하나의 요청이 스프링에 도착해서 처리되기까지 어떤 길을 지나는지 따라가 보겠습니다.

그림 1-13. 요청은 톰캣을 지나 디스패처 서블릿으로 전달되고, 리플렉션으로 담당 컨트롤러가 호출됩니다

요청이 들어오면 스프링은 여러 단계를 거쳐 담당 컨트롤러로 넘깁니다. 웹 서버인 톰캣(Tomcat)이 요청을 받아 스프링에 넘기면, 디스패처 서블릿(DispatcherServlet) 이 요청 주소를 보고 담당 컨트롤러를 찾아 호출합니다. 개발자는 컨트롤러만 만들어 두면 되고, 어떤 주소를 어떤 컨트롤러가 맡을지 실행 중에 찾아 연결하는 일은 스프링이 리플렉션으로 대신합니다.

이것만은 기억하자

  • 프레임워크는 공통으로 필요한 뼈대를 미리 갖춘 틀입니다. 개발자는 뼈대를 다시 만들지 않고, 갖춰진 틀 위에 자기 기능만 구현합니다.
