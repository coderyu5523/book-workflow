챕터 4. 인증과 인가 - 로그인한 본인만

앞 챕터까지 만든 게시판은 글을 저장하고 꺼내는 일은 하지만, 그 요청을 누가 보냈는지는 확인하지 않습니다. 로그인 화면도, 요청을 보낸 사람을 가리는 장치도 어디에도 없습니다. 그래서 로그인 한 번 없이 1번 글에 수정 요청을 보내도 서버는 막힘없이 글을 덮어쓰고, 남의 글을 지우는 요청도 그대로 통과시킵니다.

화면을 붙이던 동료도 같은 것을 봤습니다.

동료: "저도 남의 글이 그냥 지워지던데요. 애초에 로그인 화면이 없잖아요."

지금 이 서버는 문만 덩그러니 있고 지키는 사람은 없는 성과 같습니다. 누구든 걸어 들어가서 창고를 열 수 있습니다. 이번 챕터에서 할 일은 그 성에 방어를 세워, 요청 하나하나가 걸러지도록 만드는 것입니다.

그림 4-1. 로그인하면 JWT가 발급되고, 이후 요청은 필터에서 신원이 심기고 인터셉터에서 자격이 가려진 뒤 컨트롤러로 전달됩니다

이번 챕터가 끝나면

  • 인증과 인가가 어떻게 다른지 설명할 수 있습니다
  • 로그인하면 JWT를 발급하고, 필터로 토큰을 확인해 신원을 심고, 인터셉터로 쓰기 요청을 막습니다
  • 로그인한 본인만 자기 글을 수정하고 삭제하게 만듭니다

4.1 완전히 공개된 게시판

문제를 눈으로 보고 시작하겠습니다. 로그인도, 아무 표식도 없이 1번 글에 수정을 요청합니다.

터미널 로그인 없이 남의 글 수정
PUT http://localhost:8080/api/boards/1 { "title": "누구나 고칠 수 있다", "content": "로그인도 안 했는데 고쳐졌다" }

응답은 200, 성공입니다.

{ "status": 200, "msg": "성공", "body": { "boardId": 1, "title": "누구나 고칠 수 있다", "content": "로그인도 안 했는데 고쳐졌다" } }

아무 표식도 없이 보낸 요청이 남의 글을 그대로 덮어썼습니다. 문은 있지만 오는 사람이 누구인지 확인하는 이가 없어, 걸어 들어온 사람은 식량 창고든 무기 창고든 마음대로 엽니다.

그림 4-2. 입구만 있고 지키는 사람이 없는 성에서는 누구나 안쪽 창고를 엽니다

방금 보낸 수정 요청이 이 성의 입구를 그냥 통과했습니다. 컨트롤러 앞에 요청을 보낸 사람을 확인하는 장치가 하나도 없어, 누가 보냈든 컨트롤러가 곧장 서비스를 호출해 글을 고칩니다.

제대로 된 성은 다르게 생겼습니다. 바깥에 성벽을 두르고, 성벽 위에는 경비를 세웁니다. 경비가 오는 사람마다 누구인지 확인합니다.

그림 4-3. 성벽과 경비가 둘러싼 성은 확인되지 않은 요청을 바깥에서 걸러 냅니다

여기서 성은 우리가 만든 서버입니다. 성벽과 경비는 서버 앞에 세울 방어에 해당합니다. 외부에서 요청이 들어오면 이 방어가 먼저 요청을 검사해서, 누가 보냈는지 확인하고 자격 없는 요청을 안쪽으로 들이지 않습니다. 이번 챕터에서 만들거나 고치는 클래스는 게시판이라는 성에 이 방어를 세우는 데 쓰입니다.

4.2 인증과 인가는 다르다

방어된 성을 다시 봅니다. 성벽 위 경비는 오는 사람마다 누구인지 확인합니다. 하지만 성 안에 들어왔다고 아무 창고나 열 수 있는 것은 아닙니다. 무기 창고 문 앞에서는 그 사람에게 열 자격이 있는지를 따로 따집니다.

앞의 확인, 요청을 보낸 사람이 누구인지 밝히는 일을 인증(Authentication) 이라고 합니다. 뒤의 확인, 그 사람이 특정 동작을 할 자격이 있는지 따지는 일을 인가(Authorization) 라고 합니다. 인증은 "너 누구야"에 답하고, 인가는 "그걸 할 권한이 있어"에 답합니다.

이 장에서 두 확인은 서로 다른 장치가 맡습니다. 신원을 밝히는 인증은 요청이 들어오는 길목에서 토큰을 확인하는 필터가 담당하고, 자격을 따지는 인가는 그 뒤에서 요청을 막아서는 인터셉터가 담당합니다. 그림 4-1에서 나란히 있던 두 상자가 각각 이 둘입니다. 두 장치가 무엇인지는 뒤에서 하나씩 만들며 확인합니다. 먼저 신원을 무엇으로 밝힐지부터 정해야 합니다.

4.3 세션 대신 왜 JWT인가

로그인을 붙이는 방법으로 먼저 떠오르는 것은 세션입니다. 서버가 로그인한 사람의 정보를 자기 안에 보관해 두고, 다음 요청이 오면 "아까 그 사람"이라고 알아보는 방식입니다. 이렇게 서버가 접속한 사람의 상태를 기억하고 있는 방식을 상태 유지(Stateful) 라고 합니다.

그런데 여기엔 걸리는 데가 있습니다. HTTP는 원래 요청 하나하나를 따로 취급합니다. 방금 로그인한 사람이 다음 요청을 보내도, 서버는 그것이 같은 사람이 보낸 것인지 알지 못합니다. 그래서 세션 방식은 서버가 로그인 정보를 자기 메모리에 쌓아 두고 사람마다 번호표를 붙여 관리해야 합니다. 접속자가 늘면 서버가 기억해야 할 것도 함께 늘고, 서버를 여러 대로 나누면 누가 어느 서버에 로그인했는지까지 맞춰야 합니다.

반대쪽 방법은 서버가 아무것도 기억하지 않는 것입니다. 로그인에 성공한 사람에게 신분을 증명하는 표를 하나 만들어 건네주고, 이후로는 그 표를 요청마다 지니고 오게 합니다. 서버는 표가 진짜인지만 확인하면 됩니다. 이렇게 서버가 상태를 기억하지 않는 방식을 무상태(Stateless) 라고 합니다.

*그림 4-4. 세션은 서버가 사람마다 상태를 기억하는 방식이고, 토큰은 본인이 신분 표를 들고 다니는 방식입니다*

이 표에 해당하는 것이 JWT(JSON Web Token) 입니다. 로그인에 성공하면 서버가 유저 정보를 담은 토큰을 만들어 건네고, 클라이언트는 이후 요청마다 그 토큰을 지니고 옵니다. 서버는 토큰이 위조되지 않았는지만 확인하면 되므로, 누가 로그인했는지 따로 기억해 둘 필요가 없습니다. 이 책의 게시판은 이 방식으로 로그인을 붙입니다.

4.4 회원 도메인과 연관관계

토큰을 발급하려면 먼저 로그인할 회원이 있어야 합니다. 게시글을 만들 때처럼 회원을 표현하는 엔티티부터 만듭니다.

user/User.java를 열고 아래 코드를 작성합니다.

설명 user/User.java. 회원 엔티티
@NoArgsConstructor @Data @Entity @Table(name = "user_tb") public class User { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Integer id; @Column(unique = true) private String username; private String password; private String email; @CreationTimestamp private Timestamp createdAt; @Builder public User(Integer id, String username, String password, String email, Timestamp createdAt) { this.id = id; this.username = username; this.password = password; this.email = email; this.createdAt = createdAt; } }

구조는 2장에서 만든 Board 엔티티와 같습니다. 눈여겨볼 곳은 username에 붙은 @Column(unique = true)입니다. 같은 유저네임이 두 번 저장되지 못하도록 데이터베이스 차원에서 막습니다. 회원을 조회할 기준이 유저네임이므로, 유일해야 로그인할 사람을 하나로 특정할 수 있습니다.

조회는 그 유저네임으로 합니다. user/UserRepository.java를 열고 아래 코드를 작성합니다.

설명 user/UserRepository.java. 유저네임으로 조회
@RequiredArgsConstructor @Repository public class UserRepository { private final EntityManager em; public void save(User user) { em.persist(user); } // 유저네임으로 한 건 조회. 없으면 빈 Optional public Optional<User> findByUsername(String username) { return em.createQuery("select u from User u where u.username = :username", User.class) .setParameter("username", username) .getResultStream().findFirst(); } }

findByUsername은 JPQL로 유저네임이 일치하는 회원을 찾아, 있으면 Optional에 담고 없으면 빈 Optional을 돌려줍니다. 3장에서 없는 글을 빈 상자로 표현한 것과 같습니다.

회원이 생기면 게시글에도 변화가 생깁니다. 이제 글마다 그것을 쓴 사람이 누구인지 붙일 수 있습니다. board/Board.java에 작성자를 가리키는 필드를 더합니다.

설명 board/Board.java. 작성자 연관관계 추가
@ManyToOne(fetch = FetchType.EAGER) @JoinColumn(name = "user_id") private User user;

여러 글이 한 작성자를 가리키므로 이 관계를 @ManyToOne으로 표시하고, @JoinColumn(name = "user_id")으로 board_tb에 작성자의 기본 키를 담을 user_id 칸을 둡니다. 이제 board.getUser()로 작성자를 꺼낼 수 있습니다. fetch = FetchType.EAGER는 게시글을 조회할 때 작성자도 함께 가져오라는 설정인데, 그 성능 문제는 다음 챕터에서 파헤칩니다.

작성자를 함께 가져오는 조회 메서드도 하나 준비합니다.

설명 board/BoardRepository.java. 작성자를 함께 가져오는 조회
public Optional<Board> findByIdJoinUser(int boardId) { return em.createQuery("select b from Board b join fetch b.user where b.id = :id", Board.class) .setParameter("id", boardId) .getResultStream().findFirst(); }

findByIdJoinUser는 게시글 한 건을 작성자와 묶어 가져옵니다. 여기서는 "작성자를 함께 가져오는 조회"라는 이름으로만 쓰고, join fetch가 왜 필요한지는 다음 챕터로 미룹니다.

작성자가 딸려 오니, 게시글 상세를 응답할 때 작성자 정보도 함께 내보낼 수 있습니다. 3장에서 만든 상세 그릇 BoardResponse.DetailDTO에 작성자의 아이디(userId)와 유저네임(username) 두 항목을 더합니다. 비밀번호처럼 보여선 안 되는 값은 응답에 담지 않으므로, 유저네임과 아이디만 나갑니다.

{ "status": 200, "msg": "성공", "body": { "boardId": 1, "title": "title1", "content": "content1", "userId": 1, "username": "ssar" } }

4.5 회원가입과 로그인

회원 도메인이 준비됐으니, 실제로 가입하고 로그인하는 부분을 만듭니다. 먼저 가입과 로그인 요청을 담을 그릇을 정합니다. user/UserRequest.java를 열고 아래 코드를 작성합니다.

설명 user/UserRequest.java. 회원가입·로그인 요청 DTO
public class UserRequest { public record SaveDTO( @NotEmpty(message = "유저네임을 입력해주세요") @Size(min = 2, max = 20, message = "유저네임은 2자 이상 20자 이하로 입력해주세요") String username, @NotEmpty(message = "비밀번호를 입력해주세요") String password, @Email(message = "이메일 형식이 올바르지 않습니다") String email) { // 요청 값으로 엔티티를 만든다 public User toEntity() { return User.builder().username(username).password(password).email(email).build(); } } public record LoginDTO( @NotEmpty(message = "유저네임을 입력해주세요") String username, @NotEmpty(message = "비밀번호를 입력해주세요") String password) { } }

SaveDTO는 가입할 때, LoginDTO는 로그인할 때 받을 값을 담습니다. 필드마다 붙은 @NotEmpty, @Size, @Email은 값이 조건에 맞는지 검사하는 표식입니다. 유저네임은 비어 있으면 안 되고 길이는 2자에서 20자 사이여야 하며, 이메일은 형식이 맞아야 한다는 규칙을 값 옆에 적어 둔 것입니다. 이 표식이 실제로 언제 검사되고 어긋나면 어떤 응답이 나가는지는 4.9에서 다룹니다. 지금은 요청 값에 지켜야 할 규칙을 달아 둔다는 정도로 넘어갑니다.

실무에서는 비밀번호를 반드시 암호화합니다

비밀번호를 입력받은 그대로 저장하면 데이터베이스를 들여다보는 누구든 남의 비밀번호를 읽을 수 있습니다. 그래서 실무에서는 되돌릴 수 없는 해시로 바꿔 저장합니다. 이 책은 인증 흐름에 집중하려고 비밀번호를 평문으로 다룹니다.

이제 회원가입과 로그인을 서비스에 담습니다. user/UserService.java를 열고 TODO의 pass를 지우고 아래 코드를 작성합니다.

실습 1 user/UserService.java. 회원가입과 로그인
@RequiredArgsConstructor @Service public class UserService { private final UserRepository userRepository; // 1. 회원가입. 유저네임 중복을 막고 저장한다 @Transactional public void 회원가입(UserRequest.SaveDTO requestDTO) { // TODO: 중복 확인 → 저장 if (userRepository.findByUsername(requestDTO.username()).isPresent()) { throw new Exception400("이미 존재하는 유저네임입니다"); } userRepository.save(requestDTO.toEntity()); } // 2. 로그인. 비밀번호가 맞으면 JWT를 발급한다 public String 로그인(UserRequest.LoginDTO requestDTO) { // TODO: 조회 → 비밀번호 확인 → 토큰 발급 User user = userRepository.findByUsername(requestDTO.username()) .orElseThrow(() -> new Exception401("유저네임 또는 비밀번호가 일치하지 않습니다")); if (!user.getPassword().equals(requestDTO.password())) { throw new Exception401("유저네임 또는 비밀번호가 일치하지 않습니다"); } return JwtUtil.create(user); } }

회원가입은 먼저 같은 유저네임이 이미 있는지 확인합니다. findByUsername이 회원을 담아 오면 이미 쓰이는 이름이므로 잘못된 요청으로 보고 Exception400을 던져 가입을 막습니다. Exception400은 3장의 Exception404처럼 RuntimeException을 상속한 한 줄짜리 예외이고, 뒤에서 400 응답으로 바뀝니다. 같은 이름을 쓰는 회원이 없으면 toEntity로 요청 값을 엔티티에 담아 저장합니다.

로그인은 반대 순서입니다. 유저네임으로 회원을 찾고, 입력한 비밀번호를 저장된 비밀번호와 대조합니다. 유저네임이 없든 비밀번호가 틀리든 같은 메시지로 답해, 어떤 유저네임이 있는지 밖으로 드러나지 않게 합니다. 맞으면 JwtUtil.create로 토큰을 만들어 돌려줍니다. 토큰 내부는 다음 절 4.6에서 만듭니다.

두 서비스를 바깥과 잇는 컨트롤러를 만듭니다. user/UserController.java를 열고 TODO의 pass를 지우고 아래 코드를 작성합니다.

실습 2 user/UserController.java. 회원가입·로그인 엔드포인트
@RequiredArgsConstructor @RestController public class UserController { private final UserService userService; // 1. 회원가입 (POST /join) @PostMapping("/join") public ResponseEntity<?> join(@Valid @RequestBody UserRequest.SaveDTO requestDTO) { userService.회원가입(requestDTO); return Resp.ok(null); } // 2. 로그인 (POST /login) → JWT 발급 @PostMapping("/login") public ResponseEntity<?> login(@Valid @RequestBody UserRequest.LoginDTO requestDTO) { String accessToken = userService.로그인(requestDTO); return Resp.ok(accessToken); } }

/join은 가입 요청을 받아 서비스로 넘기고, 저장만 하면 되므로 Resp.ok(null)로 성공만 알립니다. /login은 서비스가 돌려준 토큰 문자열을 그대로 응답 바디에 담아 내보냅니다. 클라이언트는 이 토큰을 받아 두었다가 이후 요청마다 지니고 옵니다. @RequestBody 앞에 붙은 @Valid는 앞에서 DTO에 달아 둔 검증 표식을 실제로 검사하라는 신호인데, 이 부분도 4.9에서 이어서 다룹니다.

4.6 JWT 구조와 검증

로그인이 만들어 건네는 토큰이 어떻게 생겼는지 볼 차례입니다. JWT는 점(.) 두 개로 나뉜 세 조각으로 이루어집니다. 각 조각이 맡은 역할이 다릅니다.

그림 4-5. JWT는 헤더, 페이로드, 서명 세 조각으로 이루어지며 점으로 이어져 한 줄이 됩니다

세 조각 중 페이로드에 담긴 정보는 누구든 열어 볼 수 있습니다. 그래서 비밀번호처럼 감춰야 할 값은 넣지 않고, 누구인지 알려 줄 정도의 값만 담습니다. 위조를 막는 것은 마지막 서명 조각입니다. 서명은 서버만 아는 비밀 문자열로 만들어지므로, 페이로드를 몰래 고치면 서명이 맞지 않게 되어 검증에서 걸립니다. 그래서 서버는 토큰을 기억해 두지 않고도, 들어온 토큰의 서명만 확인해 위조 여부를 가려낼 수 있습니다.

토큰을 만들고 확인하는 코드에는 상수가 여럿 등장합니다. 먼저 그 뜻을 정리합니다.

상수 값 역할
HEADER "Authorization" 토큰을 실어 보내는 요청 헤더의 이름
TOKEN_PREFIX "Bearer " 토큰 앞에 붙이는 표식
SECRET 서버만 아는 비밀 문자열 서명하고 검증할 때 쓰는 열쇠
EXPIRATION_TIME 7일 토큰이 유효한 기간

core/util/JwtUtil.java를 열고 TODO의 pass를 지우고 아래 코드를 작성합니다. 위 상수 네 개는 클래스 맨 위에 필드로 선언되어 있고, 아래 두 메서드가 그 값을 씁니다.

실습 3 core/util/JwtUtil.java. JWT 발급과 검증
// 1. 유저 정보를 담아 토큰을 만든다 public static String create(User user) { String jwt = JWT.create() .withSubject(user.getUsername()) .withExpiresAt(new Date(System.currentTimeMillis() + EXPIRATION_TIME)) .withClaim("id", user.getId()) .sign(Algorithm.HMAC512(SECRET)); return TOKEN_PREFIX + jwt; } // 2. 서명을 확인하고 담긴 정보로 User를 복원한다 public static User verify(String jwt) { DecodedJWT decodedJWT = JWT.require(Algorithm.HMAC512(SECRET)).build().verify(jwt); Integer userId = decodedJWT.getClaim("id").asInt(); String username = decodedJWT.getSubject(); return User.builder().id(userId).username(username).build(); }

create는 그림의 세 조각을 채웁니다. 페이로드에 유저네임·아이디·만료 시각을 담고, SECRET으로 서명 조각을 만듭니다. 완성된 토큰 앞의 Bearer 표식은 "이 뒤에 오는 값이 토큰이다"라고 알리는 관례입니다. 토큰에 담긴 값 하나하나를 클레임(Claim) 이라고 하며, id는 그중 하나입니다.

verify는 반대 방향입니다. 서명을 확인해 같은 SECRET으로 만든 진짜 토큰인지 가려내고, 맞지 않으면 예외가 납니다. 통과하면 페이로드의 값으로 User 객체를 되살립니다. 토큰 하나가 로그인한 사람의 신원으로 복원되는 것입니다.

JwtUtil이 토큰을 만들고 여는 도구라면, 그 도구를 요청에 연결하는 코드가 하나 더 필요합니다. 요청 헤더에서 토큰을 꺼내고, 꺼낸 토큰을 verify에 넘겨 유저를 복원하는 일입니다. core/util/JwtProvider.java를 열고 TODO의 pass를 지우고 아래 코드를 작성합니다.

실습 4 core/util/JwtProvider.java. 토큰 추출과 유저 복원
@Component public class JwtProvider { // 1. 헤더에서 "Bearer " 접두어를 떼고 토큰만 꺼낸다 public String resolveToken(HttpServletRequest request) { String bearerToken = request.getHeader(JwtUtil.HEADER); if (bearerToken != null && bearerToken.startsWith(JwtUtil.TOKEN_PREFIX)) { return bearerToken.replace(JwtUtil.TOKEN_PREFIX, ""); } return null; } // 2. 토큰이 유효하면 User, 아니면 null public User getUser(String token) { try { return JwtUtil.verify(token); } catch (Exception e) { return null; } } }

resolveToken은 헤더에서 Bearer 표식을 떼고 토큰만 꺼내며, 없으면 null을 돌려줍니다. getUser는 그 토큰을 verify에 넘겨 유효하면 유저를, 어긋나면 null을 돌려줍니다. 진위 판단을 "유저 아니면 null"로 감싼 것으로, 다음 절의 필터가 그대로 씁니다.

4.7 인증을 맡는 필터

이제 요청이 들어오는 길목에 인증을 놓습니다. 앞서 정문에 비유한 그 확인입니다. 요청마다 헤더의 토큰을 확인해, 유효하면 그 신원을 요청에 붙여 두는 일입니다.

이 일을 맡는 것이 필터(Filter) 입니다. 필터는 요청이 컨트롤러에 도달하기 전에 먼저 거쳐 가는 길목의 검문소입니다. 스프링에서는 OncePerRequestFilter를 상속해, 요청 한 건마다 한 번씩 실행되는 필터를 만듭니다.

core/filter/JwtAuthenticationFilter.java를 열고 TODO의 pass를 지우고 아래 코드를 작성합니다.

실습 5 core/filter/JwtAuthenticationFilter.java. 인증 필터
@RequiredArgsConstructor @Component public class JwtAuthenticationFilter extends OncePerRequestFilter { public static final String SESSION_USER = "sessionUser"; private final JwtProvider jwtProvider; @Override protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) throws ServletException, IOException { // 1. 헤더에서 토큰을 꺼낸다 String token = jwtProvider.resolveToken(request); // 2. 유효하면 신원을 요청에 심어 둔다 (막지는 않는다) if (token != null) { User sessionUser = jwtProvider.getUser(token); if (sessionUser != null) { request.setAttribute(SESSION_USER, sessionUser); } } filterChain.doFilter(request, response); } }

필터가 하는 일은 신원을 밝혀 붙여 두는 것까지입니다. 토큰을 꺼내 유저로 복원하면, request.setAttribute로 그 유저를 요청에 sessionUser라는 이름표로 심어 둡니다. 뒤에 오는 컨트롤러나 인터셉터가 이 이름표로 "이 요청을 보낸 사람"을 알 수 있습니다.

여기서 중요한 것은 마지막 줄입니다. 토큰이 없거나 틀려도 필터는 요청을 막지 않고 filterChain.doFilter로 그대로 통과시킵니다. 정문에서 사원증을 확인해 "이 사람이 누구다"까지만 밝히고, 어느 방에 들어갈 수 있는지는 따지지 않는 것과 같습니다. 신원이 확인되면 이름표가 붙고, 안 되면 이름표 없이 지나갑니다. 막는 일은 인증이 아니라 인가의 몫이라, 다음 문에서 처리합니다.

4.8 인가를 맡는 인터셉터

필터가 이름표를 붙여 통과시켰으니, 이제 그 이름표를 보고 요청을 막을지 말지 결정하는 문을 세울 차례입니다. 앞서 서버실 문에 비유한 인가입니다.

이 문을 맡는 것이 인터셉터(Interceptor) 입니다. 인터셉터는 필터를 지난 요청이 컨트롤러에 도달하기 직전에 한 번 더 가로채는 장치입니다. preHandle 메서드가 true를 돌려주면 요청이 컨트롤러로 넘어가고, 예외를 던지면 그 자리에서 막힙니다.

core/interceptor/AuthInterceptor.java를 열고 TODO의 pass를 지우고 아래 코드를 작성합니다.

실습 6 core/interceptor/AuthInterceptor.java. 인가 인터셉터
public class AuthInterceptor implements HandlerInterceptor { @Override public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) { String method = request.getMethod(); // 1. 읽기(GET)와 사전 요청(OPTIONS)은 통과시킨다 if ("GET".equalsIgnoreCase(method) || "OPTIONS".equalsIgnoreCase(method)) { return true; } // 2. 쓰기 요청은 신원이 심어져 있어야 통과 User sessionUser = (User) request.getAttribute("sessionUser"); if (sessionUser == null) { throw new Exception401("로그인이 필요합니다"); } return true; } }

인터셉터는 요청의 방식을 먼저 봅니다. 목록과 상세를 조회하는 GET은 로그인 없이도 열려 있어야 하므로 그대로 통과시킵니다. OPTIONS도 통과시키는데, 이는 브라우저가 본 요청을 보내기 전에 미리 확인차 던지는 요청이라 막으면 안 됩니다.

글을 쓰거나 고치거나 지우는 요청에서만 문이 닫힙니다. 필터가 심어 둔 sessionUser가 없으면 로그인하지 않은 요청이므로 Exception401을 던져 막고, 있으면 통과시킵니다. 던져진 예외가 어떤 응답이 되는지는 4.9에서 잇습니다.

만든 인터셉터는 스프링에 등록해야 동작합니다. 이 등록은 참고 코드 core/config/WebMvcConfig.java가 맡습니다. AuthInterceptor를 게시글 주소(/api/boards와 그 하위 경로)에만 세워, 로그인과 회원가입 주소에는 문을 두지 않습니다. 그래서 로그인하지 않은 사람도 가입하고 로그인할 수 있습니다. 같은 설정에서 CORS도 한 줄로 열어 두는데, 이는 화면과 서버가 서로 다른 주소에서 돌아갈 때 브라우저가 요청을 막지 않게 하는 설정으로, 자세한 내용은 이 책의 범위를 벗어나므로 짚고만 넘어갑니다.

필터가 @Component로 자동 등록되고 인터셉터가 이 설정으로 등록되면, 두 문이 요청 하나를 차례로 거릅니다. 요청은 필터에서 신원이 심기고, 인터셉터에서 쓰기 여부에 따라 걸러진 뒤, 컨트롤러로 전달됩니다.

그림 4-6. 필터는 신원을 심고 통과시키며, 인터셉터는 쓰기 요청에서 신원을 확인해 없으면 막습니다

4.9 소유자 검증과 검증 실패

필터와 인터셉터로 두 문을 세웠지만, 문제의 절반은 아직 남아 있습니다. 로그인한 사람이 남의 글에 수정을 보내도 응답은 그대로 200입니다. 인터셉터는 로그인을 했는지만 확인하기 때문에, 남의 글을 고치려는 요청도 일단 통과시킵니다. 그래서 이 글을 쓴 본인이 맞는지를 글마다 한 번 더 확인해야 합니다.

이 확인은 인터셉터가 아니라 서비스에서 합니다. 어느 글의 작성자인지는 글을 불러와 봐야 알 수 있기 때문입니다. 확인 코드를 짜기 전에, 던질 예외 두 개를 먼저 만듭니다. Exception401은 로그인이 필요한데 하지 않은 경우에, Exception403은 로그인은 했지만 권한이 없는 경우에 던집니다. 둘 다 3장에서 만든 Exception404와 구조가 같습니다. RuntimeException을 상속한 한 줄짜리 예외입니다. 3.4의 상태 코드 표에서 미뤄 뒀던 401과 403을 여기서 씁니다.

이제 서비스가 소유자를 확인합니다. board/BoardService.java의 수정 메서드를 아래처럼 고칩니다.

설명 board/BoardService.java. 소유자 검증
@Transactional public BoardResponse.DTO 게시글수정(Integer boardId, BoardRequest.UpdateDTO requestDTO, Integer sessionUserId) { Board board = boardRepository.findByIdJoinUser(boardId) .orElseThrow(() -> new Exception404("게시글을 찾을 수 없습니다")); // 작성자 본인이 아니면 막는다 if (!board.getUser().getId().equals(sessionUserId)) { throw new Exception403("게시글을 수정할 권한이 없습니다"); } board.setTitle(requestDTO.title()); board.setContent(requestDTO.content()); return new BoardResponse.DTO(board); }

수정 메서드가 로그인한 사람의 아이디 sessionUserId를 하나 더 받습니다. findByIdJoinUser로 글을 작성자와 함께 불러와, 글의 작성자와 요청자의 아이디가 다르면 남의 글이므로 Exception403을 던지고, 같을 때만 제목과 내용을 바꿉니다. 저장 코드는 없지만 2장의 더티 체킹이 변경을 반영합니다. 삭제도 같은 방식으로 작성자를 확인한 뒤 지웁니다.

글을 새로 쓰는 게시글추가는 주인을 확인할 필요가 없습니다. 아직 주인이 없는 새 글이니까요. 대신 로그인한 사람을 이 글의 작성자로 정해서 저장합니다. 그래서 BoardRequest의 toEntity가 작성자를 받도록 바뀝니다.

설명 board/BoardRequest.java. 작성자를 연결하는 toEntity
public Board toEntity(User user) { return Board.builder().title(title).content(content).user(user).build(); }

3장에서는 toEntity가 제목과 내용만 담았습니다. 이제 여기에 로그인한 사람까지 넘겨서, 글을 만들 때 작성자도 함께 담습니다. 그래서 글을 저장할 때 그 글을 누가 썼는지도 같이 저장됩니다.

그럼 이 로그인한 사람은 어디서 올까요? 앞에서 필터가 토큰을 확인하고, sessionUser라는 이름으로 유저를 넣어 뒀습니다. 컨트롤러는 그 유저를 request.getAttribute("sessionUser")로 꺼냅니다. 작성은 유저를 그대로, 수정과 삭제는 유저의 아이디만 서비스에 넘깁니다. 쓰기 요청은 이미 인터셉터를 통과했으니, 유저는 반드시 들어 있습니다. 목록과 상세는 로그인이 필요 없으므로 앞 챕터 그대로 둡니다. 쓰기 메서드는 아래처럼 바뀝니다.

설명 board/BoardController.java. 쓰기 요청에서 로그인 유저 꺼내기
// 게시글 쓰기 — 로그인 유저를 작성자로 넘긴다 @PostMapping public ResponseEntity<?> save(HttpServletRequest request, @Valid @RequestBody BoardRequest.SaveDTO requestDTO) { User sessionUser = (User) request.getAttribute("sessionUser"); BoardResponse.DTO respDTO = boardService.게시글추가(requestDTO, sessionUser); return Resp.ok(respDTO); } // 게시글 수정 — 유저 아이디를 소유자 검증에 넘긴다 (삭제도 같은 방식) @PutMapping("/{boardId}") public ResponseEntity<?> update(HttpServletRequest request, @PathVariable("boardId") Integer boardId, @Valid @RequestBody BoardRequest.UpdateDTO requestDTO) { User sessionUser = (User) request.getAttribute("sessionUser"); BoardResponse.DTO respDTO = boardService.게시글수정(boardId, requestDTO, sessionUser.getId()); return Resp.ok(respDTO); }

이제 남은 것은 잘못된 입력을 걸러내는 검증입니다. 4.5에서 DTO에 @NotEmpty, @Size를 달아 뒀습니다. 컨트롤러에 @Valid를 붙이면 요청이 들어올 때 이 조건들을 실제로 검사합니다. 제목 없이 글을 쓰려고 하면 이 검사에 걸려서 MethodArgumentNotValidException 예외가 발생합니다. 이 예외와 방금 만든 401·403, 그리고 회원가입에서 던진 400을 알맞은 응답으로 바꾸도록, 3장에서 만든 전역 예외 창구에 핸들러를 추가합니다.

설명 core/handler/GlobalExceptionHandler.java. 401·403·400 핸들러 추가
@ExceptionHandler(Exception400.class) public ResponseEntity<?> ex400(Exception400 e) { return Resp.fail(HttpStatus.BAD_REQUEST, e.getMessage()); } @ExceptionHandler(Exception401.class) public ResponseEntity<?> ex401(Exception401 e) { return Resp.fail(HttpStatus.UNAUTHORIZED, e.getMessage()); } @ExceptionHandler(Exception403.class) public ResponseEntity<?> ex403(Exception403 e) { return Resp.fail(HttpStatus.FORBIDDEN, e.getMessage()); } // @Valid 검증 실패를 400으로 모은다 @ExceptionHandler(MethodArgumentNotValidException.class) public ResponseEntity<?> exValid(MethodArgumentNotValidException e) { String msg = e.getBindingResult().getFieldErrors().stream() .map(fe -> fe.getField() + ":" + fe.getDefaultMessage()) .collect(Collectors.joining(", ")); return Resp.fail(HttpStatus.BAD_REQUEST, msg); }

이제 잘못된 요청(400), 401, 403이 모두 이 창구 한 곳에서 응답으로 바뀝니다.

이제 처음 문제로 돌아가 확인합니다. 로그인하면 Bearer 로 시작하는 토큰을 받습니다. 이 토큰을 Authorization 헤더에 실어서 남의 글에 수정 요청을 보내면, 4.1에서는 그냥 통과하던 요청이 이번에는 403으로 막힙니다.

그림 4-7. 로그인하면 토큰이 발급되고, 남의 글을 수정하려 하면 403으로 막힙니다

로그인하지 않고 보낸 쓰기 요청은 인터셉터에서 401로 막히고, 로그인은 했지만 남의 글을 건드리는 요청은 서비스에서 403으로 막힙니다. 제목 없이 보낸 요청은 검증에서 400으로 걸러집니다. 4.1에서 활짝 열려 있던 게시판에, 이제 신원을 밝히는 문과 자격을 따지는 문이 차례로 섰습니다.

오픈이는 자기 계정으로 로그인한 뒤, 남의 글에 다시 수정을 보냈습니다.

이번엔 막히겠지.

응답 창에 403이 떴습니다. 게시글을 수정할 권한이 없다는 메시지도 함께였습니다. 로그인하지 않은 쓰기는 401에서, 남의 글은 403에서, 각각 다른 문에 걸려 멈췄습니다. 오픈이는 목록 화면을 붙이던 동료를 불렀습니다.

오픈이: "이제 로그인 안 하면 글이 안 써지고, 로그인해도 남의 글은 못 고쳐요."
동료: "아, 제 계정으로는 제 글만 지워지네요. 아까는 아무 글이나 다 지워졌는데요."

문만 있고 지키는 사람은 없던 성에, 신원을 밝히는 경비와 자격을 따지는 문지기가 나란히 섰습니다.

4.10 이것만은 기억하자

이것만은 기억하자

  • 인증은 "너 누구야"를 밝히고, 인가는 "그걸 할 권한이 있어"를 따집니다. 이 장에서 인증은 토큰을 확인해 신원을 심는 필터가, 인가는 쓰기 요청을 막는 인터셉터가 맡습니다.
  • 로그인에 성공하면 JWT를 발급하고, 클라이언트는 그 토큰을 요청마다 지니고 옵니다. 서버는 토큰의 서명만 검증하면 되므로 로그인 상태를 따로 기억하지 않습니다. 남의 글을 고치려는 요청은 서비스의 소유자 검증에서 403으로 막힙니다.
  • 그런데 이 게시판에는 아직 글만 있고 댓글이 없습니다. 다음 챕터에서는 글에 댓글을 달고, 댓글이 글에 딸리는 연관관계를 만들다 조회 성능 문제와 마주칩니다.
