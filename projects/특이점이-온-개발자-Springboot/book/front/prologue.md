# 프롤로그

## 서버 뼈대에 막히다

오픈이는 이제 막 자바(Java)를 배우기 시작한 학생입니다. 이번 학기 과제인 **게시판 웹 서버**를 만들기 위해 호기롭게 키보드에 손을 올렸지만, 몇 줄 쓰지도 못하고 벽에 부딪혔습니다.

문제는 게시판 기능 그 이전 단계에 있었습니다. 웹 서버를 처음부터 직접 만들려다 보니 외부와 통신하는 작업부터, 들어온 요청의 주소를 해석해 알맞은 코드로 연결하는 과정까지 전부 스스로 구현해야 했습니다. 중요한 게시글 기능은 시작도 못했는데, 서버 뼈대를 만들기 위한 작업만 산더미같이 쌓여 있었습니다.

*이거 뼈대만 만들다가 과제는 손도 못 대겠는데...*

다음 날, 오픈이는 같은 수업을 듣는 선배에게 고민을 털어놓았습니다. 선배는 오픈이가 지금까지 쓴 코드를 훑어보더니 말했습니다.

**선배**: "이런 걸 처음부터 직접 다 만드는 사람은 없어요. **웹 서버에 공통으로 필요한 뼈대는 프레임워크에 이미 다 갖춰져 있거든요**. 자바로 웹 서버를 만들면 보통 **스프링(Spring)** 을 써요. 스프링으로 시작해서 게시판 기능만 구현해 봐요."

선배의 말을 들은 오픈이는 스프링에 대해 알아보기로 했습니다. 스프링은 자바를 기반으로 복잡한 애플리케이션을 쉽게 만들 수 있도록 돕는 프레임워크로, 외부 요청을 처리하는 서버의 기본 뼈대를 이미 갖추고 있습니다. 따라서 개발자가 모든 흐름을 직접 통제할 필요가 없습니다. 클래스와 메서드에 약속된 표식만 붙여 두면, 요청이 들어왔을 때 **스프링이 표식을 읽어 알맞은 코드를 찾아 실행합니다**.

개발자가 메서드를 직접 호출하던 방식과 달리, 프레임워크가 개발자의 코드를 호출하도록 흐름이 뒤집힌 이 원리를 **제어의 역전(IoC)** 이라고 합니다. 서버 뼈대를 만드는 일을 스프링에 위임하고 나니, 오픈이는 핵심인 게시판 기능에만 온전히 집중할 수 있게 되었습니다.

## 게시판을 완성하다

다음 날 저녁, 오픈이는 노트북을 열고 스프링으로 새 프로젝트를 만들어 보기로 했습니다. 스프링이 표식을 읽어 알맞은 코드를 찾아 실행한다는 원리까지는 이해했습니다.

이제 남은 건 그 원리 위에서 직접 기능을 만드는 일이었습니다. 첫 번째 목표는 게시판이었습니다.

**스프링으로 게시판의 기본 기능을 만들어 보자.**

오픈이는 게시판 서버를 완성된 화면 없이 순수 데이터만 주고받는 **API 서버** 형태로 만들기로 했습니다. 일반적인 웹사이트는 서버가 화면을 완성해 전달합니다. 반면 API 서버는 데이터만 응답하며, 브라우저나 휴대폰 같은 디바이스에서 이 데이터를 처리합니다. 서버는 화면과 상관없이 데이터만 응답하기 때문에, 브라우저와 휴대폰처럼 서로 다른 디바이스도 하나의 서버를 함께 사용할 수 있습니다. 오픈이는 API 서버를 만드는 방식 중 현재 가장 널리 쓰이는 **REST API**를 선택했습니다.

그다음 게시글을 데이터베이스에 저장하기 위해 테이블을 설계했습니다. 그런데 스프링은 데이터를 자바 객체로 다루고, 객체와 테이블은 구조가 다릅니다. 그래서 **객체의 값을 테이블에 옮겨 담으려면 매핑 작업이 필요합니다**. 이 과정을 쉽게 처리하기 위해 스프링에서는 **JPA**라는 기술을 사용합니다. JPA는 이 매핑 정보를 바탕으로 저장과 조회에 필요한 SQL을 생성합니다.

JPA는 **영속성 컨텍스트**라는 공간을 통해 객체를 관리합니다. 영속성 컨텍스트는 **애플리케이션과 데이터베이스 사이에서 객체를 보관하고, 객체에 생긴 변경을 모아 데이터베이스에 반영합니다**.

오픈이는 스프링과 JPA를 활용해 게시판의 기본 기능을 구현해 냈습니다. 학기 과제로 기획했던 게시판이 첫 동작을 시작한 순간이었습니다.

## 예외처리를 하다

게시판 기본 기능을 완성한 오픈이는 다음 날 뿌듯한 마음으로 선배에게 결과물을 보여주었습니다. 선배는 게시글 목록과 상세 조회 기능을 차례로 확인하더니, 이번에는 게시글 번호를 999로 바꿔 다시 조회했습니다. 그러자 상태 코드는 여전히 200(성공)을 반환했지만, 정작 응답 바디는 텅 비어 있었습니다.

*데이터베이스에 없는 게시글인데 오류가 나지 않고 왜 성공으로 응답하지?*

**선배**: "데이터베이스에서 조회된 게시글이 없으면 null 값을 응답하는데, 이 null 값을 서버에서 처리하지 않고 응답하니까 사용자는 정상적인 응답을 받게 될 거예요. 만약 이 상태에서 오류가 발생하면, 사용자는 자신의 문제인지 서버의 문제인지 원인을 알 수 없는 오류를 보게 되겠죠. 그래서 서버에서는 이런 **예외(Exception)가 발생했을 경우를 위해 미리 예외 처리를 해야 해요**. 그래야 어떤 사유로 요청이 실패했는지 클라이언트에게 명확히 알려줄 수 있어요."

선배가 말을 이어갔습니다.

**선배**: "그리고 지금은 서버가 객체를 그대로 응답하는 구조라서 사용자에게 불필요한 정보도 있고, 보안에도 취약해요. 그래서 **DTO라는 데이터 전송을 위한 객체**를 만들고, 이 DTO 타입으로 요청과 응답을 보내야 해요."

조언을 들은 오픈이는 예외 처리에 대해 알아보았습니다. **예외 처리란 정상적인 흐름을 이어갈 수 없는 상황이 발생했을 때, 프로그램이 멈추는 대신 오류의 원인을 사용자에게 안내하는 역할을 합니다**. 오픈이는 학습한 내용을 바탕으로 프로젝트의 구조를 수정하기 시작했습니다. 먼저 예외가 발생했을 때 한 곳에서 처리할 수 있도록 전역 예외 처리기를 추가했습니다. 그리고 DTO를 만들어 사용자에게 필요한 정보만 응답할 수 있도록 구조를 변경했습니다.

이제 오픈이의 서버는 오류가 발생하면 미리 정해 둔 상태 코드와 오류 메시지를 사용자에게 돌려줍니다.

## 요청한 사람을 식별하다

지금까지 오픈이가 구현한 게시글 기능은 누가 작성했는지 알 수 없는 익명 게시글이었습니다. 인증 기능을 추가하기 위해 공부하던 오픈이는 로그인 상태를 관리하는 방식이 크게 두 가지라는 것을 알게 되었습니다. 하나는 서버가 사용자의 로그인 정보를 저장하는 **상태 유지(Stateful)** 방식이고, 다른 하나는 로그인 정보를 저장하지 않는 **무상태(Stateless)** 방식입니다.

*둘 중에 어떤 방식으로 인증을 만들어야 하지?*

오픈이는 선배에게 어떤 방식을 선택하는 것이 좋을지 물어보았습니다.

**선배**: "상태 유지 방식은 서버가 로그인 정보를 직접 관리하니까, 필요할 때 특정 사용자를 바로 로그아웃시키는 것처럼 통제하기 쉬워요. 대신 **사용자가 늘어날수록 서버가 기억해야 할 데이터도 많아져서 부담이 커지고**, 서버가 여러 대가 되면 그 정보를 서로 공유해야 하는 문제가 생겨요."

**선배**: "반면 무상태 방식은 **서버가 로그인 정보를 기억할 필요가 없어서 사용자가 늘어나도 부담이 크지 않고**, 서버가 몇 대든 요청만 검증하면 돼요. 대신 한 번 발급한 인증 정보는 만료되기 전까지 서버가 중간에 무효로 만들기 어렵다는 단점이 있어요. 지금 만드는 REST API 방식에는 무상태 방식이 더 적합할 것 같아요. **JWT**라는 토큰을 사용하면 무상태 방식으로 인증을 할 수 있어요."

선배의 조언을 들은 오픈이는 JWT에 대해 알아보았습니다. **JWT는 사용자 인증 정보를 자체적으로 담고 있는 토큰입니다**. 그래서 서버는 로그인 상태를 따로 기억하지 않아도, 요청에 포함된 JWT만으로 사용자를 확인할 수 있습니다. 오픈이는 이 방식을 적용해 **사용자 인증 기능**과 **게시글 권한 처리 기능**까지 구현했습니다.

## 게시글과 댓글을 연결하다

마지막 관문은 댓글 기능이었습니다. 댓글을 저장하는 기능까지는 금방 만들었지만, 게시글을 조회하는 코드 앞에서 손이 멈췄습니다. 게시글에는 작성자가 있고, 댓글이 여러 개 달리고, 댓글마다 또 작성자가 있었습니다.

*게시글 하나 가져오는데 작성자, 댓글, 댓글 작성자까지 다 따로 조회해야 하나?*

머리를 쥐어뜯는 오픈이에게 선배가 마지막 힌트를 던졌습니다.

**선배**: "자바 객체는 기본적으로 일방통행이지만, 양방향 매핑을 쓰면 반대쪽에서도 참조할 수 있게 길을 뚫을 수 있어요. 그러면 조인을 통해서 한 번에 필요한 데이터를 싹 쓸어올 수 있죠."

선배의 말대로 게시글에서 댓글로 가는 길을 열어 주자, 게시글과 댓글, 작성자 정보가 쿼리 한 번에 묶여 나왔습니다.

학기 초, 주소를 어떻게 나눠야 할지 몰라 깜빡이는 커서만 보며 한숨짓던 과제가 어느새 인증과 댓글까지 오가는 번듯한 게시판으로 거듭나 있었습니다. 백엔드 세계에 첫발을 내디딘 오픈이의 서버 개발은 이제부터가 시작입니다.
