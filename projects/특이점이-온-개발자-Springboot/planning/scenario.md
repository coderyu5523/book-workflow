# 시나리오 + 버전 설계

## 시나리오

### 한 줄 요약

오픈이가 팀 과제로 게시판 백엔드를 맡아, "스프링이 어떻게 저절로 동작하는가"라는 의문에서 출발해 게시판 하나를 인증·성능까지 챙겨 완성하는 여정.

### 관통 비유

책 전체를 관통하는 단일 비유는 쓰지 않는다. 비유는 각 챕터에서 필요한 대목에만 국소적으로 쓴다(집필 STEP 5에서 챕터별 결정). 책의 뼈대는 비유가 아니라 아래 **챕터 간 스토리 아크**다.

### 전체 흐름 (챕터 스토리 아크)

각 챕터 끝의 "그런데…"가 다음 챕터의 필요를 만든다. 코드의 실제 성장 순서(spring-ch01~05)와 일치한다.

**출발** — 오픈이가 팀 과제로 게시판 백엔드를 맡는다. 스프링 프로젝트를 처음 열었는데, 자기가 짠 코드가 어떻게 저절로 실행되는지부터 막힌다.

1. **CH1 리플렉션** — "스프링은 어떻게 내 코드를 알아서 찾아 실행하지?"
   프레임워크의 정의(제어의 역전: 내가 프레임워크를 부르는 게 아니라 프레임워크가 내 코드를 부른다)에서 출발해, 스프링을 걷어내고 순수 자바로 그 원리(리플렉션)를 직접 재현한다.
   → "스프링은 마법이 아니라 리플렉션 위의 규칙"임을 알게 됨. 이제 마음 놓고 만들 수 있다.

2. **CH2 게시판 CRUD** — 원리를 알았으니 진짜로 만든다.
   `@RestController`, JPA(`EntityManager`), 더티체킹으로 글 저장·조회·수정·삭제.
   → 동작하는 게시판 API. 그런데 없는 글을 조회하면 터지고, 내부 엔티티가 응답으로 그대로 샌다.

3. **CH3 예외처리 + DTO** — CH2의 구멍을 막는다.
   응답 DTO 분리 + `Optional`·`orElseThrow` + 전역 예외처리(`@RestControllerAdvice`).
   → 견고한 응답·에러 구조. 그런데 아무나 남의 글을 수정·삭제할 수 있다.

4. **CH4 인증/인가** — 게시판이 완전히 공개다. 로그인도, 주인 확인도 없다.
   회원가입·로그인(JWT), 필터=인증(통행증 확인), 인터셉터=인가(권한 확인), 소유자 검증.
   → 로그인한 본인만 자기 글을 건드린다. 이제 글에 댓글을 달고 싶다.

5. **CH5 댓글 + JPA 심화** — 댓글은 글에 딸린다 → 연관관계가 필요.
   `@OneToMany` 연관관계, 그러다 목록 조회에서 N+1 문제를 만나 `fetch join`으로 해결.
   → 댓글까지 되는 완성 게시판 + JPA 성능까지 이해한 오픈이.

**도착** — 처음엔 자기 코드가 어떻게 실행되는지도 몰랐던 오픈이가, 프레임워크의 정체를 알고 게시판 하나를 인증·성능까지 챙겨 완성한다.

### CH1 세부 구조 (진입 챕터라 별도 정리)

1. **프레임워크란 무엇인가** — 라이브러리는 내가 갖다 쓴다. 프레임워크는 반대로 내 코드를 대신 불러준다(제어의 역전, "Don't call us, we'll call you").
2. **스프링은 어떻게 동작하는가** — 요청이 오면 스프링이 내 코드를 찾아서 실행한다. "등록한 적도 없는 내 메서드를 어떻게 찾아 부르지?"가 리플렉션으로 내려가는 문.
3. **전개(순수 자바로 재현)** — ex01 하드코딩 분기 → ex02 리플렉션+표식(어노테이션)으로 찾아 호출 → ex03 폴더를 뒤져 표식 붙은 클래스만 자동 등록·실행.
4. **착지** — 스프링의 "알아서 찾아 실행"이 곧 리플렉션. 마법이 아니라 규칙.
   - 리플렉션 실습(ex01~03)은 "찾아서 호출·스캔"에 집중. 단, ex03의 "객체 자동 생성"에 이어 빈·의존성 주입(DI) 개념을 가볍게 얹는다(CH2 생성자 주입의 밑그림). 빈 스코프·주입 방식 등 깊은 DI 메커니즘은 유보.

### 최종 결과물

글·댓글·로그인이 되는 게시판 REST API. 본인만 자기 글·댓글을 수정·삭제할 수 있고, 조회 성능(N+1)까지 잡힌 상태.

## 버전 설계

CH1은 스프링 앱이 아니라 리플렉션 학습장(순수 자바)이라 앱 버전이 없다. 게시판 앱은 CH2에서 v0.1로 태어나 CH5에서 완성된다.

| 버전 | 챕터 | 뭘 만드나 | 끝나면 독자 눈에 보이는 것 | 핵심 변경점 | 다음으로의 "그런데…" |
|------|------|----------|--------------------------|------------|---------------------|
| (앱 아님) | CH1 | 리플렉션 3단계(순수 자바) | 콘솔에 `insert 호출됨` 등 — 어노테이션 표식만으로 메서드가 자동 호출·스캔되는 것 | ex01→ex02→ex03 | "이 원리 위에 세운 스프링으로 이제 진짜 만들자" |
| v0.1 | CH2 | 게시판 CRUD API | 글 목록·상세·작성·수정·삭제가 JSON으로 실제 동작 | `@RestController`, `EntityManager` 기반 JPA, 더티체킹 | 없는 글 조회 시 그대로 터짐 / 엔티티가 응답에 노출됨 |
| v0.2 | CH3 | 예외처리 + DTO | 없는 글 조회 시 깔끔한 404 JSON, 응답이 DTO로 정리됨 | `BoardResponse` DTO, `Optional`+`orElseThrow`, `@RestControllerAdvice` | 아무나 남의 글을 수정·삭제 가능 |
| v0.3 | CH4 | 인증/인가 | 로그인하면 JWT 발급, 남의 글 수정 시 403 | User 도메인, `JwtUtil`/`JwtProvider`, 필터(인증)+인터셉터(인가), 소유자 검증, Bean Validation, **`Board.user @ManyToOne(EAGER)` 연관관계 + `findByIdJoinUser`** | 글에 댓글을 달고 싶다 |
| v0.4 | CH5 | 댓글 + JPA 심화 | 게시글 상세에 댓글 목록 동반, 댓글 작성·삭제, N+1 해결 | `Reply` 도메인, `@OneToMany`, `Board.user` EAGER→LAZY 변경, fetch 전략, `fetch join`의 정체 이해 | (완성) |

## 전환점 상세

이 책의 "아하!" 지점은 두 곳이다.

- **CH1 착지 — "마법의 정체가 리플렉션이었다"**: 프레임워크가 블랙박스에서 "이해 가능한 규칙"으로 바뀌는 순간. 책의 정체성(마법을 벗긴다)이 성립하는 지점.
- **CH5 N+1 — "목록 하나 불렀는데 쿼리가 폭증한다"**: 잘 돌아가던 코드가 성능 문제로 뒤통수를 치는 순간. 지연 로딩과 `fetch join`을 손으로 겪으며 JPA를 "쓸 줄 안다"에서 "이해한다"로 넘어감. CH4에서 `EAGER`로 심어둔 연관관계가 CH5에서 성능 문제로 되돌아오는 구조라, "심은 게 돌아온다"는 서사가 이 전환점을 극적으로 만든다.

### CH4/CH5 집필 가드 (fetch join 회수 서사)

CH4 코드에는 이미 `findByIdJoinUser`(`join fetch b.user`)가 있고 게시글 상세·수정·삭제가 이를 호출한다. 따라서 CH5를 "N+1과 `fetch join`을 처음 만난다"로 쓰면 코드 사실과 어긋난다. 집필 원칙:

- **CH4**: `findByIdJoinUser`를 "작성자를 함께 가져오는 조회"로 **이름만** 사용한다. N+1·fetch 전략 이론은 CH5로 유보한다.
- **CH5**: 이 메서드를 "이미 썼지만 왜 필요했는지 이제 이해한다"는 **회수 서사**로 다룬다. `Board.user`를 EAGER에서 LAZY로 바꿔 N+1을 재현한 뒤, CH4에서 쓴 `findByIdJoinUser`가 사실 그 해법이었음을 밝힌다.

### CH5 fetch 실습 설계 주의 (code-analysis.md에서 이관)

ch05 코드에서 `Board.user`는 `LAZY`로 고정돼 있다. 그래서 `findByIdEager_test`와 `findByIdLazy_test`를 그대로 순서대로 실행하면 결과가 동일해 "즉시 로딩"이 눈에 안 드러난다. 실습 시나리오에 **"`Board.user`를 잠시 `EAGER`로 되돌려 실행 → 다시 `LAZY`로"** 하는 어노테이션 토글 단계를 명시해야 한다. N+1은 `findByIdLazyLoading_test`(`board.getUser().getUsername()` 호출 시점)에서 발생한다.

두 테스트 모두 `board.getId()`만 콘솔에 출력하고 user에 접근하지 않으므로, EAGER/LAZY 차이는 **콘솔 출력이 아니라 `spring.jpa.show-sql` SQL 로그**(find 시점에 join이 함께 나가는지)로만 관찰된다. 실습 안내에 "콘솔 출력은 같고, 차이는 SQL 로그에서 본다"를 반드시 넣어야 독자가 동일 출력에서 막히지 않는다.

## 버전별 예제 코드

버전 스냅샷은 이미 원천 코드에 챕터별로 분리돼 있다(`code/spring-ch01`~`spring-ch05`). 이를 기준으로 완성본(`spring-end`)·예제(`spring-start`) 레포를 만들 때 저자 결정을 반영한다.

| 버전 | 원천 코드 | 완성본 반영 시 적용할 저자 결정 |
|------|----------|------------------------------|
| CH1 | `code/spring-ch01` | 패키지는 `com.reflection` 유지(스프링 아님). IDE `main()` 실행 안내 |
| v0.1 | `code/spring-ch02` | 패키지 `com.metacoding.springv3` → `com.metacoding.spring` / `@Transactional` 스프링 것으로 통일(readOnly 없음) |
| v0.2 | `code/spring-ch03` | 위 + readOnly 제거, import 통일(설명 안 함) |
| v0.3 | `code/spring-ch04` | 위 + CORS 포함(깊이는 집필 시 결정) |
| v0.4 | `code/spring-ch05` | 위 + fetch 실습에 EAGER 토글 단서 반영 |

실제 `spring-end`/`spring-start` 레포 생성 및 패키지 리네임·readOnly 제거는 STEP 4~5(챕터 집필)에서 해당 챕터 작업 시 수행한다.
