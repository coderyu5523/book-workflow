# 챕터 0. 프롤로그

### 0.1 문제를 발견하다

두 달간 밤낮없이 매달렸던 웹사이트의 테스트가 드디어 완료되었습니다. 끝났다는 해방감에 젖어 있었습니다.

하지만 설레는 마음으로 운영 서버의 문을 연 순간, 잔인한 현실이 기다리고 있었습니다. 서버에 코드를 올리자마자 에러 메시지가 비명처럼 쏟아졌습니다.

Java 버전이 맞지 않았고 꼭 있어야 할 라이브러리는 보이지 않았습니다. 설정 파일 경로는 엉뚱한 곳을 가리키고 있었습니다. 하나를 겨우 고쳐놓으면 기다렸다는 듯 다른 곳에서 또 에러가 터져 나왔습니다.

*"제 컴퓨터에서는 분명히 잘 됐는데..."*

오늘만 벌써 세 번째, 힘없이 내뱉은 변명이었습니다. 원인은 명확했습니다. 제 컴퓨터와 운영 서버의 '환경'이 서로 달랐던 것입니다. 밤을 꼬박 새워 수동으로 버전을 맞추며 배포엔 성공했지만, 다음 업데이트 때 똑같은 짓을 반복해야 한다고 생각하니 앞이 캄캄해졌습니다.

그때였습니다. 멍하니 모니터를 보던 제 옆으로 선배가 다가와 툭 한마디를 던졌습니다.

> **선배**: "오픈아, Docker 한번 알아봐. 니 컴퓨터 환경을 통째로 싸서 어디든 가져갈 수 있거든."

### 0.2 Docker를 만나다

오픈이는 입사 3개월 차 주니어 개발자입니다.

> **오픈이**: "선배, Docker가 뭔데요? 환경을 통째로 옮긴다는 게 진짜 돼요?"
>
> **선배**: "가상화부터 알아야 돼. 그래야 Docker가 뭔지 감이 와."

선배가 주방에 비유해 주었습니다. 하나의 주방에 네 명의 요리사가 일하고 있다고 상상해 보라고. 요리사 수만큼 주방을 통째로 복제하면 비용이 어마어마합니다. 냉장고나 칼 같은 공용 설비는 함께 쓰되, 조리대만 각자 따로 마련하면 됩니다.

> **오픈이**: "아~ OS를 통째로 복사하는 게 아니라, 쓸 건 같이 쓰고 공간만 따로 나누는 거네요?"

Docker의 **컨테이너**는 바로 이 방식이었습니다. 하나의 OS 커널을 공유하되, 애플리케이션의 실행 공간만 따로 분리합니다.

직접 컨테이너를 띄워 그 안에 들어가 보았습니다. 패키지를 깔고 웹 서버를 실행해 보면서, 그제야 감이 오기 시작했습니다. 공들여 세팅한 환경을 **이미지**로 찍어 저장하면, 누구의 컴퓨터든 똑같은 환경을 꺼내 쓸 수 있었습니다.

이미지를 운영 서버에 올렸더니 로컬에서 보던 모습 그대로 동작했습니다.

기뻐하던 것도 잠시, 컨테이너를 삭제했더니 안에 저장해 둔 데이터까지 전부 사라졌습니다.

> **오픈이**: "선배! 데이터가 다 날아갔어요!"
>
> **선배**: "컨테이너 지우면 안에 있는 거 다 날아가. 중요한 건 **마운트**로 밖에 빼놔야 돼."

외장 하드를 꽂아두는 것처럼, 컨테이너가 사라져도 데이터는 바깥에 남았습니다.

이제 컨테이너 하나는 다룰 수 있게 되었습니다. 그런데 실제 서비스는 컨테이너 하나로 끝나지 않습니다.

> **오픈이**: "근데 이거 여러 개 한꺼번에 못 돌려요?"

### 0.3 자동화를 배우다

컨테이너를 새로 만들 때마다 같은 패키지를 일일이 설치하는 게 번거로웠습니다.

> **오픈이**: "또 설치야? 매번 이러면 진짜 귀찮은데..."
>
> **선배**: "밀키트 알지? **Dockerfile**이란 데 레시피를 적어두면 돼. 한 번 써두면 누가 돌려도 똑같은 환경이 나와."

파일 하나만 던져주면 늘 동일한 환경이 완성되었습니다.

서비스가 커지면서 또 다른 벽에 부딪혔습니다. 프론트엔드와 백엔드를 따로 돌려야 했고 사용자가 몰리면 서버도 늘려야 했습니다. 하나를 해결하면 또 다른 문제가 기다리고 있었습니다. 그러면서 컨테이너가 점점 늘어났습니다.

> **오픈이**: "이거 하나하나 띄우는 거 진짜... 배보다 배꼽이 더 커요."
>
> **선배**: "그럴 땐 **Docker Compose**지. 파일 한 장에 다 적어두고 명령어 한 줄로 싹 띄워버려."

docker-compose.yml에 전체 서비스의 지도를 그리고 `docker compose up` 한 줄을 입력했습니다. 프론트엔드, 백엔드, DB가 한꺼번에 깨어나 서로 대화를 나누기 시작했습니다.

> **오픈이**: "와 진짜 된다! 이게 한 줄이라니..."

풀스택 웹사이트까지 완성한 오픈이. 자랑스럽게 보여주자 선배가 물었습니다.

> **선배**: "잘했어. 근데 새벽에 서버 죽으면 누가 살려줄 건데?"

오픈이는 멈칫했습니다. 컨테이너가 죽으면 개발자가 직접 다시 띄워야 합니다. 새벽에 컨테이너가 죽으면? 누군가 직접 다시 띄워야 합니다.

### 0.4 Kubernetes를 만나다

새벽 3시, 오픈이의 핸드폰이 울렸습니다.

**"[ALERT] 백엔드 서버 응답 없음"**

잠에서 덜 깬 채로 노트북을 열었습니다. 백엔드 컨테이너가 메모리 부족으로 죽어 있었습니다. 급하게 복구했지만 그 사이 수십 명의 사용자가 이탈한 뒤였습니다.

다음 날 아침, 선배가 오픈이의 다크서클을 보고 물었습니다.

> **오픈이**: "선배 이거 자동으로 안 돼요? 죽으면 알아서 살아나게 할 순 없나..."
>
> **선배**: "Compose는 한 서버 안에서 묶어 돌리는 거잖아. 자동 복구에 무중단 배포까지 하려면 **Kubernetes**를 배워야 돼."

그렇게 새로운 항해가 시작되었습니다. "원하는 상태가 무엇인지"만 선언하면, "어떻게 복구할지"는 쿠버네티스가 알아서 맞춰 갑니다. 낯선 용어들이 쏟아졌지만, 하나씩 실습하며 제 것으로 만들었습니다.

테스트 삼아 컨테이너를 강제로 종료해 보았습니다. 쿠버네티스가 몇 초 만에 새 컨테이너를 띄워 빈자리를 채웠습니다. 새 버전을 배포해도 사용자가 눈치채지 못할 만큼 매끄러웠습니다. 설정을 코드 밖에서 관리하는 법을 익히고, 외부에서 도메인으로 접속할 수 있게 길도 열었습니다.

마지막으로, Docker Compose로 만들었던 풀스택 웹사이트를 쿠버네티스 위에 다시 배포했습니다.

> **오픈이**: "자동 복구도 되고 무중단 배포도 되고... 이제 새벽에 알람 안 울리겠죠?"

뿌듯해하는 오픈이를 보며 선배가 어깨를 툭 쳤습니다.

> **선배**: "필요할 때 하나씩 배우면 돼. 처음부터 다 알 필요 없어."

### 이 여정에서 만나게 될 것들

이 책은 오픈이가 걸어온 길을 그대로 따라갑니다. 하나의 웹사이트가 다섯 개의 챕터를 거치며 단계적으로 진화합니다.

각 챕터에는 **네트워크 돋보기**라는 심화 코너가 곳곳에 등장합니다. Docker 명령어 한 줄 뒤에서 실제로 무슨 일이 벌어지는지, 그 네트워크 원리가 쿠버네티스에서는 어떻게 확장되는지를 파헤칩니다. 지금 당장 이해가 안 되어도 실습에는 지장이 없으니, 부담스러우면 건너뛰고 나중에 다시 돌아와도 됩니다.

**1장 --- 왜 컨테이너인가**
컨테이너의 개념이 어디서 왔는지, 해상 운송의 역사에서부터 시작합니다. Docker와 Kubernetes가 각각 어떤 역할을 하는지 파악하고, 이 책의 학습 흐름을 한눈에 살펴봅니다.

**2장 --- Docker 이해하기**
Docker의 작동 원리를 이해하고 직접 설치해서 사용해 봅니다. 컨테이너를 띄우고, 이미지를 만들어 공유하고, 마운트로 데이터를 보호하는 기본기를 익힙니다.

**3장 --- Docker 다루기**
Dockerfile로 환경 구성을 자동화하고, 여러 컨테이너를 연결하며 실전 문제를 하나씩 해결합니다. 마지막에는 Docker Compose로 풀스택 웹사이트를 명령어 한 줄로 띄워봅니다.

**4장 --- Kubernetes 시작하기**
컨테이너가 죽으면 알아서 살려내고, 새 버전은 중단 없이 교체하는 쿠버네티스를 만납니다. 로컬에 클러스터를 구성하고 핵심 개념을 실습으로 익힙니다.

**5장 --- Kubernetes 운영하기**
설정과 민감 정보를 코드 밖에서 관리하고, 외부 요청을 도메인 기반으로 라우팅합니다. 3장에서 만든 풀스택 웹사이트를 쿠버네티스 위에 다시 배포합니다.

자, 그럼 1장에서 만나겠습니다.
