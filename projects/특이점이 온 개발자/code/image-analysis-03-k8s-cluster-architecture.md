# 이미지 분석 3: Kubernetes 클러스터 아키텍처 (심플 구조도)

## 다이어그램 개요

보라색 테마의 깔끔한 Kubernetes 클러스터 구조도입니다. 클러스터의 핵심 구성 요소인 제어 평면, 워커 노드, 인그레스 컨트롤러, kube-proxy, Pod의 배치 관계를 한눈에 보여줍니다.

---

## 구성 요소 분석

### 1. 인터넷 (외부)
- 구름 아이콘으로 표현
- 클러스터 외부에서 들어오는 트래픽의 출발점

### 2. KUBERNETES CLUSTER (최상위 경계)
- 전체 시스템을 감싸는 큰 박스
- 내부에 제어 평면과 워커 노드를 포함

### 3. 제어 평면 (CONTROL PLANE)
- 클러스터 상단에 위치
- 톱니바퀴 아이콘으로 "관리/제어" 역할을 시각화
- 클러스터 전체의 상태를 관리하고 의사결정을 내림
- API Server, Scheduler, Controller Manager, etcd 등이 여기에 속함 (다이어그램에서는 상세 생략)

### 4. 인그레스 컨트롤러
- 워커 노드 1 내부에 위치
- 라우터 아이콘으로 표현
- 인터넷에서 들어오는 트래픽을 수신하는 진입점
- 빨간 점(●)으로 외부 연결 포인트 표시
- L7 라우팅 수행 (URL/Host 기반)

### 5. 워커 노드 1
- **KUBE-PROXY**: 보라색 상단 아이콘으로 표현, 네트워크 규칙 관리
- **파드 1**: 애플리케이션 컨테이너 실행
- **파드 2**: 애플리케이션 컨테이너 실행
- 인그레스 컨트롤러가 이 노드에 배치됨

### 6. 워커 노드 2
- **KUBE-PROXY**: 노드 1과 동일하게 독립적으로 동작
- **파드 1**: 애플리케이션 컨테이너 실행
- **파드 2**: 애플리케이션 컨테이너 실행
- 인그레스 컨트롤러 없음 (노드 1에만 배치)

## 핵심 포인트

### 1. 제어 평면 vs 워커 노드 분리
| 구분 | 역할 | 비유 |
|------|------|------|
| **제어 평면** | 전체 클러스터 관리, 스케줄링, 상태 감시 | 본사 관리팀 |
| **워커 노드** | 실제 Pod(컨테이너) 실행 | 현장 작업자 |

### 2. KUBE-PROXY는 모든 워커 노드에 존재
- 노드 1에도, 노드 2에도 각각 독립적으로 동작
- 각 노드에서 Service → Pod로의 트래픽 전달 규칙(iptables)을 관리
- **DaemonSet**으로 배포되어 모든 노드에 자동 배치

### 3. 인그레스 컨트롤러는 특정 노드에 배치
- 이 다이어그램에서는 **워커 노드 1에만** 인그레스 컨트롤러가 있음
- 외부 트래픽의 단일 진입점 역할
- 실제 운영에서는 고가용성을 위해 여러 노드에 배치 가능

### 4. Pod는 워커 노드에 분산 배치
- 각 워커 노드에 2개씩 Pod가 실행 중
- Deployment가 관리하며 원하는 수만큼 자동 유지
- 스케줄러가 적절한 노드에 배치 결정

## 이 다이어그램이 강조하는 것

이 다이어그램은 복잡한 Kubernetes를 **3가지 핵심 질문**으로 단순화합니다:

1. **누가 관리하나?** → 제어 평면 (Control Plane)
2. **누가 실행하나?** → 워커 노드 (Worker Node)의 Pod
3. **트래픽은 어떻게 들어오나?** → 인터넷 → 인그레스 컨트롤러 → kube-proxy → Pod
