# Ch.3 매번 처음부터 깔 순 없잖아

> 한 줄 요약: Dockerfile로 이미지 빌드를 자동화하고, Nginx 리버스 프록시로 두 앱을 하나의 입구에서 접속한다
> 핵심 개념: Dockerfile (FROM, COPY, ENTRYPOINT), docker build, Nginx 리버스 프록시 (upstream, proxy_pass)

## 3. Dockerfile과 리버스 프록시

### 3.1 Dockerfile - 설계도

며칠 뒤, 오픈이에게 새 요청이 들어왔습니다. 직원 조회 앱 말고 팀 공지 앱도 하나 더 띄워달라는 것이었습니다. 에어컨 소리만 윙 돌아가는 사무실에서 오픈이는 터미널을 열었습니다. 화면에는 지난번에 실행한 명령어들이 빽빽하게 남아 있었습니다.

지난번처럼 컨테이너를 하나 띄우고, 안에 들어가서 필요한 걸 설치하고, docker commit으로 이미지를 만들 생각이었습니다. 그런데 뭘 먼저 설치했는지 순서가 기억나지 않았습니다.

*apt update를 먼저 했나? 설정 파일을 먼저 복사했나?*

뒤적거리다 겨우 떠올려서 다시 설치했지만, 이번에는 뭔가 빠졌는지 실행이 되지 않았습니다. commit은 "지금 이 상태를 통째로 저장"할 뿐, 어떻게 이 상태에 도달했는지는 기록하지 않습니다. 사진 한 장은 찍어뒀는데, 레시피가 없는 셈이었습니다.

팀장에게 물어봤습니다.

**팀장**: "새 직원이 들어올 때 사무실 세팅을 어떻게 해? 매번 네가 가서 책상 놓고 모니터 꽂아줘?"

**오픈이**: "아뇨, 세팅 매뉴얼을 써두면 되죠."

**팀장**: "그거야. Dockerfile이라는 게 그 매뉴얼이야."

사무실에 새 직원이 들어오면, 세팅 매뉴얼대로 책상을 놓고 모니터를 연결하고 필요한 서류를 비치합니다. 누가 해도 같은 사무실이 나옵니다. docker commit이 "완성된 사무실 사진을 찍어두기"였다면, Dockerfile은 "세팅 매뉴얼 한 장 써두기"입니다.

매뉴얼에 적는 항목은 세 가지입니다.

> **참고: Dockerfile 기본 명령어**
>
> | 명령어 | 역할 | 비유 |
> |--------|------|------|
> | `FROM` | 베이스 이미지 지정 | 빈 사무실에 들어갈 기본 가구 세트 선택 |
> | `COPY` | 호스트 파일을 이미지 안에 복사 | 필요한 서류를 책상 위에 비치 |
> | `ENTRYPOINT` | 컨테이너 시작 시 실행할 명령 | 출근하면 제일 먼저 하는 일 |

이 매뉴얼을 `docker build` 명령어에 넘기면, Docker가 한 줄씩 읽으면서 이미지를 만들어냅니다. 사람이 직접 컨테이너에 들어가서 설치할 필요가 없습니다.

### 환경 준비

이번 챕터에서 작성할 파일들입니다.

```
ex01/
├── app1/
│   ├── Dockerfile       [실습] Nginx 기반 앱 이미지
│   └── index.html       [참고] 정적 HTML
├── app2/
│   ├── Dockerfile       [실습] app2용 Nginx 이미지
│   └── index.html       [참고] 정적 HTML
├── lb/
│   ├── Dockerfile       [실습] 리버스 프록시 이미지
│   └── nginx.conf       [설명] upstream + proxy_pass 설정
└── README.md            [참고] 빌드+실행 명령어
```

| 분류 | 의미 | 이번 챕터 |
|------|------|----------|
| [실습] | 직접 작성하는 파일 | Dockerfile 3개 |
| [설명] | 코드를 읽고 이해하는 파일 | nginx.conf 1개 |
| [참고] | 이 챕터의 핵심이 아닌 파일 | HTML 2개, README 1개 |

[참고] 파일인 index.html은 간단한 HTML이니 직접 만들어도 되고, 완성 코드에서 복사해도 됩니다. 챕터를 따라 하며 [실습] 파일을 작성하고, 막히면 완성 코드를 참고하세요.

### 3.2 docker build - 이미지 빌드

오픈이는 가장 간단한 것부터 시작했습니다. 정적 HTML 페이지 하나를 보여주는 웹 서버 이미지를 만드는 것이었습니다.

app1 폴더에는 index.html이 이미 준비되어 있었습니다. "Nginx Server1"이라는 한 줄짜리 HTML입니다. 이 파일을 nginx 이미지 안에 넣으면 끝입니다.

app1 폴더에 Dockerfile을 작성했습니다.

```dockerfile
# app1/Dockerfile — TODO: Nginx 기반 웹 서버 이미지
# 1. nginx 공식 이미지를 기반으로 시작
FROM nginx
# 2. 같은 폴더의 index.html을 nginx 기본 경로에 복사
COPY index.html /usr/share/nginx/html
# 3. nginx를 포그라운드 모드로 실행
ENTRYPOINT ["nginx", "-g", "daemon off;"]
```

FROM으로 nginx 이미지를 가져오고, COPY로 HTML 파일을 nginx가 서빙하는 경로에 넣고, ENTRYPOINT로 nginx를 실행합니다. 세팅 매뉴얼 세 줄이 전부입니다.

이 Dockerfile로 이미지를 빌드했습니다.

```bash
docker build -t app1 ./app1
```

`-t app1`은 이미지에 "app1"이라는 이름을 붙이는 옵션이고, `./app1`은 Dockerfile이 있는 폴더 경로입니다. Docker가 Dockerfile을 위에서부터 한 줄씩 읽으면서 이미지를 조립해나갔습니다.

빌드가 끝나자 바로 컨테이너를 띄웠습니다.

```bash
docker run -dit -p 8000:80 app1
```

`-p 8000:80`은 호스트의 8000번 포트를 컨테이너의 80번 포트에 연결합니다. Ch.1에서 배운 포트포워딩이에요. 브라우저에서 `http://localhost:8000`에 접속하자 "Nginx Server1"이라는 글자가 떴습니다.

됐습니다. docker commit 없이 Dockerfile 세 줄과 build 한 줄로 이미지가 만들어졌습니다. 같은 Dockerfile로 빌드하면 누가 해도, 어떤 컴퓨터에서 해도 같은 결과가 나옵니다.

두 번째 앱도 같은 방법이었습니다. app2 폴더에 Dockerfile을 만들었습니다.

```dockerfile
# app2/Dockerfile — TODO: app2용 Nginx 이미지
# 1. nginx 공식 이미지를 기반으로 시작
FROM nginx
# 2. app2의 index.html을 복사
COPY index.html /usr/share/nginx/html
# 3. nginx를 포그라운드 모드로 실행
ENTRYPOINT ["nginx", "-g", "daemon off;"]
```

구조는 app1과 동일합니다. 달라지는 건 index.html 내용뿐이에요. app2의 HTML에는 "Nginx Server2"가 적혀 있습니다.

```bash
docker build -t app2 ./app2
docker run -dit -p 9000:80 app2
```

`http://localhost:9000`에 접속하면 "Nginx Server2"가 보입니다. 두 앱이 모두 떴습니다.

> **참고: docker build 주요 옵션**
>
> | 옵션 | 역할 |
> |------|------|
> | `-t 이름` | 이미지에 이름 지정 (`-t app1`) |
> | `경로` | Dockerfile이 있는 폴더 (`./app1`) |
> | `-f 파일명` | Dockerfile 이름이 기본값이 아닐 때 지정 |

### 3.3 Nginx 리버스 프록시 - 안내 데스크

앱 두 개가 돌아가고 있었습니다. 오픈이는 동료에게 테스트를 부탁했습니다.

**동료**: "이거 어디로 접속해? 8000? 9000?"

포트 번호를 알려줬지만 동료는 금방 헷갈려했습니다. 앱이 두 개일 때는 그나마 외울 수 있지만, 서너 개로 늘어나면 사용자에게 포트 번호를 외우라고 할 수는 없습니다.

*입구가 하나면 좋겠다.*

팀장이 지나가다 한마디 던졌습니다.

**팀장**: "건물 1층에 안내 데스크를 세워. /app1이면 1번 사무실로, /app2면 2번 사무실로 안내하는 거야."

건물에 들어오는 방문자는 층수를 몰라도 됩니다. 안내 데스크에서 "1번 팀이요"라고 하면 3층으로, "2번 팀이요"라고 하면 5층으로 안내받습니다. 방문자가 기억할 주소는 건물 입구 하나뿐입니다.

이런 역할을 하는 것이 리버스 프록시(Reverse Proxy)입니다.

> **참고: 리버스 프록시**
>
> 클라이언트의 요청을 받아서 뒤에 있는 서버로 전달해주는 중간 서버입니다. 클라이언트는 리버스 프록시의 주소만 알면 되고, 실제 서버의 주소나 포트를 몰라도 됩니다.

*하나의 입구(포트 80)로 여러 앱에 접속합니다*

Nginx가 이 안내 데스크 역할을 맡습니다. lb 폴더의 nginx.conf가 안내 규칙입니다.

```nginx
# lb/nginx.conf
# 1. app1 서버 그룹 정의 — 호스트의 8000번 포트로 연결
upstream app1 {
    server host.docker.internal:8000;
}

# 2. app2 서버 그룹 정의 — 호스트의 9000번 포트로 연결
upstream app2 {
    server host.docker.internal:9000;
}

# 3. 요청 경로에 따라 분배
server {
    listen 80;
    server_name localhost;

    location /app1 {
        proxy_pass http://app1/;
    }

    location /app2 {
        proxy_pass http://app2/;
    }
}
```

`upstream`은 뒤에 있는 서버를 이름으로 묶어두는 설정입니다. app1이라는 이름에 `host.docker.internal:8000`이 연결되어 있으니, 요청이 오면 호스트의 8000번 포트로 전달합니다. `location /app1` 블록은 "/app1" 경로로 들어온 요청을 `proxy_pass`를 통해 app1 upstream으로 넘기는 구조입니다. /app2도 마찬가지예요.

> **참고: upstream과 proxy_pass**
>
> | 설정 | 역할 |
> |------|------|
> | `upstream 이름 { server 주소:포트; }` | 뒤에 있는 서버를 이름으로 등록 |
> | `location /경로 { proxy_pass http://이름/; }` | 해당 경로의 요청을 등록된 서버로 전달 |

여기서 `host.docker.internal`이 눈에 들어옵니다. 컨테이너 안에서 호스트 PC를 가리키는 특수한 주소예요. lb 컨테이너가 app1, app2 컨테이너에 직접 접속할 방법이 아직 없어서, 호스트를 한 번 거쳐 우회하는 구조입니다.

> **주의: host.docker.internal**
>
> 이 주소는 Docker Desktop(Windows, Mac)에서만 동작합니다. Linux에서는 지원되지 않아요. 그리고 호스트를 한 번 거쳐야 하니 우회 경로인 셈입니다. 컨테이너끼리 직접 통신하는 방법은 Ch.6에서 Docker 네트워크를 배울 때 다룹니다.

lb의 Dockerfile은 app1/app2와 거의 같습니다. HTML 대신 nginx.conf를 복사한다는 점만 다릅니다.

```dockerfile
# lb/Dockerfile — TODO: 리버스 프록시 이미지
# 1. nginx 공식 이미지를 기반으로 시작
FROM nginx
# 2. 커스텀 설정 파일을 nginx 기본 설정 위치에 복사
COPY nginx.conf /etc/nginx/conf.d/default.conf
# 3. nginx를 포그라운드 모드로 실행
ENTRYPOINT ["nginx", "-g", "daemon off;"]
```

COPY 경로가 다릅니다. app1/app2에서는 HTML을 `/usr/share/nginx/html`에 넣었고, lb에서는 설정 파일을 `/etc/nginx/conf.d/default.conf`에 넣습니다. nginx가 웹 페이지를 제공하는 경로와 설정을 읽는 경로가 서로 다르기 때문이에요.

빌드하고 실행했습니다.

```bash
docker build -t lb ./lb
docker run -dit -p 80:80 lb
```

lb는 호스트의 80번 포트를 사용합니다. 이제 모든 요청이 80번 포트 하나로 들어옵니다.

브라우저에서 확인했습니다.

- `http://localhost/app1` → "Nginx Server1"
- `http://localhost/app2` → "Nginx Server2"

**동료**: "오, 이번엔 주소 하나로 다 되네."

## 이것만은 기억하자

| 개념 | 핵심 |
|------|------|
| Dockerfile | 이미지 빌드를 위한 설계도. FROM/COPY/ENTRYPOINT 세 줄이면 기본 이미지를 만들 수 있다 |
| docker build | Dockerfile을 읽어 이미지를 생성. `-t`로 이름 지정, 경로로 Dockerfile 위치 전달 |
| 리버스 프록시 | 하나의 입구에서 경로에 따라 뒤의 서버로 전달. Nginx의 upstream + proxy_pass |
| host.docker.internal | 컨테이너에서 호스트 PC를 가리키는 주소. Docker Desktop 전용, 우회 경로 |

Dockerfile 한 장이면 누구든 같은 이미지를 만들 수 있고, 리버스 프록시로 여러 앱을 하나의 입구에서 접속할 수 있게 됐습니다. 그런데 app1에 사용자가 몰리면 어떻게 될까요? 서버 하나로 감당이 안 될 때, 같은 앱을 여러 개 띄워서 요청을 나누는 방법을 다음 챕터에서 다룹니다.
