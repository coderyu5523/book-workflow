# Ch.4 혼자선 감당이 안 된다

> 한 줄 요약: 같은 앱을 여러 개 띄우고 요청을 나누면, 한 서버에 몰리지 않는다
> 핵심 개념: 수평 스케일링, 로드밸런싱, round-robin

## 4. 로드밸런싱 - 같은 사무실 두 개

### 4.1 사용자가 몰리다

app1이 잘 돌아가고 있었습니다. 며칠 뒤, 오픈이의 모니터 한쪽에 슬랙 알림이 떴습니다.

**동료**: "요즘 app1 접속하면 느려. 뭐 바꿨어?"

바뀐 건 없었습니다. 접속하는 사람이 늘어난 것뿐이었습니다. app1 컨테이너 하나가 모든 요청을 혼자 처리하고 있었으니, 사람이 몰리면 느려질 수밖에 없었습니다.

*서버를 더 좋은 걸로 바꿔야 하나?*

CPU나 메모리를 올리는 방법도 있지만, 한 대가 처리할 수 있는 양에는 천장이 있습니다.

### 4.2 수평 스케일링 - 복제

팀장이 힌트를 던졌습니다.

**팀장**: "사무실이 좁으면 같은 사무실을 하나 더 만들면 되지. 안내 데스크에서 번갈아 보내면 돼."

서버 성능을 올리는 건 수직 스케일링(Scale Up)입니다. 사무실을 더 넓은 곳으로 이사하는 것과 같습니다. 반면, 같은 서버를 하나 더 띄우는 건 수평 스케일링(Scale Out)입니다. 같은 크기의 사무실을 하나 더 만드는 거예요.

> **참고: 수직 스케일링 vs 수평 스케일링**
>
> | 방식 | 설명 | 비유 |
> |------|------|------|
> | 수직 스케일링 (Scale Up) | 서버 성능을 올린다 (CPU, RAM 증가) | 사무실을 더 넓은 곳으로 이사 |
> | 수평 스케일링 (Scale Out) | 같은 서버를 여러 개 띄운다 | 같은 사무실을 하나 더 만든다 |

Ch.3에서 app1과 app2는 서로 다른 앱이었습니다. 안내 데스크(리버스 프록시)가 /app1이면 1번 사무실, /app2면 2번 사무실로 보내줬습니다. 이번에는 다릅니다. 같은 앱을 두 개 띄우고, 안내 데스크가 번갈아 보내는 겁니다.

이걸 로드밸런싱(Load Balancing)이라고 합니다. 요청을 여러 서버에 골고루 나누는 것이에요. 가장 단순한 방식은 라운드 로빈(Round Robin)으로, 순서대로 돌아가면서 하나씩 보냅니다.

> **참고: 로드밸런싱과 라운드 로빈**
>
> 로드밸런싱은 요청을 여러 서버에 분산하는 것입니다. 라운드 로빈은 가장 단순한 분산 방식으로, 1번 → 2번 → 1번 → 2번 순서대로 돌아가며 보냅니다.

### 환경 준비

클론한 레포에서 이번 챕터의 폴더로 이동합니다.

```bash
cd ex02
```

```
ex02/
├── app1/
│   ├── Dockerfile       [실습] 로드밸런싱 대상 앱 이미지
│   └── index.html       [참고] 정적 HTML
├── lb/
│   ├── Dockerfile       [실습] 로드밸런서 이미지
│   └── nginx.conf       [실습] upstream에 서버 2개 → round-robin 분산
└── README.md            [참고] 동일 이미지 2개 실행 명령어
```

app1/Dockerfile과 lb/Dockerfile은 Ch.3(ex01)과 동일합니다. 달라진 건 nginx.conf뿐입니다.

### 4.3 실습: nginx.conf - round-robin

Ch.3에서 nginx.conf에는 upstream이 두 개(app1, app2)였고, 각각 다른 포트를 가리켰습니다. 이번에는 upstream이 하나인데, 그 안에 서버가 두 개입니다.

```nginx
# lb/nginx.conf — TODO: upstream에 서버 2개 → round-robin 분산
# 1. app1 서버 그룹에 서버 2개 등록
upstream app1 {
    server host.docker.internal:8000;
    server host.docker.internal:8001;
}

# 2. /app1 요청을 app1 그룹으로 전달
server {
    listen 80;
    server_name localhost;

    location /app1 {
        proxy_pass http://app1/;
    }
}
```

upstream app1 안에 server가 두 줄입니다. Nginx는 이 두 서버에 요청을 번갈아 보냅니다. 별도 설정 없이도 기본 동작이 라운드 로빈이에요.

Ch.3의 nginx.conf와 비교하면 차이가 명확합니다.

> **참고: Ch.3 vs Ch.4 nginx.conf**
>
> | 항목 | Ch.3 (리버스 프록시) | Ch.4 (로드밸런싱) |
> |------|---------------------|-------------------|
> | upstream 개수 | 2개 (app1, app2) | 1개 (app1) |
> | server 개수 | 각 upstream에 1개 | 1개 upstream에 2개 |
> | 동작 | 경로별로 다른 앱으로 라우팅 | 같은 앱에 번갈아 분산 |

### 4.4 실행과 확인

이미지를 빌드하고, 같은 이미지로 컨테이너를 두 개 띄웠습니다.

```bash
docker build -t app1 ./app1
docker run -dit -p 8000:80 app1
docker run -dit -p 8001:80 app1
```

같은 이미지 `app1`을 두 번 실행했습니다. 첫 번째는 8000번 포트, 두 번째는 8001번 포트에 연결됩니다. 이미지는 하나인데 컨테이너가 두 개입니다. 같은 사무실이 두 개 생긴 셈이에요.

lb도 빌드하고 실행했습니다.

```bash
docker build -t lb ./lb
docker run -dit -p 80:80 lb
```

오픈이는 브라우저에서 `http://localhost/app1`에 접속했습니다. "Nginx Server1"이 나왔습니다. 새로고침을 눌러봤습니다. 같은 화면이었습니다.

*정말 분산되고 있는 건가?*

두 컨테이너가 같은 이미지에서 만들어졌으니 같은 HTML을 보여주는 게 당연합니다. 화면만 봐서는 알 수 없었습니다.

키보드를 두드리며 lb 컨테이너의 로그를 확인해봤습니다.

```bash
docker logs <lb-컨테이너-ID>
```

## 이것만은 기억하자

| 개념 | 핵심 |
|------|------|
| 수평 스케일링 | 서버 성능을 올리는 대신, 같은 서버를 여러 개 띄운다 |
| 로드밸런싱 | 요청을 여러 서버에 분산. Nginx upstream에 server를 여러 개 등록 |
| 라운드 로빈 | 가장 단순한 분산 방식. 순서대로 돌아가며 배분. Nginx 기본 동작 |

같은 이미지를 여러 개 띄우고 요청을 나눌 수 있게 됐습니다. 그런데 같은 요청이 반복될 때마다 서버가 매번 처음부터 처리하고 있었습니다. 한 번 처리한 결과를 저장해두면 더 빨라지지 않을까요? 다음 챕터에서 Nginx 캐싱을 다룹니다.
